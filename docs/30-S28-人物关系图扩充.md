### 3.2 别名归一化（关键）

**问题**：源数据里「花袭人」「珍珠」和「袭人」是三个独立节点，其实是同一人。

**做法**：建立 `ALIAS_GROUPS`（全名 → 所有简称），建边前先把两个端点都映射到规范名：

```python
ALIAS2CANON = {}
for full, shorts in ALIAS_GROUPS.items():
    ALIAS2CANON[full] = full
    for s in shorts:
        ALIAS2CANON[s] = full

def canonical(name):
    return ALIAS2CANON.get(name, name)

# 建边时
h2, t2 = canonical(h), canonical(t)
if h2 == t2: continue      # 归一化后可能自环
```

**效果**：58 条三元组被改写，合并了重复人物。

### 3.3 提及统计含别名

```python
def variants(name):
    """返回某人物的所有称呼"""
    out = {name}
    out.update(ALIAS_GROUPS.get(name, []))
    if name in SHORT2FULL:
        out.add(SHORT2FULL[name])
        out.update(ALIAS_GROUPS.get(SHORT2FULL[name], []))
    return out

# 统计时
for n in names:
    vs = variants(n)
    mention[n] = sum(txt.count(v) for txt in corpus.values() for v in vs)
```

### 3.5 家族归属规则补全

**问题**：贾代善、贾珠、贾敏、贾演、贾敬、贾代化、贾源等贾家成员全被归到「其他」，勾选「贾」家族时看不到他们。

**做法**：`FAMILY` 人工表 + 规则推断

```python
FAMILY_RULES = [
    (lambda n: n.startswith("贾") and len(n) >= 2, "贾"),
    (lambda n: n in {"贾母", "史太君", "王夫人", "邢夫人", "李纨", ...}, "贾"),
    (lambda n: n.startswith("史") and len(n) >= 2, "史"),
    (lambda n: n.startswith("王") and n not in {"王嬷嬷", "王善保"}, "王"),
    (lambda n: n.startswith("薛") and len(n) >= 2, "薛"),
    (lambda n: n.startswith("林") and len(n) >= 2, "林"),
]
```

## 五、附带发现并修复：索引被旧脚本污染

验证过程中发现 **chunk 数从 11,780 变成了 13,124**，脂批从 8,510 变成 9,854。

### 排查过程

1. 源文件正常：`pizhu.jsonl` 3,234 条 / 88,008 字
2. HBase 里 `fuqinju|pizhu` 有 4,563 行（应为 3,219）
3. 抽查行内容：`m:strategy_rev = 'v2-pizhu'` ← **旧版策略标识**
4. 当前脚本 `s10_1_unify_pizhu.py` 写的是 `v3-pizhu3src`

### 根因

今天 12:15 有人（或某流程）运行了**旧脚本 `s5_4_add_pizhu.py`**，而不是 `s10_1_unify_pizhu.py`。
旧脚本用 `v2-pizhu` 策略切分，粒度更细（4,563 条），覆盖了正确的 v3 数据。

### 修复

用正确脚本重建：

```bash
docker exec master bash -lc "cd /workspace/pipeline && python3 s10_1_unify_pizhu.py"
```

```

源B 脂批大全: 9,000
源C 癸酉本批语: 223
去重: 12,457 → 8,662（合并重复 3,729）
chunk 数: 8,662
hlm_chunks 总行数: 11,780   ← 恢复正确
```

验证：`strategy_rev: {'v3-pizhu3src': 3219}` ✅

### 教训

**必须校验 `strategy_rev`**。数据量对不上时，第一件事应该是查策略版本号，而不是猜。

## 七、关于「为什么耗时这么长」

用户中途问了这个问题，如实回答：

| 环节 | 实际耗时 | 本可以 |
|:---|:---|:---|
| 全盘 `Get-ChildItem -Recurse` 搜文件 | 跑超时 3 分钟，转后台 | 看构建脚本里的路径变量，1 次就够 |
| 探测 4 个数据源 | 分了 3 轮 | 1 个脚本一次查完 |
| 家族归属 | 跑→看→补规则→再跑，迭代 3 次 | 一开始就把规则写进去 |
| 脚本 bug（`cst.strftime`）| 白跑一次 | 写完先本地 dry-run |
| 别名重复节点 | 跑完才发现 | 第一次写就该想到 |

**核心教训**：这是「先做一版，再根据结果迭代修补」的方式。
正确做法是**先想清楚完整需求清单，再动手**。这个需求的完整清单一开始就该是：
①合并多源 ②别名归一 ③家族规则 ④提及含别名 ⑤节点上限。
我当时只想到 ①④⑤，②③是撞见才补的。
