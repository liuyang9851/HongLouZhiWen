> 日期：2026-10-24

> 结论：**用户判断完全正确。这不是显示问题，是 PDF 提取层的真实缺陷。**

## 二、4 种截断缺陷（逐个定位）

### 缺陷 1：宋体补字被当作正文结束

PDF 里生僻字用宋体补排，夹在楷体批语中间：

```
y=433.5  x=54.2   KaiTi  '主，以《'              ← 批语
y=433.5  x=147.1  SimSun '姽婳'                  ← 生僻字补字！（同一 y）
y=433.5  x=193.5  KaiTi  '词》为宾，以宝玉古歌为主，以贾'
```

旧逻辑 `else: flush()` → 遇到宋体就结束批语 → **从「以《」处腰斩**。

### 缺陷 2：跨页批语被截断

第 2 回一条长批语横跨 p59→p60，旧逻辑每页结束必 flush：

```
p59 末行：'…今先写外戚者，正是'          ← 批语未完
p60 首行：'写荣国一府也。故又怕闲文赘累…'  ← 续文，无任何标记
```

→ 旧数据只到「正是」（222 字），完整应为 **413 字**。

### 缺陷 3：双行夹批被正文截断

批语以小字并排插在正文行间，同一 y 上左右并列：

```
y=484.0  x=54.2   KaiTi  '急切之者，百事无成。正为后文作引线。'   ← 批语（左）
y=484.0  x=402.7  SimSun '如何肯又回家'                        ← 正文（右）
```

旧逻辑遇到右侧宋体就 flush → 批语在此结束。

### 缺陷 4：行内版型标记被当新批语

EUDC 私用区字形有时是**行内插入的版型标记**，不是新批语的开头：

```
y=563.1  x=54.2   KaiTi  '东坡十年寿，亦能跳出这圈子来。”斯言信矣。'
y=563.1  x=466.8  EUDC   '\ue054\ue054'      ← 行内标记，不是新批语
y=563.1  x=503.2  KaiTi  '“就'               ← 同一句继续
```

旧逻辑遇到 EUDC 就 `flush() + 开新记录` → 一句批语被切成两截。

## 三、修复方案

新建 `pipeline/s12_1_fix_pizhu_truncation.py`，逐个解决：

| 缺陷 | 修法 |
|:---|:---|
| 1 宋体补字 | 同 y + 后方紧跟楷体 → 并入 buf，不 flush |
| 2 跨页截断 | 页末若仍在收集 + 下一页首是楷体 → 带状态到下一页（`carry`） |
| 3 双行夹批 | 同 y + 该宋体 x 比上一条楷体 x 靠右 60pt 以上 → 跳过，不 flush |
| 4 行内 EUDC | 同 y + 后方紧跟楷体 → 忽略该标记，继续收集 |

### 3.1 关键：跨页时 page 要记「起始页」

跨页续接后 `flush()` 发生在结束页，但旧数据的 `page` 是起始页。
若不修正，新旧对齐 key 会错位 → 替换失败。用 `st['start_pi']` 记录起始页。

### 3.2 关键：新旧数据对齐要四级降级

| 级别 | 匹配方式 | 适用 |
|:---|:---|:---|
| ① | `(hui, page, 前10字)` | 常规情况 |
| ② | `(hui, 前10字)` 且唯一 | page 因跨页变化 |
| ③ | 同页桶内「旧文本是新文本真子串」最长 | 前缀不同（行内 EUDC 切开） |
| ④ | 同页桶内相似度 ≥ 0.75 且新更长 | 文本顺序被打乱（实测 ratio 0.80） |

**踩过的坑**：第③④级匹配成功后，仍被一道硬校验
`if not (ok_ in nk_) continue` 拦掉 —— 相似度匹配的语义本就是「不包含但相似」，
这道校验与它直接冲突。改为按匹配级别区分校验方式。

## 五、数据同步链路（踩过的坑）

修复后要同步 4 个地方，**漏一个前端就看不到**：

```
PDF 原文
   ↓ s12_1 提取修复
hlm_corpus/fuqinju/pizhu.jsonl          （主数据，带 repaired 标记）
   ↓ 同步（字段更全的旧文件也要更新）
码点核对/pizhu_redecoded.jsonl          （build_ui_data.py 读这个！）
   ↓ build_ui_data.py
web/data/pizhu.json                     （前端批语样本）
   ↓ s7_3_build_webdata.py
web/data/versions/fuqinju/chapter_*.json（阅读界面实际读这个！）
   ↓ s10_1_unify_pizhu.py

```

**踩的坑**：
1. 只改了 `hlm_corpus/fuqinju/pizhu.jsonl`，但 `build_ui_data.py` 读的是 `码点核对/pizhu_redecoded.jsonl` → 前端没变
2. 改了 `web/data/pizhu.json`，但阅读界面读 `web/data/versions/fuqinju/chapter_078.json` → 还是没变

## 六、附带发现：脂批大全数据质量差

检索时会同时命中三源，发现**脂批大全**的文本有明显噪音：

```
脂批大全:  '文有宾主，不可误。此文以《��词》为宾，以宝玉古诗（左言右奇）为主…'
           ↑ U+FFFD 乱码        ↑ 注音形式「（左言右奇）」
脂批大全:  '呆~阿)78.文有宾主不可误。此文以芙蓉诔为主…'
           ↑ 前缀噪音「呆~阿)78.」
```

而抚琴居校本的修复版是干净的：
```
抚琴居:    '文有宾主，不可误。此文以《芙蓉诔》为主，以《姽婳词》为宾…'
```

**这说明保留三源是必要的** —— 抚琴居校本是质量最高的来源，
脂批大全只能作补充（覆盖前两源没有的条目）。

## 九、教训

| # | 教训 |
|:---|:---|
| 1 | **「数据不完整」要往上游追，不要在下游打补丁**。用户说「可能是从 pdf 处理时有问题」，判断准确 —— 前端显示的是数据的忠实投影，数据错了显示必然错。 |
| 2 | **PDF 文本层的信息要充分利用**。旧脚本只看字体名，没看 y/x 坐标；而补字、双行夹批、行内标记这三类问题**全都只能靠坐标判断**。 |
| 3 | **一次只修一种模式会反复失败**。我先修了补字 → 出现跨页问题；修了跨页 → 出现双行夹批；修了夹批 → 出现行内 EUDC。这 4 种是同一份 PDF 的四种排版特征，必须一起处理。 |
| 4 | **同步链路要画出来**。同一条数据流经 4 个文件到前端，漏一个就白干。 |
