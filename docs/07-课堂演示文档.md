# 第一部分 · 项目介绍

## 1.1 一句话开场

> 我把《红楼梦》前 80 回（60 万字）加 8,510 条脂批（三源：抚琴居 3,219 + 癸酉本 222 + 脂批大全 5,069），
> 做成一个**能溯源的知识问答系统** —— 每个答案都能点回原文具体段落。
> 而**文本和向量全部存在 Hadoop 里**：HDFS 存事实源，HBase 存索引，MapReduce 做统计，Hive 提供 SQL。

## 1.2 要解决什么问题

普通的 RAG  Demo 大概是这样的：

```
用户问 → 向量检索 → LLM 生成 → 给个答案
                                   ↑ 无法验证对不对
```

**三个致命问题**：

| 问题 | 后果 |
|:---|:---|
| 答案没有出处 | 用户不知道是原文还是编的 |
| 检索只有一路 | 关键词对了但语义不对，或反过来 |
| 向量存 Milvus/Pinecone | **违反本项目的硬性要求**（必须用 Hadoop 生态） |

## 1.3 我们的做法

```
用户问
  ↓
① 问题路由（4 条通道：主观/元数据/统计/普通）
  ↓
② 查询改写 + 别名展开
  ↓
③ 三路检索：bigram 倒排 + 512 维向量 + 图谱共现
  ↓
④ RRF 融合
  ↓
⑤ DeepSeek 生成（流式）
  ↓
⑥ 引用溯源：每条 [n] 可点回原文并高亮
```

## 1.4 成果数字

| 项 | 值 |
|:---|---:|
| 语料 | 前 80 回 / 60 万字 / 8,510 条脂批（三源：抚琴居 3,219 + 癸酉本 222 + 脂批大全 5,069） |
| 索引 | **11,780 chunk**（正文 3,270 + 脂批 8,510） |
| 脂批来源 | 3 源：抚琴居校本 3,219 / 癸酉本 222 / 脂批大全 5,069 |
| 向量 | 11,780 × 512 维 |
| HBase 表 | 5 张 / 606,783 行 |
| MapReduce 作业 | 4 个（全部成功） |
| 界面 | 6 个 |
| 评测 | 事实型 100% 命中 / 拒答 100% / 推理型 3.6/5 |

## 2.2 Hadoop 各组件在本项目中的角色

| 组件 | 本项目用来做什么 | 具体证据 |
|:---|:---|:---|
| **HDFS** | 存事实源：chunk 正文、向量快照、MR 结果、问答日志 | `/hlm` 下 6 个目录，19 个子目录 |
| **HBase** | 存派生索引：chunk / 向量 / 倒排 / 词频 / 统计 5 张表 | 606,783 行 |

## 2.3 最关键的设计：事实源 vs 派生层

```
事实源（HDFS，可靠、可追溯）
  chunks.jsonl         2.0 MB
  vectors.jsonl        2.8 MB
  pizhu_chunks.jsonl   1.3 MB
  pizhu_vectors.jsonl  8.8 MB
        ↓ 可全量重建
派生索引（HBase，低延迟）
  hlm_chunks   11,780 行
  hlm_vectors  11,780 行
  hlm_terms   448,841 行
```

**为什么这么分？**（教材 §3.10.4 原话）：

> 事实源必须可靠、可追溯、有版本；派生层按访问模式选存储、坏了能从事实源重建。

**我们真的验证过**（后面演示会做）：
删掉 3 张 HBase 表 → 从 HDFS 重建 → 检索结果**逐条完全一致**。

## 2.4 HBase 行键设计（重点）

```
rowkey = <version> | <source> | <hui:03d> | <chunk_id>
          fuqinju  |  text    |  003      |  bde3ef…
          fuqinju  |  pizhu   |  003      |  001190a5…
```

| 段 | 作用 |
|:---|:---|
| `version` 在最前 | 按版本扫描一次搞定；不同版本的同一位置**永不串版本** |
| `hui:03d` 补零 | 字典序 = 数值序，可按回次范围扫描 |
| `chunk_id` 在尾 | 同回内排序稳定 |

**这是「版本不破坏分区」的直接实现**：版本进 rowkey 前缀 → 分区（按回次）与版本**正交**。

## 2.5 RAG 三个关键决策

| 决策 | 选择 | 为什么 |
|:---|:---|:---|
| 分块 | 场景段合并，300–800 字 | 实测 min/mean/p95/max = 151/589/786/879，分布集中 → 分区也均衡 |
| 融合 | RRF（k=60） | 关键词得分 [0,1]、向量得分 [-1,1]，量纲不同，只用排名 |
| 向量存 | HBase `float32 bytes` | 11,780 条 = 8.3 MB（base64 要 11.1 MB，JSON 要 83 MB） |

### 3.3.3 【重点讲解】HDFS 块与副本

**讲解要点（对照输出讲）**：

| 输出 | 含义 | 教材对应 |
|:---|:---|:---|
| `len=2099616` | 这个块 2.00 MB | 块大小 |
| `Live_repl=2` | 2 个副本 | `dfs.replication=2` |
| 两个 `DatanodeInfoWithStorage[172.19.0.4…]`、`[172.19.0.3…]` | 副本分布在 slave1 和 slave2 | **副本不放在同一节点** |


> 我们仍然用 HDFS 的理由是：课程要求用 Hadoop 生态 + 事实源需要多副本容错 + 可审计。
> **这个取舍要不回避地说出来，不能装作没这问题。**

### 3.3.5 【踩坑演示】MapReduce 输入目录不能以 `_` 开头

```powershell
$ docker exec master bash -lc "hdfs dfs -mkdir -p /hlm/_demo_in"
```
> 故意建一个下划线开头的目录

```powershell
$ docker exec master bash -lc "hdfs dfs -put -f /workspace/pipeline/out/chunks.jsonl /hlm/_demo_in/"
```
> 把文件放进去

```powershell
$ docker exec master bash -lc "hdfs dfs -ls /hlm/_demo_in/"
```
> 确认文件**确实存在**

```powershell
$ docker exec master bash -lc "hadoop jar /opt/hadoop/share/hadoop/tools/lib/hadoop-streaming-3.3.6.jar -input /hlm/_demo_in -output /hlm/_demo_out -mapper 'wc -l' -reducer 'wc -l' 2>&1 | grep -i 'invalid\|not exist' | head -3"
```
> 用这个下划线目录当输入跑一个最简作业 —— **会报 Input path does not exist**

**预期输出**：
```
InvalidInputException: Input path does not exist: hdfs://master:9000/hlm/_demo_in
```

> **讲解**：`ls` 能看到文件，作业却说「不存在」。
> 根因是 Hadoop `FileInputFormat` 会**静默过滤** `_` 和 `.` 开头的路径
> （这是约定：`_SUCCESS`、`.crc` 这类元数据文件不该被当数据）。
> **修法**：输入目录不要用下划线开头。
>
> 这个坑在教材上不会写，但实际一定会遇到 —— 演示出来比讲十遍都管用。

```powershell
$ docker exec master bash -lc "hdfs dfs -rm -r -f /hlm/_demo_in; hdfs dfs -rm -r -f /hlm/_demo_out"
```
> 清理演示用的临时目录

```
  向量 rowkey = fuqinju|001|10f1ef930816dfd9
    v:emb 字节数 = 2048 (= 512 × 4 = 2048)
```

### 3.4.3 【重点讲解】HBase 行键与预分区

```powershell
$ docker exec master bash -lc "printf 'describe \'hlm_chunks\'\n' > /tmp/d.rb; hbase shell -n /tmp/d.rb | grep -E 'NAME|VERSIONS'"
```
> 查看 hlm_chunks 的列族定义

**预期输出**：
```
{NAME => 'd', VERSIONS => '1', …}
{NAME => 'm', VERSIONS => '1', …}
```

**讲解要点**：

| 设计 | 值 | 为什么 |
|:---|:---|:---|
| 列族 `d` / `m` | data / meta | 正文大且整取、元数据小且过滤 → **不同访问模式分开** |
| `VERSIONS => 1` | 只留 1 版 | 语料静态，不需多版本，省空间 |

```powershell
$ docker exec master bash -lc "printf 'split \'hlm_chunks\'\n' > /tmp/s.rb; hbase shell -n /tmp/s.rb"
```
> 查看表被切成了哪些 region（验证预分区生效）

**讲解要点（写热点治理）**：

```
create 'hlm_chunks', {NAME=>'d',VERSIONS=>1}, {NAME=>'m',VERSIONS=>1},
       SPLITS => ['1','2','3','4','5','6','7']
```

- rowkey 首字符是回次的十位（`0`~`7`）
- `SPLITS => ['1'..'7']` → 切成 **8 个 region**
- 8 个 region 可以并行接收写入，不是「先写满一个 region 再分裂」
- **实测**：1,035 行写入 2.5 秒（约 414 行/秒）；8,510 行脂批 4.4 秒

### 3.4.4 抽样看一条 chunk

```powershell
$ docker exec master bash -lc "printf 'get \'hlm_chunks\', \'fuqinju|text|003|034acbced041747a\'\n' > /tmp/g.rb; hbase shell -n /tmp/g.rb | head -8"
```
> 按 rowkey 点查一个 chunk，看正文和元数据

**讲解要点（对照 rowkey 讲设计）**：

```
rowkey = fuqinju | text | 003 | 034acbced041747a
         ↑版本     ↑来源  ↑回次 ↑chunk_id
```

- `fuqinju` 在最前 → 按版本扫描一次搞定
- `text` → 区分正文 chunk 和脂批 chunk
- `003` → 补零三位，字典序 = 数值序
- `034acb…` → 16 位 hash，同回内排序稳定

## 3.6 Hive SQL 查询

### 3.6.1 建 Hive 外部表

```powershell
$ docker exec master bash -lc "cd /workspace/pipeline && python3 s3_to_hbase_hive.py"
```
> 把 MR 结果写进 HBase（hlm_wordfreq / hlm_stats），并建 4 张 Hive 外部表

**讲解要点**：

```sql
CREATE EXTERNAL TABLE hlm_word_freq (bigram STRING, cnt INT)
  ROW FORMAT DELIMITED FIELDS TERMINATED BY '\t'
  STORED AS TEXTFILE LOCATION '/hlm/mrout/wordfreq';
```

- `EXTERNAL` + `LOCATION` → **删表不删数据**
- 这与「HDFS 是事实源」的原则一致：Hive 只是给 HDFS 上的文件套一层 SQL 视图

### 3.6.2 用 SQL 查统计结果

```powershell
$ docker exec master bash -lc "beeline -u jdbc:hive2://master:10000 -n root --outputformat=tsv2 -e 'SELECT bigram, cnt FROM hlm_word_freq ORDER BY cnt DESC LIMIT 10' 2>/dev/null | grep -v SLF4J | head -12"
```
> 用 SQL 查词频 Top-10（底层会自动跑一个 MapReduce 作业）

```powershell
$ docker exec master bash -lc "beeline -u jdbc:hive2://master:10000 -n root --outputformat=tsv2 -e 'SELECT hui, n_chunk, n_chars FROM hlm_chunk_stat ORDER BY n_chunk DESC LIMIT 5' 2>/dev/null | grep -v SLF4J | head -8"
```
> 用 SQL 查「chunk 最多的 5 回」

**预期输出**：
```
67	39	22349
78	21	11457
77	20	10758
62	20	11988
74	19	11159
```

> **讲解要点**：Hive 的 `ORDER BY` 会触发一个 MapReduce 作业（可以在 YARN UI 上看到）。
> 这就是「SQL on Hadoop」的本质：**SQL 是接口，底层还是 MapReduce**。

### 3.6.3 【踩坑演示】分隔符必须与文件格式一致

```powershell
$ docker exec master bash -lc "beeline -u jdbc:hive2://master:10000 -n root --outputformat=tsv2 -e 'SELECT a, b, cnt FROM hlm_cooccur ORDER BY cnt DESC LIMIT 5' 2>/dev/null | grep -v SLF4J | head -7"
```
> 查人物共现 Top-5（三列：a / b / cnt）

**讲解要点**：

> 共现作业最初输出的是 `a|b \t 1`（两列），
> Hive 按 tab 分列后，`a|b` 整列塞进 `a` 字段，`b` 变成 NULL。
> **Hive 不会报错，只会静默给 NULL** —— 这是最容易漏的坑。
> 改成 `a \t b \t 1`（三列）后才正确。


**预期输出**：

```
Q: 如果穿越到《红楼梦》，你会选谁？
A: 这是一个主观判断 / 假设性问题，超出《红楼梦》语料可以回答的范围。
   本系统的定位是「基于语料的可追溯问答」—— 每个结论都必须能落到原文出处。
   而「谁更伟大」「你会选谁」这类问题没有客观答案，语料里也没有依据，
   硬答只会变成编造。
   建议换个问法，例如：
   - 「为什么说《红楼梦》在叙事上很独特？」
   - 「小红（林红玉）在书中是个什么样的人？」
```

> **讲解**：这类问题现在 **0.1 ms** 就答完（不调 LLM，省 token）。
> 实测 10 条应拒答问题，**正确拒答率 100%**。

> **这里可以讲一个真实的迭代故事**：
> 加入脂批索引后，拒答率从 100% 掉到 90% ——
> 因为索引变大后模型能检索到更多片段，开始「先说没有、再做推断」。
> 这是个**主指标在涨、副作用在跌**的典型场景。
> 如果只看一个总分，这个回退会被平均掉，根本看不见。
> **这就是「不合成单一准确率」的意义。**

### 3.9.3 【验证 C】分区方案对比（R-508）

```powershell
$ cd D:\学校事务\大数据原理与应用\红楼智问\pipeline
```
> 回到本地管道目录（这个脚本不需要容器）

```powershell
$ python s2_4_partition_compare.py
```
> 计算 4 种分区方案的记录数与负载比

**预期输出**：
```
方案                                    分区数      总记录         总字节    记录max/mean    字节max/mean
A 章节范围分区（每10回一区）                   8    1,035   1,826,580         1.229         1.240
B chunk_id 哈希分区（8 区）                  8    1,035   1,826,580         1.105         1.110
B' chunk_id 哈希分区（16 区）               16    1,035   1,826,580         1.268         1.292
C 按版本分区（仅 1 版本 → 退化）               1    1,035   1,826,580         1.000         1.000
```

**讲解话术（三个反直觉结论）**：

> **结论 1：范围分区的负载比（1.229）反而比哈希（1.105）差，但都远低于阈值 2。**
>
> 为什么教材说「范围分区容易热点」，我们这里却没有？
> 因为我们的切分单元是「场景段」而不是「整回」，
> 块大小被约束在 151–879 字（mean=589），**块本身就均匀**，热点前提被消除了。
> 这是「**切分策略决定分区均衡性**」的直接证据。
>
> 如果按整回分区，第 67 回 21,728 字 = 均值 7,490 的 2.9 倍，
> max/mean ≈ 2.9 > 2，**就必须解释热点**。这才是教材说法的正确适用场景。
>
> **结论 2：分区数不是越多越好。**
> B（8 区）ratio=1.105，B'（16 区）ratio=1.268 —— 分区翻倍，负载比反而更差。
> 分区越细，越容易被随机波动主导。
>
> **结论 3：最终选方案 A（章节范围）。**
> ① 负载比已达标 ② 保留回次顺序，查某回只扫 1 个 region ③ 语义清晰，好向非技术人员解释。

## 3.10 演示收尾：一句话总结

> 这个项目做了三件在 RAG Demo 里通常看不到的事：
>
> **一、向量真的存在 Hadoop 里。**
> 不是 Milvus，不是 Pinecone，是 HBase 的 `v:emb` 列，float32 原始字节，11,780 条共 8.3 MB。
> 而且 HDFS 上有快照，删了能重建。
>
> **二、答案真的能溯源。**
> 每条回答带 `[n]` 编号，点一下跳到原文具体段落并高亮。
> 不是「参考了《红楼梦》」这种糊弄话。
>
> **三、评测真的找出了缺陷。**
> 四轮修复：元数据问题答「未找到」→ 因果型检索不到 → 脂批没进索引 → 加索引后拒答率掉了。
> 每一轮都是评测发现的，不是拍脑袋想的。
>
> 最后我想说：**我们没有报「准确率 XX%」这个数字。**
> 因为事实型能自动判、推理型没客观标准，混在一起报一个数就是自欺欺人。
> 我们分三类报告，把每条原文都留在结果文件里供人复核 ——
> 这比一个好看的分数更有价值。

## A.4 讲师备忘：可能被问到的问题

| 问题 | 回答要点 |
|:---|:---|
| **为什么不用 Milvus？** | 课程硬性要求「RAG 文本和向量存储在 Hadoop 框架下」。而且 11,780 条规模用 HBase + numpy 暴力检索，延迟 22 ms，完全够用 |
| **为什么用 HBase 不用 Hive 存向量？** | Hive 是批处理，点查延迟秒级；HBase 是 KV，点查毫秒级。向量检索是高频点查场景 |
| **8.3 MB 向量为什么不直接放内存文件？** | 因为要求「存在 Hadoop 框架下」。内存矩阵只是**运行时缓存**，事实源仍在 HDFS/HBase |
| **分区负载比 1.229 算好吗？** | 教材阈值是 2，1.229 远低于阈值。而且我们解释了为什么能这么低：切分粒度均匀消除了热点前提 |
| **为什么不用 Spark？** | 集群里有 Spark 3.5.8，但 MapReduce 对教学更直观（能明确看到 map/shuffle/reduce 三阶段），且 4 个作业数据量小，MR 够用 |
| **评测准确率多少？** | **不报单一准确率**。事实型答案命中 100%、引用回次命中 91.3%、拒答 100%、推理型机器预评 3.6/5，三类分开。而且推理型缺人工评分，这是局限 |
| **脂批 8,510 条怎么来的？** | `pizhu_redecoded.jsonl`，从 PDF 码点重解码。旧解码程序猜的 version 字段已全部停用，改用 `versions_legend`（9 个版本标注） |
| **为什么行高 2.15？** | 正文 60 万字的长段落阅读，2.15 行高实测比常规 1.6 舒适得多。这是「界面为阅读服务」而不是「为好看服务」 |
| **如果语料扩到 1000 万字怎么办？** | ① 切分和向量化都可并行（MR / Spark）② 向量检索需上 ANN（Faiss HNSW）③ HBase region 数要按 RegionServer 数重新设计 ④ 但要注意：上 ANN 就偏离「纯 Hadoop 生态」了，需要权衡 |
| **项目的最大不足是什么？** | ① 推理型没有人工评分 ② 小文件问题（块利用率 1.56%）③ 向量暴力检索不可扩展 ④ 单机 ZooKeeper 不是高可用。这些都在文档里明确写了 |
