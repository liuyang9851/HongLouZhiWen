## 二、消除剩余截断：规则错了，不是数据缺

### 2.1 诊断

对 109 条截断逐条回 PDF，看「批语最后那个 span 之后紧跟什么」：

| 数量 | 打断原因 |
|---:|---|
| **61** | 下一个是同号楷体（19.1 KaiTi）— **是我的规则误判** |
| 25 | 下一个是正文 22.9（其实已正常结束） |
| 11 | 页内找不到（跨页，诊断命中错页） |
| 9 | 小字号 1.9/11.5/15.2（页脚/校注圈号/异文小注） |
| 3 | 下一个是 ◆ 标记（确实结束） |

### 2.2 根因

v4 的规则是「**正文一出现就结束批语**」。但实际排版是行内夹批：

```
第1行：[正文A][◆][批语第1段]        ← 行尾是批语 → 应续行
第2行：[批语第2段][正文B]            ← 行尾是正文 → 批语结束
```

v4 在第 1 行遇到「正文A」就 close，把一条批语劈成两条：

```
'看他所写开卷之第'  +  '一个女子便用此二语以订终身…'
```

### 2.3 修法（v5/v6）

改成**按行判定**：只看该行 `size>=10` 的 span，取按 x 排序的最后一个——

| 行尾是什么 | 处理 |
|:---|:---|
| 批语（19.x KaiTi） | **不结束**，续到下一行 |
| 正文（22.9） | 在本行结束 |

其它修正：
- 15.0–16.5 号楷体 = 行内异文小注（如「(以)」），收进批语
- 22.9 号楷体正在收 big 批语时继续收（回前/回末批正文与它同字号）

| 版本 | 条数 | 截断 | 总字数 | 覆盖回次 |
|:---|---:|---:|---:|---:|
| 原始（旧脚本） | 3,234 | 1,161（35.9%） | 58,795 | 79 |
| v4（S28） | 4,679 | 109（2.3%） | 97,894 | 79 |
| **v6（本次）** | **4,563** | **4（0.09%）** | **98,192** | **80** |

剩余 4 条都是被校注圈号打断或含特殊标记，属个案。

## 三、重建 RAG 索引（核心）

### 3.1 影响范围（先量清楚再动手）

实测 HBase rowkey 分布：

| rowkey 前缀 | chunks | vectors | terms | 本次 |
|:---|---:|---:|---:|:---|
| zhipi\|pizhu（脂批大全） | 5,069 | 5,069 | 40,695 | 不动 |
| **fuqinju\|pizhu** | **3,219** | **3,219** | **35,497** | **重建** |
| guiyouben\|pizhu | 222 | 222 | 5,685 | 不动 |
| chenggao\|text | 1,689 | 1,689 | 165,043 | 不动 |
| fuqinju\|text | 1,051 | 1,051 | 133,983 | 不动 |
| guiyouben\|text | 530 | 530 | 67,938 | 不动 |

**关键红利**：脂批倒排是**独立行** `<ver>|pizhu|<bigram>`，
与正文 `<ver>|text|<bigram>` 分开存 → 重建完全不碰正文索引。

### 3.2 执行（41.4 秒）

```
删除   chunks 3,219 + vectors 3,219 + terms 35,497 = 41,935 行   1.3s
向量化 4,563 条（bge-small-zh，512 维，batch 32）              29.1s
写入   hlm_chunks 4,563 / hlm_vectors 4,563 / hlm_terms 39,116  6.3s
校验   行数全部对上                                              —
```

新 chunk_id 方案（升版 `STRATEGY_REV = "v2-pizhu"`）：

```
chunk_id = sha1("pizhu|回次|序号|文本哈希前8|v2-pizhu")[:16]
```

`app.py` 启动时会把 11,780×512 的向量矩阵读进内存。

### 4.3 追踪脚本改成实时读取

原来的问题：`s25_capture_trace.py` 和 `s26_capture_build_trace.py`
把表行数**写死在代码里**（11780 / 448841），索引一变数据就失真。

改成启动时实时扫表：

```python
def live_counts():
    c = A.hbase()
    return {t: sum(1 for _ in c.table(t).scan(batch_size=2000))
            for t in ("hlm_chunks","hlm_vectors","hlm_terms","hlm_wordfreq","hlm_stats")}
```

还修了一个**逻辑错误**：建库追踪原先写死「成为 [4] 号引用」，
但索引重建后同一个 chunk 实际变成 [3]。改成从在线追踪里反查：

```python
def _citation_index(cid):
    d = json.load(open("/tmp/trace.json"))
    for st in d["stages"]:
        if st["id"] == 6:
            for i, c in enumerate(st["detail"]["contexts"], 1):
                if c["chunk_id"] == cid:
                    return i
```

## 七、教训

1. **「正文出现就结束」在多栏/夹批排版里是错的** —— 判据要看**行尾**，不是行中。
2. **改数据不改索引 = 没改**。展示层和检索层是两条链路，必须同时更新；
   而且向量矩阵在内存里，**不重启就等于没重建**。
3. **写死的数字是定时炸弹**。表行数这类易变指标应从 HBase 实时读，
   而不是抄进脚本。
4. **硬编码的业务语义更危险**：`became_citation = 4` 这种，
   数据一变就错，而且错得"看起来很真"——这次改成反查。
