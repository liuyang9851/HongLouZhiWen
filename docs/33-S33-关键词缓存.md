# S33 · 关键词缓存（LRU + TTL + 落盘）

> 日期：2026-10-27
> 起因：S32 引入「LLM 生成检索关键词」后，每次问答多了一次 LLM 调用（0.8~1.2s）
> 用户确认「好的」（加缓存）

---

## 一、为什么需要缓存

S32 的新流程每问一次就要调一次 LLM 生成关键词。但大量场景是**重复问题**：

| 场景 | 说明 |
|:---|:---|
| 用户刷新重问 | 同一问题反复提交 |
| 演示反复走示例 | 8 个 starter 问题反复点击 |
| 多轮对话同一实体 | 「宝玉…」之后又问「宝玉…」 |
| 标点/空格差异 | 「宝玉为什么挨打？」「宝玉为什么挨打」「宝玉 为什么 挨打」 |

**实测收益**：命中缓存时检索耗时 **1,922 ms → 465 ms（快 76%）**。

---

## 二、设计

### 2.1 三层机制

```
① 内存 LRU        快，但有上限（默认 500）
     ↓
② TTL 过期        默认 7 天（问题语义不会变，长的 TTL 合理）
     ↓
③ 落盘 JSON       重启不丢
```

### 2.2 缓存 key 的规范化（关键设计）

```python
def _norm_q(q: str) -> str:
    """
    问题规范化（作为缓存 key）。

    注意：**不能过度归一**。
      · 去空白、去标点 → 安全
      · 去「为什么/是什么」→ 危险（「宝玉为什么挨打」vs「宝玉怎么挨打」可能答案不同）
    所以只做最小归一。
    """
    q = (q or "").strip()
    q = re.sub(r"[\s\u3000]+", "", q)              # 去空白
    q = re.sub(r"[？?！!。，,、；;：:]+$", "", q)     # 去尾部标点
    return q
```

**为什么只做最小归一**：

| 归一策略 | 风险 | 采用 |
|:---|:---|:---:|
| 去空白 | 无 | ✅ |
| 去尾部标点 | 无 | ✅ |
| 去疑问词（为什么/是什么） | **危险** —— 问题类型可能改变 | ❌ |
| 语义归一（同义词替换） | **危险** —— 需要另一次 LLM 调用 | ❌ |

**实测容错效果**：

| 输入 | 命中同一缓存 |
|:---|:---:|
| 宝玉为什么挨打？ | ✅ |
| 宝玉为什么挨打 | ✅ |
| 宝玉 为什么 挨打？ | ✅ |
| 宝玉为什么挨打。 | ✅ |

4 种写法共用 **1 条**缓存（`entries=1, hits=5`）。

### 2.3 LRU 淘汰

```python
if len(_kw_cache) > KEYWORD_CACHE_MAX:
    # 按 ts 最旧的删
    ordered = sorted(_kw_cache.items(), key=lambda x: x[1].get("ts", 0))
    for kk, _ in ordered[:len(_kw_cache) - KEYWORD_CACHE_MAX]:
        _kw_cache.pop(kk, None)
```

上限默认 500 条（可用 `HLM_KW_CACHE_MAX` 覆盖）。

### 2.4 落盘策略（踩坑）

第一版：

```python
def _kw_cache_save(force=False):
    _kw_cache_dirty += 1
    if not force and _kw_cache_dirty < 20:
        return          # 累积 20 次才写
    ...
```

**问题**：只有 1 条缓存时，`_kw_cache_dirty=1 < 20` → **永远不写盘**。
验证时发现 `keyword_cache.json` 根本没生成。

修正：

```python
def _kw_cache_save(force=False):
    """
    策略：
      · 缓存条目 ≤ 50 → 每次都写（文件小，开销可忽略，保证不丢）
      · 条目 > 50    → 每 20 次新写入刷一次（减少 IO）
    """
    global _kw_cache_dirty
    _kw_cache_dirty += 1
    if not force and len(_kw_cache) > 50 and _kw_cache_dirty < 20:
        return
    ...
```

**再加一层保险**：进程关闭时强制刷盘

```python
@app.on_event("shutdown")
async def _on_shutdown():
    """进程关闭前强制刷盘关键词缓存（避免丢未落盘的条目）"""
    try:
        _kw_cache_save(force=True)
        log(f"关键词缓存已刷盘: {len(_kw_cache)} 条")
    except Exception as e:
        log(f"关闭时刷盘失败: {e}")
```

### 2.5 原子写入

```python
tmp = _KEYWORD_CACHE_PATH + ".tmp"
with open(tmp, "w", encoding="utf-8") as f:
    json.dump(_kw_cache, f, ensure_ascii=False)
os.replace(tmp, _KEYWORD_CACHE_PATH)      # 原子替换
```

**为什么**：直接写目标文件时，写到一半进程被杀会得到损坏的 JSON，
下次启动 `json.load` 失败 → 整个缓存丢失。

### 2.6 只缓存非空结果

```python
if kws:
    _kw_cache_put(question, kws)
return kws
```

**为什么**：LLM 调用失败/超时会返回空列表。
如果把这个空列表缓存下来，之后同样的调用会一直返回空 —— 等于**永久性故障**。
不缓存空结果，下次还会重试。

## 五、验证

### 5.1 缓存加速

| 次 | 耗时 | 缓存状态 |
|:---|---:|:---|
| 第 1 次（miss） | 1,922 ms | entries=1, hits=0, misses=1 |
| 第 2 次（hit） | **465 ms** | entries=1, hits=1 |

**加速 76%**，检索结果完全一致（第33回/第34回/第17回）。

### 5.2 标点容错

4 种写法 → `entries=1, hits=5`（共用一条缓存）。

### 5.3 持久化

```
写入后：keyword_cache.json  120 B
{"宝玉为什么挨打": {"kws": ["板子","打死","贾政","金钏","琪官","忠顺王府"], "ts": 1793070570}}
```

**重启后端后**：

```
重启后缓存: entries=1
首次提问耗时: 528 ms  ← 命中缓存，未调 LLM
```

### 5.4 批量测试

10 个问题（含 2 个重复）：

```
entries: 8 / 500
hits=4  misses=7  命中率=36.4%
已落盘: True
```

命中率 36.4% 是因为测试里故意混了重复问题；
真实使用中，重复率越高收益越大。

## 九、遗留

| # | 项 | 说明 |
|:--:|:---|:---|
| 1 | 无预热机制 | 首次提问仍要等 LLM（可预跑示例问题） |
| 2 | 缓存不含 model_id | 换模型后仍用旧关键词（可接受，关键词与模型关系不大） |
| 3 | 相似问题不复用 | 「宝玉为什么挨打」与「宝玉挨打的原因」是两条缓存 |
| 4 | 无 LRU 访问时间更新 | 命中时不更新 ts，长期可能淘汰热点条目 |

### 关于遗留 #3、#4

**#3**：要复用需要用 embedding 算语义相似度（又是一次计算），
权衡后认为不值得 —— 重复率高的场景（演示/刷新）已经命中。

**#4**：命中时不更新 ts，意味着 LRU 实际是「按首次写入时间淘汰」。
对 500 条的上限来说影响很小（演示场景根本到不了上限）。
