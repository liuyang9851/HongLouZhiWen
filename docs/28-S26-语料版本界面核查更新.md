## 一、核查结论：**大面积过时**

语料版本界面的数字是**写死在 HTML 里的**，经与实测数据逐项比对，**8 项中 7 项错误**。

### 1.1 三版本正文规模

| 项 | 界面显示（旧） | 实测（当前） | 差异 |
|:---|---:|---:|:---|
| 抚琴居 条数 | 83 | **81** | -2 |
| 抚琴居 汉字数 | 526,673 | **506,739** | -19,934 |
| 程高本 汉字数 | 730,730 | **728,570** | -2,160 |
| 癸酉本 条数 | 29 | **28** | -1 |
| 癸酉本 汉字数 | 189,383 | **183,573** | -5,810 |
| 合计 条数 | 232 | **229** | -3 |
| 合计 汉字数 | 1,446,786 | **1,418,882** | -27,904 |

**为什么差这么多**：
- 旧数字来自 `stats_summary.json` 的 **S1 阶段快照**，之后 S7 重新从 PDF 提取回目、S8 修了 80 回回目、S12–S15 修了 9,193 条脂批
- **第67回重复问题**（S21 发现）：`067_合并.txt` + `067a.txt` + `067b.txt` 被当成 3 个独立回次，已去重
- 抚琴居的「83 条」包含了重复的第67回（83 → 81）

### 1.3 矩阵标题误导

| | 旧 | 新 |
|:---|:---|:---|
| 标题 | 版本 × 回次覆盖矩阵 | **脂批版本** × 回次覆盖矩阵 |
| 说明 | 颜色越深 = 该版本在该批语越多 | 颜色越深 = 该**脂批版本**在该回段批语越多 |

**问题**：这个矩阵的纵轴是**脂批来源版本**（甲戌本/庚辰本/蒙府本/戚序本/杨藏本/列藏本/己卯本/甲辰本），
但它紧贴在「三版本正文规模」表下方，读者很容易误以为是抚琴居/程高/癸酉三版本的覆盖矩阵。

**修法**：标题加「脂批」二字 + 补一段说明「与上方是两个不同维度」。

### 1.4 统计界面的字数口径问答

另一处写死（统计信息页「前80回一共多少字」）：

```
口径二：含标点原文 591,499 字（fuqinju/meta.json）  ← 旧
口径三：仅汉字 526,673 字（不含标点）                ← 旧
```

实测：段落合计 600,130 字 / 汉字 506,739 字。

```javascript
// 旧代码 —— 完全没有数据来源，纯手写
```

## 三、修复方案：改为读实测文件

### 3.1 新增生成脚本

`scripts/s26_1_build_corpus_stats.py` —— 从语料源实测，生成 `web/data/corpus_stats.json`：

```json
{
  "versions": [
    {"id":"fuqinju","label":"抚琴居校本","records":81,"chars":600130,
     "han":506739,"range":"0-80","note":"含凡例","use":"RAG 主链"},
    {"id":"chenggao","label":"程高本","records":120,"chars":861457,
     "han":728570,"range":"1-120","use":"版本对照"},
    {"id":"guiyouben","label":"癸酉本","records":28,"chars":215958,
     "han":183573,"range":"81-108","note":"第81–108回","use":"版本对照"}
  ],
  "totals": {"records":229,"chars":1677545,"han":1418882},
  "quality": [
    {"id":"Q1","desc":"回目格式一致性","value":"全部通过","level":"ok"},
    {"id":"Q2","desc":"段落非空性","value":"0 空段（另有 17 个 ≤2 字的诗歌小标题，属正常）","level":"ok"},
    {"id":"Q3","desc":"替换符 U+FFFD 检测","value":"0 处（S12–S15 已全部修复）","level":"ok"},
    ...
  ],
  "generated_at": "2026-10-24 23:15"
}
```

### 3.2 前端改为动态渲染

```javascript
// 新代码 —— 读实测文件
let csd = null;
try {
  const r = await fetch('/data/corpus_stats.json?v=' + Date.now());
  if (r.ok) csd = await r.json();
} catch (e) { ... }
if (!csd) csd = { versions: [], totals: {...}, quality: [], generated_at: '（未生成）' };
```

表格和规则都从 `csd` 渲染，并在底部标注「实测于 {generated_at}」。

### 3.3 三处修正的判据（不只是换数字）

**Q2 段落非空性** —— 原始判据把 17 个「≤2 字的段」当异常：

```
fuqinju 第64回 段17: '西施'
fuqinju 第64回 段20: '虞姬'
fuqinju 第34回 段19: '其二'
```

这些是**诗歌小标题**（《五美吟》的篇名、「其一/其二」序号），本来就该独立成段。
**改判据**：只有**空段**才算异常，短段作为「正常现象」注明。

**Q8 版本归属** —— 原始显示「1 条未识别」，实测 499 条：

```
抚琴居  238/3234 条为修复/清理新增，未回填版本
癸酉本  223/223 条仅标 source（该源无版本归属概念）
脂批大全  38/9000 条为修复/清理新增，未回填版本
```

**改口径**：分源如实说明，而不是给一个笼统数字。
其中「癸酉本全缺 version」不是缺陷 —— 该数据源本身就只有 `source` 概念。

## 六、如何避免再次过时

1. **数据改动后重跑生成脚本**
   ```bash
   python scripts/s26_1_build_corpus_stats.py
   ```
2. **界面显示「实测于 YYYY-MM-DD HH:MM」** —— 用户一眼能看出数据新鲜度
3. **不要再在 JS 里写死数字**

> 建议：把 `s26_1_build_corpus_stats.py` 加入 `pipeline/run_all.sh` 末尾，
> 每次数据管道跑完自动更新界面数字。

## 七、教训

| # | 教训 |
|:---|:---|
| 1 | **硬编码的展示数字必然会过时**。数据管道跑了 4 轮（S7/S12/S13/S15），界面一次都没跟上。 |
| 2 | **「修复完成」不等于「展示正确」**。S12–S15 把 U+FFFD 清零了，但界面还写着「检出 68 处」—— 白白让用户以为有问题。 |
| 3 | **相邻的两个表可能讲不同的事**。三版本正文表 + 脂批版本矩阵放在一起，纵轴含义完全不同，必须显式说明。 |
| 4 | **判据也会出错**。「≤2 字的段」不是坏数据，是诗歌小标题。修数据前先确认判据对不对。 |
| 5 | **实测 > 记忆**。我一开始也以为界面数字「大概对」，逐项比对才发现 8 项错 7 项。 |
