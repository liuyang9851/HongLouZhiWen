# S25 · 项目原理页（一次问答的全链路追踪）

> 日期：2026-10-25
> 需求：「在左边栏加一个项目原理页，具体以一个例子为例展示数据在用户端、Hadoop 各组件的各部分、大模型部分的变化流转过程」

---

## 一、设计思路

### 1.1 核心决定：用真实追踪，不用示意图

**大多数"架构讲解页"是画出来的示意图**，数字是编的。
本页反其道而行：

1. 写一个采集脚本，在 `hlm-api` 容器内**真跑一遍**问答
2. 逐阶段抓取输入/输出/耗时/中间数据结构
3. 落盘成 `web/data/trace.json`
4. 页面读取该 JSON 渲染

**所以页面上每个数字、每个 chunk_id、每个向量分量，都是真实值。**

### 1.2 举的例子

选 `宝玉和黛玉是什么关系？` 这个问题的理由：

| 要求 | 该问题是否满足 |
|:---|:---|
| 必须触发 L1 关键词召回 | ✅ 有实体词、关系词 |
| 必须触发 L2 向量召回 | ✅ 语义问题 |
| **必须触发 L3 图谱召回** | ✅ 出现 2 个人物，且是「关系」类问题 |
| 必须体现别名展开 | ✅ 用简称「宝玉/黛玉」而非「贾宝玉/林黛玉」 |
| 能体现多版本语料 | ✅ 检索结果横跨抚琴居/程高本/脂批 |

## 二、页面结构（6 个章节）

### Hero
- 例子问题 + 5 个 KPI（8 阶段 / 4.35s / 3 路检索 / 5 条上下文 / 448,841 倒排行）

### 1. 先分清：离线建库 vs 在线问答

这是理解系统的**关键前提**，用左右两栏对照：

| 离线（Hadoop，部署时跑一次 ~30 分钟） | 在线（每次提问，本例 4.35 秒） |
|:---|:---|
| 原始语料 → HDFS | 用户提问 → FastAPI |
| MapReduce 切 bigram 建倒排 | 查询改写 0.03 ms |
| ONNX 编码 11,780 条向量 | 三路召回 1.31 s |
| 写入 HBase 5 张表 | RRF 融合 0.2 ms |
| | 大模型生成 3.04 s |

**核心结论**：Hadoop 负责「把书变成可检索的索引」（慢，做一次）；
在线只做点查，所以检索只要 1.3 秒，剩下 70% 都花在大模型上。

### 2. 八个阶段的时间线

每阶段一张卡片，含：
- 编号 + 阶段名 + **组件徽章** + 耗时
- `输入 → 输出`（左右对照）
- **实际数据**（按阶段定制渲染）
- 为什么这样做的说明
- 「查看原始数据」按钮（展开完整 JSON）

八阶段与定制可视化：

| # | 阶段 | 组件 | 可视化方式 |
|:--:|:---|:---|:---|
| 1 | 查询理解与改写 | FastAPI（纯 Python） | 3 种查法 chip 列表 |
| 2 | L1 关键词召回 | HBase `hlm_terms` | bigram 标签 + **HBase 行 rowkey/postings** + 候选打分 |
| 3 | L2 向量召回 | ONNX + HBase `hlm_vectors` | **向量算式卡片**：问题向量前 8 维 × 矩阵 11780×512 = 相似度 |
| 4 | L3 图谱召回 | HBase `hlm_stats` | 识别出的人物 chip + **共现行 `cooccur\|林黛玉\|贾宝玉` cnt=237** |
| 5 | RRF 融合 | FastAPI | **三路名次表**（L1/L2/L3 名次 + RRF 分） |
| 6 | 回表取正文 | HBase `hlm_chunks` | 5 条上下文卡片（版本/回次/段号/字数/正文摘要） |
| 7 | Prompt 拼装 | → LLM API | 真实 system prompt + user prompt（含真实原文） |
| 8 | LLM 生成 | DeepSeek API | 带 `[n]` 引用高亮的回答 + **token 用量** |

### 3. Hadoop 各组件职责表

| 组件 | 阶段 | 实际动作 | 数据量 | 耗时 |
|:---|:---|:---|:---|---:|
| HDFS | 离线 | 存原始语料与 MR 中间产物 | 88.7 MB | — |
| MapReduce | 离线 | 建倒排 448,841 行 + 词频 133,673 行 + 共现 588 行 | — | — |
| HBase `hlm_terms` | 在线·L1 | 按 bigram 点查 postings | 读 ~16 行 | 143 ms |
| HBase `hlm_vectors` | 在线·L2 | 加载 11780×512 矩阵做矩阵乘 | 23.0 MB | 656 ms |
| HBase `hlm_stats` | 在线·L3 | 读一行共现记录 | 1 行 | 511 ms |
| HBase `hlm_chunks` | 在线·回表 | 按 5 个 id 取正文 | 5 行 | 0.0 ms |
| 大模型 | 在线·生成 | 读上下文组织回答 | 3,311 字符 → 474 字符 | 3.04 s |

**关键提示**：整个在线问答中，**MapReduce 一次都没跑**。

### 4. 时间花在哪

横向条形图（真实 measured）：

```
L1 关键词（HBase 点查）   143.3 ms   3.3%
L2 向量（ONNX + 矩阵乘）   655.6 ms  15.1%
L3 图谱（扫全部正文）      511.3 ms  11.8%
大模型生成               3,039.3 ms  69.9%
其他（改写/融合/拼装）        0.4 ms   0.0%
```

**两个诚实说明的优化点**：
1. 大模型占 70% 是 API 延迟，换更快模型即可改善
2. **L3 的 511 ms 其实是浪费的** —— 为找「同时提到两人的 chunk」遍历了全部 11,780 条正文（O(N) 全扫描）。离线补一张「人物 → chunk_id」正排表可降到毫秒级

### 5. 一条数据的完整变形链

7 步卡片，展示形态变化：

```
用户输入「宝玉和黛玉是什么关系？」（11 个汉字）
  → 3 个查询串（简称展开 + 关系词扩展）
  → 9 个 bigram（宝玉·玉和·和黛·黛玉·玉是·是什…）
  → 512 维 float32 向量
  → 5 个 chunk_id（90 个候选按名次倒数融合）
  → 5 段原文 / 共 1,728 字（每段带版本·回次·段号）
  → 474 字符带引用回答
```

### 6. 为什么必须用 Hadoop 生态

四条理由：数据量不适合塞内存 / 建索引是典型批处理 / 在线需低延迟点查 / 三种负载天然分层。

### 3.2 遇到的问题（4 个）

| # | 问题 | 修法 |
|:--|:---|:---|
| 1 | `search_vector` 返回值误当 tuple 解包 | 改为直接接收 list |
| 2 | `CFG` 里没有 `default_model` | 改用 `all_providers()` 找默认项 |
| 3 | `call_llm` 返回 dict 不是 str | 取 `.get("content")`，同时采集 reasoning + usage |
| 4 | **trace 脚本自己用了旧的人物检测逻辑** | 与 `search_graph` 修复后一致，改为别名匹配 |

第 4 个最有意思：我修了 `search_graph` 的 bug，却**忘了同步修改采集脚本里复制的同一段逻辑**，
导致页面上 L3 显示"该行不存在"，而实际 `search_graph` 已返回 10 条。这是典型的"修一处漏一处"。

## 四、顺手修复的两个真实 bug

做这个页面时，为了让 L3 图谱通道有真实数据可展示，追查了它为什么一直返回 0，
发现 `search_graph` 有**两个叠加的 bug**：

### Bug 1：人物检测用正式名，检测不到简称

```python
# 修复前
persons = [c for c in ALIAS if c in query]      # c 是「贾宝玉」
```

用户问「**宝玉**和**黛玉**是什么关系？」，而 `ALIAS` 的键是「贾宝玉」「林黛玉」——
`"贾宝玉" in "宝玉和黛玉是什么关系？"` 为 `False`，**永远检测不到人物**。

```python
# 修复后
persons = [c for c, aliases in ALIAS.items()
           if any(a in query for a in aliases)]   # 任一别名命中即算
```

### Bug 2：正文匹配用正式名，匹配不到 chunk

```python
# 修复前
if a in c["text"] and b in c["text"]:            # a = "林黛玉"
```

正文绝大多数地方写的是简称「黛玉」，「林黛玉」很少连续出现，
所以即使共现行存在（`cooccur|林黛玉|贾宝玉` cnt=**237**），也匹配不到任何 chunk。

```python
# 修复后
aliases_a = ALIAS.get(a, [a]); aliases_b = ALIAS.get(b, [b])
if any(x in text for x in aliases_a) and any(x in text for x in aliases_b):
```

### 影响

| 指标 | 修复前 | 修复后 |
|:---|---:|---:|
| 「宝玉和黛玉是什么关系？」L3 召回 | **0** | **10** |
| 「宝玉和宝钗是什么关系？」L3 召回 | **0** | **10** |

**图谱通道此前对所有简称提问都是形同虚设的。** 这个 bug 一直存在，但因为 L1+L2 总能兜底，
答案看起来"还行"，所以没被发现——是"双通道掩盖单通道失效"的典型例子。

> 这也是做原理页的意外收获：**为了把一件事讲清楚，反而把它的 bug 找出来了。**

路由：`VIEWS` 增加 `principle`，`#/principle` → `renderPrinciple(stage)`

### 5.3 复用既有模式

沿用了 S23 建立的约定：
- 模块从 `window.__HLM__` **延迟获取** `esc`（避免 ES module 求值顺序问题）
- 长页面需要 `height:auto + overflow:visible` + `.stage:has()` 开滚动
- 数据走 `/data/*.json`（server.js 已有该路由）

### 5.4 折叠交互

每个阶段卡片有「查看原始数据」按钮，展开完整 JSON（`hidden` 切换）。
因为 JSON 可能很长，用 `max-height: 240px; overflow-y: auto` 限制内部滚动。

> 副作用：鼠标悬停在 prompt 代码块上时，滚轮滚的是代码块而非页面。
> 这是有意的（让用户能读完整 prompt），但调试时一度困惑。

## 八、环境变更说明

本次会话发现 **Windows 端口 3000 落入系统排除范围（2980–3079）**，
`node server.js` 启动报 `EACCES`。

检查命令：
```powershell
netsh int ipv4 show excludedportrange protocol=tcp
```

**前端改用 4000 端口**（`server.js` 支持 `HLM_WEB_PORT` 环境变量，无需改代码）：

```powershell
Start-Process node -ArgumentList 'server.js' -WorkingDirectory <web> `
  -Environment @{HLM_WEB_PORT='4000'} -WindowStyle Hidden
```

新地址：http://127.0.0.1:4000
