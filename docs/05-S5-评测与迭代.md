## 一、为什么不用现成的 golden_eval_60

红学数据源里有 `golden_eval_60.json`（60 条，20 事实 + 20 综合 + 20 推理），看起来很合适。**实测检查后放弃**：

```json
{
  "id": "golden_q_auto_011",
  "query": "根據蔡義江評注《紅樓夢》第8回『通靈寶玉與金鎖對句』原文…",
  "relevant_doc_ids": ["cai_note_0019"],
  "relevant_chunk_ids": ["cai_note_0019_chunk_0"]
}
```

它的 `relevant_chunk_ids` 指向 `cai_note_*`、`qaSynthesisArticle_*`、`transfernotesArticle_*`
—— **都是外部文档（蔡义江评注、红学文章），不是本项目的 hlm_chunks 语料**。

后果：拿它算 Recall@k 永远对不上（我们的 chunk_id 是 `bde3ef…` 这种 16 位 hex）。

**所以事实型评测集自建**，全部从 `hlm_corpus/clean/chapters.jsonl` 抽取，
并且**每条的 evidence 位置都用 anchor 校验过**（见 §2.1）。

## 二、评测集设计

### 2.1 事实型（27 条）—— 可自动评

每条包含：

| 字段 | 用途 |
|:---|:---|
| `question` | 问题 |
| `answer` | 标准答案（短答） |
| `answer_keywords` | 答案里应出现的词（评「答对没」） |
| `evidence{hui, para_index}` | 证据位置（评「引用命中没」） |
| `evidence_anchor` | **证据段落里必须出现的原文片段**（校验 evidence 位置对不对） |

**「答案关键词」和「证据锚点」必须分开** —— 这是第一版栽的坑：

```
判词类问题：「可叹停机德，堪怜咏絮才」写的是谁？
  证据段落 = 「可叹停机德，堪怜咏絮才」
  答案     = 「薛宝钗与林黛玉」
  ↑ 判词里根本没有这两个名字（要靠解读）

第一版用 answer_keywords 去匹配证据段落 → 17/27 误报「证据位置错」
改成 anchor 后 → 23/23 通过（+4 条统计型无段落证据）
```

**统计型 4 条**（f027-f030）的 golden 来自 MapReduce/HBase，不是正文，单独统计。

### 2.2 推理型（15 条）—— 只能人工评

覆盖：进府原因、谐音隐喻、人物关系、管家权力、衰败征兆、判词作用、好了歌、脂批价值等。

**第一版还栽过一个坑**：参考要点里混入了写给评分人看的元指令：

```
❌ "姑表兄妹（…）。注意：若语料未明写，应说明。"
                          ↑ 这句被自动评分当成"答案要点"
```

系统答对了「姑表兄妹」，但因为没写「注意」二字被判低分。
**改成四元组** `(id, question, 参考要点, 评分提示)`，把元指令拆到 `scoring_hint`。

### 2.3 应拒答（10 条）—— 测 R-111

| 类型 | 例 |
|:---|:---|
| 跨作品 | 《三国演义》里诸葛亮为什么六出祁山？ |
| 纯主观 | 《红楼梦》和《小时代》哪个更伟大？ |
| 伪前提 | 曹雪芹是哪一年写出第81回的？ |
| 荒谬 | 林黛玉的微信号是多少？ |
| **真实提问** | 林黛玉和贾宝玉同床这么久为什么没怀孕？（来自 74 条真实知乎提问） |

## 三、评测驱动的三轮修复（核心价值）

### 第 1 轮：元数据类问题答「未找到」

| 项 | 内容 |
|:---|:---|
| **发现** | f009「第3回的回目是什么？」→ 答「语料中未找到」。f010、f027 同理 |
| **根因** | 回目在 `huimu` 字段、全书字数在统计表里，**都不在正文段落**。检索去正文里找，当然找不到 |
| **修法** | `build_meta_context()`：识别「第N回回目 / 全书多少字 / 共多少回」→ 直接构造 context，不去正文搜 |
| **效果** | `answer_ok` 91.3% → **100%** |

修复后的效果（实测）：

```
Q: 全书正文一共多少字？
A: 全书字数有三个不同口径，需分别说明：
   - 段落字数合计：599,196 字
   - 仅汉字（不含标点）：526,673 字
   - 含标点原文：591,499 字
   所以问"多少字"要先确定口径…
```

> 模型主动指出「三个口径」——这是我们喂给它的 context 里就写明了，
> 不这么做的话，RAG 会随便挑一个数字答，评审一问「你怎么统计的」就露馅。

### 第 2 轮：因果型问题检索不到正确回次

| 项 | 内容 |
|:---|:---|
| **发现** | 「林黛玉为什么进贾府」→ Top-5 全是第 29/30/23/13 回，**第3回一条没有** |
| **根因** | 第3回确实有 14 个 chunk（HBase count 验证过），但问题是「问原因」，正文是「叙述过程」（到了都中、进入神京）→ 字面/语义都有 gap |
| **修法** | 规则化 query rewrite：`为什么→到/入/投/弃舟登岸/到了都中` |
| **效果** | Top-1 从第29回 → **第3回段4**；`cite_hui_hit` 82.6% → **91.3%** |

### 第 3 轮：脂批根本不在索引里

| 项 | 内容 |
|:---|:---|
| **发现** | r015「脂批对理解《红楼梦》有什么价值？」→ 答「语料中未找到」（1 分） |
| **根因** | `hlm_chunks` 只索引了正文（1,035 chunk），**3,234 条脂批从来没进过 RAG 索引** |
| **修法** | `s5_4_add_pizhu.py`：脂批切 chunk + 向量化 + 写同一批 HBase 表（加 `source` 字段） |
| **效果** | 索引 1,035 → **4,269**；推理型均分 3.27 → **3.6/5**；r015 从"未找到"变成"引用脂批原文" |

修复后 r015 的引用（实测）：

```
[2] 第12回 source=pizhu 版本=庚辰本/甲戌本  "与'红楼梦'"
[5] 第18回 source=pizhu 版本=己卯本/戚序本  "妙卿出现。至此细数十二钗…"
```

### 第 4 轮（副作用修复）：脂批入索引后，拒答率掉到 90%

| 项 | 内容 |
|:---|:---|
| **发现** | 加脂批后正确拒答率 100% → 90%，x007「如果穿越到《红楼梦》你会选谁」被长篇回答了 |
| **根因** | 索引变大后能检索到更多片段，模型开始"先说没有、再做推断"——判定脚本视为未拒答 |
| **修法** | 加 `_SUBJECTIVE` / `_CROSSWORK` 正则 → **直接软拒答，不调 LLM**（0.1 ms） |
| **效果** | 拒答率回到 **100%**，且这类问题现在 0.1ms 就答完（省 token） |

> 这一轮值得单独说：**每次都改进了主指标、又引入新问题，再修**。
> 这是真实工程的常态，也是「不合成单一准确率」的意义——
> 如果只看一个总分，这个回退会被平均掉，看不见。

## 四、指标设计说明

### 4.1 为什么同时给「回次命中」和「段落命中」

| 指标 | 值 | 严格度 |
|:---|---:|:---|
| 引用回次命中率 | 91.3% | Top-5 里有正确**回次** |
| 引用段落命中率 | 69.6% | Top-5 精确覆盖到正确**段落** |

差 21.7 个点，原因：chunk 是按场景段切的（平均 589 字），一个论点常跨多个 chunk。
引用到了正确回次但段落区间不完全覆盖 —— 属于**可接受的召回**，
但严格算就掉分。两个指标都给，读者自己判断。

### 4.2 keyword_coverage 的局限

`keyword_coverage` 是宽松判定：关键词出现 ≠ 语义正确。
比如问「袭人原本是谁的丫鬟」，回答里出现「贾母」但说的是别的事，也会命中。

所以报告里同时保留：
- 自动指标（数量化）
- **逐条原文**（供人复核）

### 4.3 推理型评分的三轮演进（诚实记录）

| 版本 | 做法 | 均分 | 问题 |
|:---|:---|---:|:---|
| v1 | 参考要点按标点切碎，逐字匹配 | 1.2 | 中文同义表达全判错（「去世」vs「亡」） |
| v2 | 概念词 + 同义扩展 + 诚实加分 | 2.93 | 参考要点里的元指令仍被当答案 |
| v3 | 元指令剥离（`_META_DESC` 正则） | 3.27 | — |
| v3 + 脂批索引 | 索引扩充后回答质量提升 | **3.6** | — |

**v1 到 v3 的提升主要来自「修评分」，不是「修系统」** —— 这一点必须写明，
否则会误以为系统突然变好了。

## 五、评测的局限（必须说明）

| # | 局限 | 影响 |
|:---|:---|:---|
| 1 | 事实型只有 27 条 | 置信区间宽，不能外推为「系统整体准确率」 |
| 2 | 推理型无人工评分 | 当前只有机器预评，「结论」不完整 |
| 3 | keyword_coverage 宽松 | 关键词出现 ≠ 语义正确 |
| 4 | 只用了一个模型 | 没做 deepseek-flash vs v4-pro vs GLM 横向对比 |
| 5 | 评测集由我构建 | 有自证偏差风险（虽然证据位置全校验过） |
| 6 | 脂批版本未分离评测 | 脂批有 9 个版本标注，未测「按版本检索」 |

## 六、给评审看的一段话

> 本项目的评测**没有**给出「准确率 XX%」这种数字。
>
> 因为事实型可以自动判对错、推理型没有客观标准，
> 混在一起报一个数，正是自己骗自己。
>
> 我们做的是：
> 1. 三类**分开**报告
> 2. 每条的**原文**都留在结果文件里供复核
> 3. 明确写出**局限**和**下一步**
> 4. 更重要：**评测找出了 3 个真实缺陷并逐轮修掉** ——
>    元数据问题答「未找到」、因果型问题检索不到、脂批根本没进索引。
>    这比一个好看的分数有价值得多。
