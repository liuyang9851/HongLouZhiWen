## 1. RAG 链路

### 1.1 全链路步骤（README、04、原理、S32 合并）

| # | 步骤 | 技术 | 关键参数 |
|:--:|:---|:---|:---|
| 1 | 问题进来，判断类型 | 正则分类 `classify_question` | 4 个分支，见 §2 |
| 2 | LLM 生成检索关键词（S32 新增） | `KEYWORD_SYS_PROMPT`，要求"用原文可能出现的词" | 3~8 个关键词、每个 1~4 字；超时 8 s（S32） |
| 3 | 规则改写兜底 | `REWRITE_RULES` + `SCENE_HINTS` 人工枚举表 | 3 个变体（04） |
| 4 | 别名展开 | 简称→全名（宝玉→贾宝玉），另有 `PROTECTED_TERMS` 保护「通灵宝玉」不被拆（08） | 改写后检索式上限 **24 个**（04、S32） |
| 5 | L1 关键词召回 | HBase `hlm_terms`，bigram 倒排，按命中 bigram 数 + tf 加权；S31 加 IDF 加权 `idf = 1+log((N+1)/(df+1))`；S31 把 `huimu` 回目也纳入倒排文本源 | 词项 133,673（早期）/ 448,841 行（07、原理）；`N_CHUNKS=11780` 可由 `HLM_N_CHUNKS` 覆盖（S31） |
| 6 | L2 向量召回 | bge-small-zh-v1.5 本地 ONNX；启动时把向量表全量载入内存 numpy 矩阵，查询做 `M @ qv` | **512 维**；矩阵 11780×512（原理）、23.0 MB；`HLM_EMB_DIM=512`（04） |
| 7 | L3 图谱召回 | 查 `hlm_stats` 的人物共现行（`cooccur|林黛玉|贾宝玉`），再按别名匹配正文 chunk | 共现 10,742 组（04）；示例行 cnt=237（原理） |
| 8 | RRF 融合 | `score = Σ_i 1/(60 + rank_i)`，只用名次不用分数量纲 | **k=60**（`HLM_RRF_K=60`，README/04/07） |
| 9 | 同回去重 | 方案 B：同回正文上限 2、同回脂批上限 1、脂批总数上限 `max(1, topk//2)` | `MAX_TEXT_PER_HUI=2`、`MAX_PZ_PER_HUI=1`、`MAX_PZ_TOTAL=max(1,topk//2)`（S9） |
| 10 | 回表取正文 | HBase `hlm_chunks` 按 chunk_id 取，返回版本/回次/段号/chunk_id | 上下文条数 top-k = **5**（`HLM_TOPK_CONTEXT=5`），召回 top-k = **30**（`HLM_TOPK_RECALL=30`）（04） |
| 11 | Prompt 拼装 | system prompt 5 条规则 + 用户消息按「选中原文 / 语料片段 / 问题」三段 | 片段编号形如 `[1] (第3回 段23-23 · fuqinju · chunk=10f1ef930816dfd9)`（04） |
| 12 | 生成 | DeepSeek 官方 API（默认 `deepseek-flash`）、智谱 GLM；OpenAI 兼容协议；SSE 流式 | thinking 开关 `reasoning_effort=medium`；多轮保留最近 **8 条**（4 轮）、单条截断 **1,500 字**（04） |
| 13 | 引用回跳 | 每条结论后 `[n]` 角标，点击跳原文阅读并 `<mark>` 高亮；优先按 `hit_text` 文本匹配，`para_id` 兜底 | `highlightPara()` 两级匹配（08） |

### 1.2 提示词策略（04 §3.1、27档 §3.2）

- system prompt 5 条：①优先基于【语料片段】回答、片段没有就说"语料中未找到"、绝不编造 ②每条结论后标 `[1][2]` 出处 ③片段间版本差异/矛盾要指出 ④人物、回次、诗词引用必须准确，不确定就说"不确定" ⑤中文、简洁。
- 额外三段：「思考语言」要求中文思考（实测默认英文，reasoning 开头是 `The question asks...`）；「关于《红楼梦》版本」说明语料为抚琴居校本前 80 回，另有程高本 120 回与癸酉本后 28 回作对照；三档策略按档注入不同说明段（`knowledge` 段、`count` 段）。
- 关键词生成 prompt 的三条要求：用原文用词而非问题用词（「挨打」→「笞挞」「板子」「打死」）、补全专名简称、补可能相关的人物/物件/地点；强约束只输出 JSON `{"keywords": [...], "reason": "..."}`（S32）。

### 1.3 降级链（04 §5、S32、S33）

- 三轮降级：主模型失败 → 换备用模型 → 前端退回非流式 `/chat` → 再退回纯检索 `/api/locate` → 明确报错（04）。
- 关键词生成四种降级：超时（>8 s）/调用失败 → 返回空、只用规则改写；输出非 JSON → 正则提取 `{...}` 重试；关键词含非中文或超长 → 单条过滤（S32）。
- 关键词缓存（S33）：内存 LRU（默认 500 条）+ TTL（默认 7 天）+ 落盘 JSON；key 只做最小归一（去空白、去尾部标点），不去疑问词；实测命中缓存时检索 **1,922 ms → 465 ms**。

## 2. 三档知识策略（27档；README 亦称"四类分流"）

文档标题写「三档」，流程图实际是 4 个出口（档1 / 档2 / 档2b / 档3），`classify_question()` 返回 5 个标签。

| 出口 | 标签 | 触发条件 | 回答方式 |
|:---|:---|:---|:---|
| 档1 语料充分 | `corpus` | 检索到 **≥3 条片段** + 非元知识型 + 非统计型 | 基于片段回答 + 引用编号 |
| 档2 元知识型（有片段） | `knowledge_plus_corpus` | ≥3 条片段 + 命中 `META_KNOWLEDGE_PAT` | 通识为主 + 片段佐证 |
| 档2 元知识型（无片段） | `knowledge` | 片段 <3 条 + 命中 `META_KNOWLEDGE_PAT` | **纯模型知识兜底**，开头标注「以下内容基于通识知识，非本次检索到的原文，供参考：」 |
| 档2b 精确统计型 | `count` | 命中 `COUNT_Q_PAT`（优先级高于片段数） | 不猜数字，说明为何不能靠检索，引导点 🔬 自定义查询 |
| 档3 超出范围 | `refuse` | 命中 `OUT_OF_SCOPE_PAT`（优先级最高） | 软拒答，**不调 LLM**，实测 0.1 ms |

判定顺序（`classify_question` 实现）：`OUT_OF_SCOPE_PAT` → `refuse`；`is_count_question` → `count`；`n_contexts>=3` 且 `META_KNOWLEDGE_PAT` → `knowledge_plus_corpus`；`n_contexts>=3` → `corpus`；`META_KNOWLEDGE_PAT` → `knowledge`；否则 `refuse`。

四个正则的覆盖范围（原文列举）：

- `META_KNOWLEDGE_PAT`：版本名（程高本/程甲本/程乙本/脂本/脂评本/庚辰本/甲戌本/己卯本/蒙府本/戚序本/杨藏本/列藏本/舒序本/梦稿本/郑藏本）、对比词（区别/差异/不同/对比/比较/异同）、原因词（为什么/原因/为何/何以）、评价词（意义/价值/地位/影响/评价/看法/解读/理解/赏析/艺术/手法/风格）、主题词（主题/主旨/思想/内涵/寓意/象征/隐喻/伏笔/草蛇灰线）、续书相关（续书/后四十回/高鹗/程伟元）、红学相关（红学/考证/探佚/脂砚斋是谁/曹雪芹/作者/成书/流传）、概述词（总结/概括/概述/梳理/归纳）。
- `COUNT_Q_PAT`：出现了?(几次|多少次|多少个)、一共(有)?(几次|多少)、频次、频率、次数、多少字、多少个字、字符数、字数是多少、排名、前几、最多、最少、统计。
- `OUT_OF_SCOPE_PAT`：三国/水浒/西游/金瓶梅/聊斋/论语/诗经/唐诗/宋词、相对论/量子/编程/python/java/股票/基金/天气、我爱你/你是谁/你叫什么/讲个笑话/写首诗。

- 两条链路都改：`/chat` 与 `/chat/stream` 分别实现（27档 §3.4 强调"容易漏改"）。
- 回归测试 6 例全部符合预期（元知识兜底 2 例、引导查询 1 例、正常引用 1 例、拒答 2 例），截图 `docs/shots/33-knowledge-fallback.png`（27档 §4.3）。
- 附带修复：`SUBJECTIVE_REPLY` 文案被跨作品事实问题复用，改为通用表述（27档 §5.1）。

### 6.4 沙箱自定义查询的五层防护（S21实现 §2.2）

| 层 | 内容 |
|:--:|:---|
| 第 1 层 | **AST 静态检查**（父进程做、不执行）：拒绝 `import`/`from ... import`、`open`/`exec`/`eval`/`compile`/`__import__`、`getattr`/`setattr`/`globals`/`locals`/`vars`/`dir`、`__class__`/`__bases__`/`__subclasses__`/`__globals__`/`__builtins__`、`socket`/`subprocess`/`multiprocessing`/`threading`/`ctypes`、`while True`/`with`/`async`、超长字符串常量（>100 KB）；并要求必须给 `result` 赋值 |
| 第 2 层 | **受限 builtins 白名单**（约 50 个安全函数）：`len`/`sum`/`max`/`min`/`sorted`/`range`/`enumerate`/`zip`/`print`/`int`/`str`/`dict`/`list`…；没有 `open`/`exec`/`eval`/`__import__`/`getattr` |
| 第 3 层 | **数据入口白名单**：只能通过 `load_all_text` / `load_chapter` / `load_chapters` / `load_pizhu` / `load_person_roles` / `load_stats` / `VERSIONS` 读语料，完全无法碰文件系统 |
| 第 4 层 | **subprocess 资源限制**：`prlimit --cpu=5 --as=512M --nproc=8 --fsize=1M --nofile=32` + `timeout`（设计文档写 10 s，实现文档写 12 s）；即 CPU 5 s / 内存 512 MB / 进程 8 / 单文件 1 MB / 文件描述符 32 |
| 第 5 层 | **网络拦截**：builtins 无 `socket`/`urllib`/`http`，并在子进程内 patch `socket.socket` |

- 隔离手段实测结论：`timeout`、`prlimit --cpu/--as/--nproc/--fsize` 可用；`unshare --net`（容器无 CAP_SYS_ADMIN）、`firejail`/`bwrap`、`RestrictedPython` 均不可用 → 只能靠 AST + subprocess 双重防护（S21设计 §2.2）。
- 安全测试 9 个用例：删库、读 /etc/passwd、写文件、网络外传、反射绕过、fork 炸弹均被 AST 拦截；内存炸弹 800 MB 由 `prlimit --as` 触发 MemoryError；CPU 死循环被 `prlimit --cpu` kill；正常代码执行成功（S21实现 §2.3）。
- 失败重试：默认重试 1 次，把错误回给 LLM 让它自己改；**安全检查拒绝的代码不重试**，避免反复尝试绕过（S21实现 §3.4）。
- 实测查询结果：全文「之」字 1,877 次 / 624,373 字（0.3%）；最长回第 67 回 21,705 字、最短「凡例」957 字；「宝玉」最多第 19 回 116 次（次名第 28 回 98 次）；程高 864,355 vs 抚琴居 624,373，差 239,982（S21实现 §1.2，全部一次成功无重试）。

### 6.5 部署与运维

- 三条部署路线（README、RN）：`./start.sh`（用你的 Hadoop）/ `--with-hdfs`（内置单节点 HDFS，Docker）/ `--local-only`（纯本地文件）；三条路线检索结果「完全相同（实测 9/10 命中一致）」。
- 版本兼容性立场：HDFS 低风险（文件格式 + WebHDFS REST，2.x/3.x 通用）；**HBase 3.x 已移除 Thrift1，本项目不可用**，故主推 HDFS 作为数据源（README、RN）。
- 数据源自动恢复（N101，v1.0.1 修 5 个 bug）：entrypoint 二次启动死锁、HDFS 未就绪时首次加载空 dict 被缓存（chunk 永久 -1）、`HLM_DATA_SOURCE=hdfs` 强制模式不探测可用性、`resolve_source()` 把 `none` 写进缓存、`load_all()` 失败未清理 `_chunks`/`_index`；验证方式「停 HDFS → chunk=0 → 起 HDFS → 10~30 秒自动恢复 chunk=11780」。
- 一键恢复脚本 `scripts/s27_restore_after_reboot.py`；数字一致性校验 `scripts/s32_verify_diagram_numbers.py --fix`（校验 JS 硬编码数字与 HBase 实测值一致，并检查 `strategy_rev` 是否被旧脚本污染）（README）。

## 7. 可展示的亮点清单（均可在文档中找到依据）

1. **强制引用溯源到段**：每条结论带 `[版本·回次·段号]` 角标，点击跳到原文阅读并 `<mark>` 高亮；回跳优先按段落文本匹配、`para_id` 兜底，所以下标偏移也不会跳错（04 §4.2、08 问题 1）。
2. **三路混合检索 + RRF**：bigram 倒排（`hlm_terms` 44.8 万行）+ 512 维向量（`hlm_vectors`）+ 人物共现（`hlm_stats`），用 `1/(60+rank)` 融合——关键词分 [0,1]、向量分 [-1,1] 量纲不同，只用名次天然规避量纲问题（README、04 §2.2、07 §2.5）。
3. **"没有检索到"≠"无法回答"**：把问题分成语料充分 / 元知识兜底 / 精确统计 / 超范围四条路，通识回答必须显式标注「以下内容基于通识知识，非本次检索到的原文」，精确计数不猜数字而是引导用查询工具（27档）。这是"诚实标注"而非统一拒答。
4. **能让 AI 写代码查数据**：用户问"全文出现几次「之」"，系统让 LLM 生成 Python，经 AST 白名单 + 受限 builtins + 数据入口白名单 + prlimit + 网络守卫五层后执行，前端把生成的代码折叠展示、可审计；内存炸弹/CPU 炸弹靠 prlimit 兜底而非 AST（S21实现）。
5. **检索会随问题类型换策略**：`挨打`→`板子/打死`、`宝钗`→`薛宝钗` 这类"原文用词"映射由 LLM 生成关键词完成，规则表作兜底；6 个标准问题上 Top-3 从 5/6 提升到 6/6（S32 §5.1）。
6. **评测找出 3 个真缺陷并逐轮修**：元数据问题答"未找到"（answer_ok 91.3%→100%）、因果问题检索不到（cite_hui_hit 82.6%→91.3%）、脂批没进索引（1,035→11,780，均分 3.27→3.6）；且加脂批后拒答率回退 100%→90%，再靠正则 0.1 ms 软拒答修回（05 §3）。
7. **公开自己的错误而非只报结论**：癸酉本探究页第 7 章专门写两个方法错误（对照语料被污染、定位方法错误）；结论强制分三层（确定 / 统计显著需保留 / 不能从统计推出）（界面 §二⑥）。原理页也直说「L3 的 511 ms 其实是浪费的」（原理 §4）。
8. **Hadoop 分工明确、能自证**：HDFS 存事实源、HBase 存派生索引、MapReduce 离线算 4 个作业（在线一次都不跑）、Hive 提供 SQL；删掉 3 张 HBase 表后从 HDFS 重建，检索结果逐条完全一致（07 §2.3）；MapReduce 与 Spark 在 133,673 个 bigram 上实测对比（`44-S40`）。
9. **顺手被找出来的 bug 讲得清**：L3 图谱通道此前对简称提问恒为 0，原因是人物检测和正文匹配都用了正式名（`贾宝玉 in "宝玉和黛玉…"` 为 False）；修复后召回 0→10。这是"双通道掩盖单通道失效"的典型例子（原理 §四）。
