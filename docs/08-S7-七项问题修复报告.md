## 二、逐项详解

### 问题 1 · 引用跳转定位错误

#### 根因（两层）

**第一层**：后端 `citations` 的 `para_id` 用的是 `p{hui}_{para_start}`，
即「这个 chunk 从第几段开始」。但一个 chunk 覆盖 5~10 段，
点引用落在 chunk **开头**，不是实际命中的那一段。

```
实测：「通灵宝玉上的铭文」引用 chunk para_start=8
      而「莫失莫忘，仙寿恒昌」实际在第 8 回段 14
      → 跳错 6 段
```

**第二层**（修完第一层后暴露）：后端 `para_start` 与前端段落下标**不一致**。

```
后端 chapters.jsonl 的 para[0] 是「回目行」
前端 web/data 的 paragraphs 已剔除回目
→ 同一段落后端 para_start=15，前端下标是 7，偏移 8 段
```

验证数据（第 67 回）：
```
后端 chunk para=15-16  →  内容「来至沁芳桥上立住…」
前端 p67_7             →  内容「黛玉听了这些话，也知宝玉是为自己开心…」  ← 不是同一段
```

#### 修复

**后端**：新增 `hit_para_text()`，在 chunk 内部按 bigram 命中数找出真正的那一段，
返回其**文本**（不只返回下标）：
```python
def hit_para_text(c, question):
    segs = [x for x in text.split(chr(10)) if x.strip()]
    # 逐段算 bigram 命中数 / 长度归一，取最高分
    return segs[best_i][:120]
```

**前端**：`highlightPara()` 优先按 `hit_text` 做文本匹配（免疫下标偏移），
`para_id` 只作兜底：
```js
// 1) 按文本匹配（最可靠）
for (const p of paras) {
  if (norm(p.textContent).includes(key)) { target = p; break; }
}
// 2) 退回 para_id
if (!target && paraId) target = paper.querySelector(`[data-para-id="${paraId}"]`);
```

**附带发现并修复的检索问题**：别名展开把「**通灵**宝玉」拆成了「宝玉/宝二爷/怡红公子」，
导致召回全是宝玉的日常段落，把物件本身丢了。加了 `PROTECTED_TERMS` 保护。

#### 验证

```
修复前 Top-5：第67回、第5回脂批、第67回、第43回脂批、第37回   ← 完全没命中第8回
修复后 Top-1：第8回「那顽石亦曾记下他这幻相并癞僧所镌的篆文」  ← 正是铭文所在段
```

浏览器实测：点引用 → 跳到第8回 → **精准高亮**「那顽石亦曾记下他这幻相并癞僧所镌的篆文」
（截图 `docs/shots/13-fix-citation-jump.png`）

#### 根因

1. `<select id="verSelect">` 有 3 个 `<option>`，但**代码里没有任何 `.onchange` 绑定**
2. 后端 `hlm_chunks` 只有 `version=fuqinju`，其他两版本根本没入库

### 问题 4 · Markdown 渲染

#### 根因

前端用 `txtEl.textContent = answer` 显示，`**粗体**`、`## 标题`、`| 表格` 全部原样输出。

#### 修复

新写 `web/public/js/md.js`（约 300 行，零依赖），支持：

| 语法 | 支持 | 说明 |
|:---|:---:|:---|
| `#` ~ `######` 标题 | ✅ | 降一级（h1 留给页面标题） |
| `**粗体**` `__粗体__` | ✅ | |
| `*斜体*` `_斜体_` | ✅ | 只在一侧是标点/空白时触发，避免误伤 |
| `~~删除线~~` | ✅ | |
| `` `行内代码` `` | ✅ | |
| ```` ```lang ```` 代码块 | ✅ | 带语言标记 |
| `> 引用` | ✅ | 支持多行 + 内部递归 |
| `-` / `1.` 列表 | ✅ | 支持嵌套 + 续行 |
| `\| a \| b \|` 表格 | ✅ | 带横向滚动包裹 |
| `---` 分割线 | ✅ | |
| `[文字](url)` | ✅ | **只允许 http/https/#**，防 `javascript:` |
| XSS 防护 | ✅ | 先 escapeHtml 再插标签 |

#### 关键设计取舍

**为什么自己写而不用 marked.js**：
1. 前端要求零第三方依赖（离线可用、无 CDN）
2. 只需渲染 LLM 输出这一种场景，不需要完整 CommonMark
3. 安全边界自己可控（`marked` 默认允许原始 HTML，需要额外 DOMPurify）

#### 踩到的坑：`**1. 袭人**` 被误判为有序列表

LLM 常输出 `**1. 袭人**（最确凿）`（粗体包编号）。
列表正则 `^\s*\d+[.)]\s+` 会把它当列表项。

修复：行首是 `**` 或 `__` 时一律不按列表处理：
```js
const boldStart = /^\s*(\*\*|__)/.test(line);
const isOl = !boldStart && /^\s*\d+[.)、]\s+/.test(line);
```

#### 验证（15/15 通过）

```
✅ 标题+粗体   ✅ 无序列表   ✅ 有序列表   ✅ 表格
✅ 行内代码     ✅ 代码块     ✅ 引用       ✅ 分割线
✅ 粗体包编号不是列表        ✅ 真实LLM输出
✅ 斜体删除线   ✅ 嵌套列表   ✅ 链接
✅ XSS 防护（<script> 被转义）
✅ 防 javascript: 链接（被替换为 #）
```

浏览器实测（截图 `docs/shots/14-fix-markdown.png`）：
`**正面（八字篆文）**` → 粗体；`> 莫失莫忘，仙寿恒昌` → 引用块；
`---` → 分割线；无任何 `**` `##` 残留。

### 问题 5 · 模型配置自定义

#### 需求

让用户自己填 **API 网址 / 密钥 / 模型名**，并**区分 OpenAI 与 Antigravity 两种协议**。

#### 两种协议的实际差异（这是「注意区分」的核心）

| 维度 | OpenAI 兼容 | Antigravity / Google |
|:---|:---|:---|
| **端点** | `{base}/chat/completions` | `{base}/v1beta/models/{model}:generateContent` |
| **鉴权** | `Authorization: Bearer <key>` | `x-goog-api-key: <key>` |
| **请求体** | `{model, messages:[{role,content}]}` | `{contents:[{role,parts:[{text}]}]}` |
| **角色名** | `user` / `assistant` / `system` | `user` / **`model`**；system 放 `systemInstruction` |
| **响应取文** | `choices[0].message.content` | `candidates[0].content.parts[].text` |
| **流式** | SSE `data: {delta:{content}}` | SSE (`?alt=sse`)，每块取 `parts` |

#### 实现

**后端**：
- `PROVIDERS`（内置）+ `CUSTOM_PROVIDERS`（用户自定义，存 `/app/providers.json`）
- `all_providers()` 合并，自定义优先
- `resolve_key()` 支持两种取密钥方式：配置内 `api_key` 优先，其次 `key_env` 环境变量
- `call_llm()` 按 `kind` 路由到 `_call_openai()` 或 `_call_antigravity()`
- `_msgs_to_antigravity()` 做消息格式转换（assistant→model，system 抽出来）

**新 API**：

| 方法 | 路径 | 用途 |
|:---|:---|:---|
| GET | `/providers` | 列出全部配置（**不回传密钥明文**，只回 `has_key`） |
| POST | `/providers` | 新增/修改（持久化到 JSON） |
| DELETE | `/providers/{id}` | 删除自定义配置（内置不可删） |
| POST | `/providers/test` | **测试连通**（发一条最短请求，填完立刻知道对不对） |

**前端** `providers.js`：配置面板
- 协议单选（OpenAI / Antigravity），切换时输入提示同步变化
- 4 个预设按钮（DeepSeek flash/pro、智谱、Antigravity）
- 「测试连通」按钮 + 「保存」按钮
- 已配置列表（内置/自定义标签、密钥状态、删除、填入表单）
- 折叠的协议差异对照表（用户可自查）

#### 版本如何参与检索

**rowkey 第一段就是版本**（S2 时的设计红利，加版本不用改表结构）：
```
chenggao|text|008|5842a29c1fac0f07

fuqinju|pizhu|008|xxxx
```

**三个检索函数都支持版本过滤**：
```python
def search_keyword(query, topk=30, version=None):
    vers = [version] if version else ROOT_VERSIONS   # 指定版本 or 全部
    for v in vers:
        prefixes.append(f"{v}|text|")

def search_vector(query, topk=30, version=None):
    if version:
        mask = [(v == version) or (s == 'pizhu') for v, s in zip(vers, srcs)]
        sims = np.where(mask, sims, -2.0)              # 向量层掩码过滤
```

`ChatReq.version` 为 `None` 时**三版本融合检索**（当前默认），
指定版本时只检索该版本（脂批始终参与，因为只有抚琴居本有）。
