### 1.1 教材对 A 线的原始定位

教材（`2026-Chapter2.5-Data collection.pdf` p6 / p18）把三条贯穿项目线按「数据世界」分类：

| 项目 | 数据世界 | 主要数据对象 | 最终系统目标 | 重点能力 |

### 1.3 本项目明确「不做什么」（教材 V1 六项要求之一）

| 不做 | 理由 |
|:---|:---|
| **不做红学版本校勘** | 版本只作**元数据记载**，不作研究对象。记录出处/获取时间/校验值/版本号贯穿 Schema 即可 |
| **不训练 NER 模型** | 人物实体用「人物表 + 别名映射 + 规则」覆盖；教材明确不要求深度学习 NER |
| **不部署 Milvus/Weaviate 集群** | 向量能力用 HBase + numpy 暴力检索（实测 2 万×512 维 0.8 ms/查询）；向量库选型不是基础必做项 |
| **不做安全关键控制** | 属 C 线议题 |
| **不做实时流处理主链** | A 线在第 10 章是「持续反馈链」而非实时主链 |
| **不对外分发语料** | 公版文本 + 第三方数据集（CC-BY-4.0 部分须署名）；仅课程教学使用 |
| **不做用户体系与鉴权** | 单机教学演示；仅记录会话，不做账号 |

### 2.3 《项目A-难点分析.md》提出的三项决定成绩档次的难点（U6）

| 难点 | 文档原文要点 | 本项目应对 |
|:---|:---|:---|
| ① Chunk 切分策略论证 | 按回切太长（约 6000 字）、按固定字数切语义断裂、按场景切需文学判断、按人物切跨回；且「分区不破坏版本」把切分策略与分区设计绑死 | **多粒度切分 + 可重建**：以「回→场景段→滑动窗口」三级切分，chunk_id 由 `sha256(version + hui + para_range + strategy_rev)` 决定，策略版本号进 ID → 改策略即新 ID 集，旧索引可并行保留 |
| ② 评测方案设计（事实型 vs 推理型分离） | 事实型可自动评，推理型只能人工抽样；**不能把两类混报一个「准确率 88%」** | 评测集拆两套：`factual`（60 条 golden 中筛 + 自建精确答案集，自动评 EM/F1 + 引用命中率）、`reasoning`（人工抽样 5 分制）**分开报告，不合成单一分数** |
| ③ 版本可追溯而非版本校勘 | 记录版本元数据即可，不研究版本 | `version` 作为**首类字段**贯穿 chunk / vector / index / API 响应；每条答案强制返回 `{version, hui, para_index, char_span}` |

### 4.5 R-50x：Hadoop 技术需求（对应 U7，P0，**核心评分项**）

> 用户明确要求「**RAG 文本和向量存储在 Hadoop 框架下**」。
> 这不是「顺便用一下 Hadoop」，而是**文本与向量的主存储必须落在 HDFS/HBase**。

| 编号 | 需求 | 技术选型 | 验收判据 |
|:---|:---|:---|:---|
| **R-501** | **原文与 Chunk 存 HDFS**，按「版本 / 回次范围」分区 | HDFS 目录 + JSONL/Parquet | `hdfs dfs -ls -R /hlm/warehouse` 可见分层；`fsck` 报告块与副本 |
| **R-502** | **向量存 HBase**（主）+ HDFS（快照） | HBase 表 `hlm_vectors` | 扫描可见 rowkey=chunk_id、列 `v:e` 存 float32 字节；HDFS 侧有 parquet 快照可重建 |
| **R-503** | **Chunk 正文 + 元数据存 HBase**（热点点查） | HBase 表 `hlm_chunks` | 按 chunk_id 取单条 < 20 ms |
| **R-504** | **关键词倒排索引存 HBase** | HBase 表 `hlm_terms`（term → chunk_id 列表） | 单词查询返回 chunk 列表，与 SQLite FTS 对拍 |
| **R-505** | **知识图谱三元组存 HBase** | HBase 表 `hlm_kg`（双写 head/tail 便于双向查） | 一度邻居查询 < 100 ms |
| **R-506** | **统计结果用 MapReduce 计算**，结果回写 HDFS + HBase | Hadoop Streaming（Python mapper/reducer） | 至少 4 个作业：词频、人物频次、共现、逐回统计；JobHistory 有记录 |
| **R-507** | **统计结果用 Hive 提供 SQL 查询** | Hive 外部表映射 HDFS | `SELECT ... FROM hlm_word_freq ORDER BY cnt DESC LIMIT 10` 可跑 |
| **R-508** | **分区设计论证**：章节范围 vs chunk_id 哈希两种方案对比 | max/mean 负载比 | 两种方案负载比数据 + 热点解释（>2 时必须解释） |
| **R-509** | **副本与恢复实验**：2 副本、节点离线仍可读、恢复后校验一致 | HDFS + 自建 manifest | 停 1 个 DataNode 仍可读；恢复后 sha256 一致 |
| **R-510** | **索引可重建**：删掉 HBase 索引表后，能从 HDFS 事实源全量重建 | 重建脚本 | 重建后检索结果与重建前一致（抽样 20 条对拍） |
| **R-511** | **事实源 / 派生层分离**：HDFS 存事实源，HBase 存派生索引 | 目录与表分离 | 文档 + 实际目录结构佐证 |
| **R-512** | **版本不破坏分区**：同一版本的 chunk 落在可一致重建的位置 | `version` 参与 rowkey 前缀 | 变更切分策略后新 ID 体系与旧 ID 可共存、可区分 |
| **R-513** | HDFS 实操证据 | — | 上传/读取/下载成功；`fsck` 的 Block/位置记录；HDFS 架构图 |

### 6.2 分区键设计（R-508）

需比较两种方案（教材要求 ≥2 种）：

| 方案 | 分区键 | 预期收益 | 预期风险 |
|:---|:---|:---|:---|
| **A. 章节范围分区** | `version + hui 范围`（每 10 回一区 → 8 区 × 3 版本） | 范围读取直观；原文可追溯；符合教材「按版本/卷/章范围」 | 各章大小不均（第 67 回 2.9 倍）；批语 4.05 偏斜 |
| **B. chunk_id 哈希分区** | `hash(chunk_id) % N` | 负载均衡（预期 max/mean ≈ 1.1） | 打散章节顺序；范围查询需全分区扫描 |

评分要求：给出两种方案的**记录数 / 字节数 / max/mean 负载比**，>2 时解释热点来源，并提出第二种方案。

### 6.3 Chunk 切分策略（难点①的应对）

| 粒度 | 策略 | 用途 |
|:---|:---|:---|
| L1 | **按回**（81 条，凡例+80 回） | 章节导航、逐回统计 |
| L2 | **按场景段**：以「话说/却说/且说/这里/只见/不在话下/且听下回」等叙事标记 + 空行切分 | RAG 主检索单元（目标 300~800 字） |
| L3 | **滑动窗口**：L2 段超长时按 500 字 / 100 字重叠再切 | 兜底，避免超长块 |

**chunk_id 生成规则**（保证「分区不破坏版本」+「索引可重建」）：

```
chunk_id = sha1( version + "|" + hui + "|" + para_start + "|" + para_end + "|" + strategy_rev )[:16]
```

- `strategy_rev`：切分策略版本号（如 `v1`）。**改策略 → 新 ID 集**，旧索引保留可对比（R-512）
- `version` 进 ID → 不同版本的同位置 chunk **天然隔离**，不会串版本

| 编号 | 规则 | 处置 |
|:---|:---|:---|

## 11. 数量级与容量估算（教材 10% 考核项）

### 11.1 本项目实际规模

| 项 | 计算 | 结果 |
|:---|:---|:---|
| 正文汉字 | 526,673 + 730,730 + 189,383 | **1,446,786 汉字** |
| Chunk 数（L2 场景段估算） | 600,163 字 ÷ 平均 500 字/块 | **≈ 1,200 块** |
| Chunk 数（L3 全量三版本） | 1,446,786 ÷ 500 | **≈ 2,900 块** |
| 向量（2048 维 float32） | 2,900 × 2048 × 4 B | **≈ 23.8 MB** |
| 向量（512 维 float32） | 2,900 × 512 × 4 B | **≈ 5.9 MB** |
| HBase base64 膨胀 | × 4/3 | 2048 维 → **≈ 31.7 MB** |
| 脂批（去重） | — | **8,994 条** |
| 原始语料总体积 | 实测 | **23.53 MB** |

### 11.2 规模扩展推演

| 规模 | 向量存储（2048 维） | 检索方式 | 单机能否 |
|:---|:---|:---|:---|
| 本项目 2,900 块 | 23.8 MB | numpy 暴力 0.8 ms | ✅ |
| 10 万块 | 819 MB | numpy 暴力约 3 ms | ✅ 内存可容 |
| 1,000 万块 | 81.9 GB | **必须 ANN**（HNSW/IVF） | ❌ 内存不够 |
| 1 亿块 | 819 GB | 必须分布式 ANN + 分片 | ❌ |

**结论**：本项目规模下「HBase 存向量 + numpy 暴力」是**正确工程判断**，不是偷懒。
上 ANN 的临界点在**千万块量级**——这与教材「先问访问模式再选存储」的立场一致。

## 12. 风险与失败场景（教材 V1 要求 ≥3 个）

| # | 失败场景 | 影响 | 缓解措施 |
|:---|:---|:---|:---|
| F1 | **两个 DataNode 同时不可用** → 副本数 2 全部丢失 | 数据不可读 | 教学演示中明确这是单机容器的**故障域不隔离**所致（三个节点同一物理机）；生产应 ≥3 副本跨机架 |
| F2 | **embedding 模型更换** → 新旧向量混用导致检索异常 | 答非所问 | 模型 ID 进 rowkey（`m:model_id`）；切换时强制重建（R-604 + R-510） |
| F3 | **DeepSeek API 不可用 / 限流** | 无法生成答案 | 多模型降级（R-607）；检索结果仍可展示「仅检索模式」 |
| F4 | **切分策略变更** → 旧 chunk_id 与新 chunk_id 对不上 | 索引重建失败 | `strategy_rev` 进 ID，新旧并行（R-512） |
| F5 | **HBase 写入热点**（按 `hui` 分区导致第 19 回集中） | 写性能下降 | 预分区 + rowkey 加盐（`hash(ver)%N` 前缀） |
| F6 | **小文件问题**（MapReduce 输出碎片） | NameNode 压力 | 输出用 `-D mapreduce.job.reduces=1` 或合并；文档说明 164 KB 粒度的元数据风险 |
| F7 | **中文编码问题**（`LANG` 未设导致 `-files` 分发中文名崩溃） | 作业失败 | `-files` 文件名一律 ASCII（实测过的坑） |
