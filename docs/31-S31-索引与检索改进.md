## 二、改动①：回目纳入倒排索引

### 2.1 问题

S30 排查时发现：

```
回目（huimu）：第33回 手足耽耽小动唇舌 不肖种种大遭笞挞    ← 有「笞挞」
正文（text）：  …举起大板打了十来下…                     ← 没有「笞挞」
索引（hlm_terms）：只对 text 建，不含 huimu
```

**后果**：用户输入「笞挞」「不肖种种」「风尘怀闺秀」这些回目词，检索 0 命中。

### 2.2 修改

`pipeline/s7_2_index_versions.py:373-375`（原代码）：

```python
for ch in vchunks:
    for bg, tf in bigrams(ch["text"]).items():
        postings[bg].append([ch["chunk_id"], tf])
```

改为：

```python
for ch in vchunks:
    # S31：把 huimu（回目）也纳入倒排索引
    # 只影响倒排召回面，chunk 的 d:text 内容不变（原文阅读仍显示正文）
    _idx = (ch["text"] or "") + " " + (ch.get("huimu") or "")
    for bg, tf in bigrams(_idx).items():
        postings[bg].append([ch["chunk_id"], tf])
```

**关键设计**：只改索引的**文本源**，不改 `d:text` 字段。
用户在原文阅读看到的仍是正文，不会看到回目混进正文。

### 2.3 重建索引

```bash
docker exec master bash -lc "cd /workspace/pipeline && python3 s7_2_index_versions.py"
```

结果：


**词项数 +990**，正是回目带来的新增词项。

## 三、改动②：IDF 加权

### 3.1 问题

`backend/app.py` 原打分：

```python
scores[cid] = scores.get(cid, 0) + 1.0 + min(tf, 2) * 0.1
#                                ↑ 所有 bigram 权重都是 1.0
```

实测 df（文档频率）：

| 词 | df | 性质 |
|:---|---:|:---|
| 宝玉 | 596 | 几乎处处有 |
| 打死 | 24 | 稀有，情节专有 |

两者权重都是 1.0，而「宝玉」在更多 chunk 里出现 → **泛用词主导排序**。

### 3.2 修改

```python
# S31：IDF 加权
# 原实现所有 bigram 权重都是 1.0，导致泛用词（宝玉 df=596）
# 与情节专有词（打死 df=24）等权，泛用词主导排序。
df = int(row.get(b"p:df", b"0").decode() or 0)
idf = 1.0 + math.log((N_CHUNKS + 1.0) / (df + 1.0))
for cid, tf in json.loads(row[b"p:postings"].decode()):
    scores[cid] = scores.get(cid, 0) + idf * (1.0 + min(tf, 2) * 0.1)
```

配合常量（可环境变量覆盖）：

```python
N_CHUNKS = int(os.getenv("HLM_N_CHUNKS", "11780"))
```

**为什么用 `1 + log(...)` 而不是纯 `log(...)`**：
保证 idf ≥ 1，避免 df 极大时权重趋 0 导致整个 bigram 被"静音"。

**为什么不用 `log(N/df)` 纯式**：`df = N` 时 log(1)=0，该词完全失去作用 —— 但像「的」「了」这类词在停用词表里本该被过滤，实际不会出现 df=N 的 bigram。

### 3.3 效果

「宝玉为什么挨打」：

```
修复前：Top5 = 第67回 / 第33回 / ...
修复后：Top5 = 第33回 / 第67回 / ...
```

第33回稳定排第一。

## 四、改动③：全集型问题引用重排

### 4.1 问题

「宝玉的丫鬟有谁」是全集型问题，答案主干来自**人物身份聚合表**（S20 实现），这部分一直正确。

但 **Top-1 引用** 会落在无关回次：

```
修复前引用：第87回 / 第67回 / 第3回
                 ↑ 第87回跟宝玉的丫鬟没关系
```

答案是对的，但用户看到的第一个引用是错的 → 观感上像"答非所问"。

### 4.2 原因

聚合表里每条记录都带 `first_hui`（首见回次）：

```json
{"name": "袭人", "first_hui": 3, "cooccur_sent": 152},
{"name": "晴雯", "first_hui": 5, "cooccur_sent": 57},
...
```

但这些信息只用于**生成参考材料文本**，没有参与**检索排序**。

### 4.3 修改

**① 在 `build_role_context()` 里记录提示回次**

```python
global ROLE_HINT_HUIS
ROLE_HINT_HUIS = sorted({int(x.get("first_hui") or 0)
                         for x in lst
                         if isinstance(x, dict) and x.get("first_hui")})
```

**② 在检索后按提示回次重排**（`/chat` 与 `/chat/stream` 两个端点都加）

```python
if ROLE_HINT_HUIS:
    _hint = set(ROLE_HINT_HUIS)
    _ctxs = r.get("contexts") or []
    _hit = [c for c in _ctxs if int(c.get("hui") or 0) in _hint]
    _rest = [c for c in _ctxs if int(c.get("hui") or 0) not in _hint]
    if _hit:
        _new_ctxs = _hit + _rest
        r["contexts"] = _new_ctxs
        contexts = _new_ctxs      # 关键：citations 后续用的是 contexts 变量
```

### 4.4 踩的坑：只改 `r["contexts"]` 不生效

第一版只写了 `r["contexts"] = _hit + _rest`，日志显示重排执行了，但返回的 `citations` 顺序没变。

**原因**：

```python
contexts = r["contexts"]        # 第 2131 行：变量指向同一个列表对象
...
r["contexts"] = _hit + _rest    # 第 2202 行：r 的键指向新列表
                                #          但 contexts 变量仍指向旧列表！
...
for i, c in enumerate(contexts, 1):   # 第 2236 行：用的还是旧列表
    citations.append(...)
```

**修法**：同时更新 `contexts` 变量。

> 这是一个典型的「变量别名」坑 —— 改字典的键不等于改变量。

### 4.5 踩的坑：只改了 `/chat` 没改 `/chat/stream`

前端用的是 `/chat/stream`（SSE 流式），而我只在 `/chat` 加了重排。

表现为：curl 测 `/chat` 正常，浏览器里没效果。

**修法**：两个端点都加同样逻辑（日志分别标记 `引用重排` / `引用重排(stream)` 便于区分）。

### 4.6 效果

```
修复前引用：第87回 / 第67回 / 第3回 / 第67回
修复后引用：第 3回 / 第 3回 / 第87回 / 第67回
                ↑ 命中提示回次 [3,5,8,21,35,58,59]
```

### 5.2 途中遇到的假警报

测试「林黛玉为什么进贾府」时一度显示「通识」模式，以为是新 bug。

排查发现是 **HBase 瞬断**：

```
[02:32:34] HBase 连接异常，重连重试 1/3: TTransportException(type=4, message='TSocket read 0 bytes')
```

HBase 断开 → 检索返回空 → `classify_question` 走 `knowledge` 分支 → 通识兜底。

HBase 恢复后重测，正常返回「语料」模式。

> **教训**：容器环境里 HBase Thrift 会偶发瞬断，
> 看到"异常行为"应先查 `docker logs` 有没有 `TTransportException`，
> 再怀疑代码逻辑。

### 关于遗留 #1

第67回高频出现的根本原因是它的 chunk 长度大（9,195 字 / 24 段），
而 chunk 越大，命中任意 bigram 的概率越高。

**可选改进**：按 chunk 长度归一化 kw 分数（BM25 的 `b` 参数做法）。
