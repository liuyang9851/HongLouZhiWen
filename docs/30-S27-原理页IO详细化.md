# S27 · 原理页「输入/输出」详细化改造

> 日期：2026-10-25
> 反馈：「拆解的输入/输出不够详细：比如 6 MapReduce 建倒排的输出"3 行倒排（抽样 3 个）"没头没尾，不解释倒排是什么，也没说抽样从哪里抽，写得更详细而具体些，非必要不用自创的术语。」

---

## 一、问题拆解

用户的反馈其实包含 **4 个独立问题**：

| # | 问题 | 具体表现 |
|:--|:---|:---|
| 1 | 输出写得太省 | 「3 行倒排（抽样 3 个）」——几个字，读者不知道这 3 行是什么 |
| 2 | 术语没解释 | 「倒排」是什么？没人说过 |
| 3 | 抽样规则不明 | 「抽样 3 个」——从哪抽的？怎么挑的？ |
| 4 | 自创/缩写术语多 | chunk、bigram、L1/L2/L3、rowkey、postings、df、tf、Reducer… |

这 4 个问题是叠加的：**术语没解释 + 输出太省 + 抽样不明 + 术语太多** = 读者完全无法理解这一步在干什么。

---

## 二、改造方案

### 2.1 新增「先认几个词」章节

在展开逐阶段拆解之前，先用 7 张卡片解释后面会反复出现的词。

| 术语 | 页面上的解释（节选） |
|:---|:---|
| 文本块 | 检索的最小单位。整本书被切成一段段 300~800 字的块，每块有一个编号 |
| 两字组合 | 把汉字按「相邻两字」切开。「宝玉和黛玉」切出来是：宝玉、玉和、和黛、黛玉。用两字而不是整词，是为了不依赖分词 |
| 索引表（倒排索引） | 「两字组合 → 哪些文本块包含它」的表。之所以叫「倒排」，是因为常规思路是「块 → 它有哪些词」，这里是反过来「词 → 哪些块」 |
| 正排表 | 「文本块编号 → 它的正文和出处」的表。先用索引表找到编号，再回这张表取正文 |
| 向量 | 把一段文字变成 512 个小数。语义相近的文字，这 512 个数也相近 |
| 召回 | 从全库 11,780 个文本块里，先粗粗挑出一小批可能相关的 |
| RRF 融合 | 三路各给一个排名，把名次取倒数相加。好处是不用管三路的分数量纲 |

**关键**：「倒排索引」不是自创词，是信息检索的标准术语；但页面必须解释它，不能假设读者知道。

### 2.2 输入/输出改成三段式结构

原来是「一行文字」，现在每个阶段的两端都回答三个问题：

```
┌ 输入 ─────────────────────────────────────
│ 是什么    第 3 回的第 17~25 号段落（共 9 个段落）
│ 规模      9 段正文合计 652 字；加 8 个换行符，计 660 个字符
│ 从哪来    上一阶段那 32 个段落里的第 17~25 个
└───────────────────────────────────────────
                    ↓
┌ 输出 ─────────────────────────────────────
│ 是什么    1 个文本块（检索的最小单位），编号 517c6120437ffe24
│ 规模      660 字符，落在 300~800 字的目标区间内
│ 编号怎么算 把 chenggao|003|0017|0025|09|v2-3ver 做 SHA-1，取前 16 位
└───────────────────────────────────────────
```

**固定键**：`是什么` / `规模` / 后面两个按阶段定制（`从哪来`·`到哪去`·`为什么`·`怎么算`·`怎么做`·`怎么找`·`一个行是什么`）。

### 2.3 用户点名的阶段 6 重写前后对比

#### 改之前

```
输入：527 个 bigram
输出：3 行倒排（抽样 3 个）
```

#### 改之后

**输入**

| 键 | 内容 |
|:---|:---|
| 是什么 | 三个版本全部文本块各自切出的两字组合，以及每个组合在该块内出现几次 |
| 规模 | 全库合计 **448,841** 个不同组合；本块贡献 527 个 |
| 怎么读入 | Hadoop 把 `chunks.jsonl` 切成多个分片，多台机器同时处理，所以这一张表是**分布式算出来的** |

**输出**

| 键 | 内容 |
|:---|:---|
| 是什么 | 一张「两字组合 → 出现在哪些文本块」的索引表，表名 `hlm_terms` |
| 规模 | 全表 **448,841 行**，一行对应一个两字组合 |
| **抽样怎么来** | 页面显示的 3 行**不是随机抽的**：从本块 527 个组合里，按「在本块内出现次数」从高到低取前 3 个 —— 即 <b>宝玉</b>(6次)、<b>丫鬟</b>(2次)、<b>进来</b>(2次)（次数相同则按首次出现顺序） |
| 一行是什么 | 行键 `chenggao\|text\|宝玉`。行内 `p:postings` 是 [(文本块编号, 该块内出现次数), …] 的列表；`p:df` 是包含这个组合的文本块总数 |

**这 4 条正好对应 4 个问题**：是什么→解释倒排、规模→给出总量、抽样怎么来→说清抽样规则、一行是什么→教读者怎么读这一行。

### 2.4 详情区同步去术语

IO 说清了概念后，下方展示真实数据的详情区也逐个改：

| 改之前 | 改之后 |
|:---|:---|
| `Reducer 把同一 bigram 的 (chunk_id, tf) 归并成一行` | `MapReduce 把同一个两字组合的「出现在哪个块、出现几次」合并成一行` |
| `df = 908（含此 bigram 的 chunk 数）` | `p:df = 908（全库有多少个文本块含这个组合）` |
| `postings 中共 908 条` | `p:postings 里共 908 条记录` |
| `✅ 本 chunk 在内，tf = 6` | `✅ 本块在内，块内出现 6 次` |
| `前 3 条 postings` | `前 3 条记录（格式：[文本块编号, 块内出现次数]）` |
| `rowkey 格式 版本\|text\|bigram` | `行键格式 版本\|text\|组合` |
| `chunk_id = sha1(哈希输入)[:16]` | `文本块编号 = SHA-1(哈希输入) 取前 16 位` |
| `汉字 552 个 → 滑窗取相邻两字 → 527 个不同 bigram` | `552 个汉字 → 每两个相邻字组成一个组合 → 527 个不同组合` |
| `用 bigram 而非分词` | `用两字组合而非分词` |
| `chunk 正文` / `rowkey = …` | `文本块正文` / `行键 = …` |

### 2.5 阶段名也改直白

| 原阶段名 | 改为 |
|:---|:---|
| Chunk 切分 | **切文本块** |
| bigram 切分 | **切两字组合** |
| MapReduce 建倒排 | **分布式建索引表** |
| 写入 HBase 正排 | **写入正排表** |
| 闭环：进入问答 | **进入问答环节** |
| L1 关键词召回 | **关键词召回（查索引表）** |
| L2 向量召回 | **向量召回（算相似度）** |
| L3 图谱召回 | **人物共现召回** |
| RRF 融合 + 同回次去重 | **三路结果合并排序** |
| 回表取正文 | **按编号取回正文** |

### 2.6 全文术语清扫（29 处）

| 位置 | 改之前 | 改之后 |
|:---|:---|:---|
| Hero KPI | 倒排行总数 | 索引表总行数 |
| 离线流程 | 切 bigram → 建倒排表 | 切两字组合 → 建索引表 |
| 在线流程 | L1 HBase 点查 103 ms / L2 向量余弦 / L3 共现行 | 关键词（查索引表）· 向量（算相似度）· 人物（读共现行） |
| 在线流程 | RRF 融合 | 三路合并排序 |
| Hadoop 表 | 按 bigram 逐行点查倒排表，取 postings 累加打分 | 按两字组合逐行查索引表，取出记录累加打分 |
| RRF 表头 | `chunk_id` / L1 名次 / L2 名次 / L3 名次 / RRF 分 | 文本块编号 / 关键词名次 / 向量名次 / 人物名次 / 综合分 |
| RRF 标题 | `RRF = Σ 1/(k + rank_i)` | 每路按名次取 1/(60 + 名次)，三路相加得到综合分 |
| 时间条 | L1 关键词（HBase 点查） | 关键词召回（查索引表） |
| 变形链 | L1 bigram 切分 / chunk_id 列表 | 关键词：切成两字组合 / 文本块编号列表 |

**保留的术语**（都是真实文件名/表名/字段名，无法也不该改）：
`chunks.jsonl`、`hlm_terms`、`hlm_chunks`、`hlm_vectors`、`p:postings`、`p:df`、`d:text`、`MapReduce`、`HBase`、`ONNX`。

## 三、顺带修的两处问题

### 3.1 重复内容

建库阶段 4 的「阶段说明」和「详情区说明」几乎逐字相同：

```
阶段说明：chunks.jsonl 上传到 HDFS 后，MapReduce 作业直接从 HDFS 读，
          不需要再经过本地文件。副本数 2 意味着每条数据在两个 DataNode 上各有一份。
详情说明：MapReduce 作业直接从 HDFS 读，不经过本地文件。
          副本 2 意味着每条数据在两个 DataNode 上各有一份。
```

**原因**：IO 改造后，IO 的 `冗余方式` 一行已经说了「存 2 份副本」，
详情区的补充说明与阶段说明都成了冗余。

**修法**：所有阶段的「阶段说明」整块移除，信息统一放在 IO 与详情区。

### 3.2 硬编码的过期数字

流程列表里的时间是写死的，而追踪数据已更新：

| 位置 | 硬编码 | 实际 |
|:---|:---|:---|
| 大模型生成 | 5307 ms | 3,039 ms |
| 关键词召回 | 103 ms | 143 ms |
| 三路合并排序 | 90 个候选 | 30+30+10 |

**修法**：改为从追踪数据动态计算：

```javascript
const tL1 = stages.find((s) => s.id === 2)?.ms || 0;
const nCand = `${s2d.top_candidates ? 30 : 0} + ...`;
```

## 六、学到的一点

写技术文档时，**「我懂」和「读者懂」之间隔着一整套术语**。

这次的问题不是信息缺失——数据一直在页面上，chunk_id、df、postings 都展示了。
问题是**没有给出理解这些数据的框架**：

1. 先解释词（术语表）
2. 再说清每步的输入输出是什么、有多大、从哪来到哪去
3. 最后才展示原始数据

**顺序反了，数据再多也读不懂。**

而「抽样怎么来」这一条尤其关键：它不只是补充说明，
而是告诉读者**「你看到的 3 行代表什么、能不能代表全部」**——
这是数据可信度的问题，不是文字详略的问题。
