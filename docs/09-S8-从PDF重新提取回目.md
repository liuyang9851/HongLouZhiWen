## 二、真正的根因

### 2.1 旧流程根本没从 PDF 提取回目

`hlm_corpus/_extract_fuqinju.py` 第 35 行：

```python
TITLES = {int(k): v for k, v in json.load(
    open(os.path.join(ROOT, "huimu.json"), encoding='utf-8'))['zhiping'].items()}
```

它把回目**写死成 `huimu.json` 的 `zhiping` 字段**。
而该字段本身就有 U+FFFD：

```python
huimu.json['zhiping']['64'] = '第64回 幽淑女悲题五美吟 浪荡子情遗九龙\ufffd'
huimu.json['zhiping']['78'] = '第78回 老学士闲征\ufffd\ufffd词 痴公子杜撰芙蓉诔'
```

**≈ 不是 PDF 提取坏了，是从来没有从 PDF 提取过回目。**

### 2.2 `huimu.json` 三个字段的真实状态

| 字段 | 来源 | 第64回 | 第78回 |
|:---|:---|:---|:---|
| `cgb` | 程高本 | ✅ 九龙**佩** | ✅ 闲征**姽婳**词 |
| `zhiping` | 脂评汇校本（抚琴居） | ❌ 九龙`�` | ❌ 闲征`��`词 |
| `guiyou` | 癸酉本 | 无此回 | 无此回 |

有意思的是：程高本那个字段是好的，抚琴居本那个反而是坏的
—— 说明 `huimu.json` 是分批构建的，抚琴居那批在某个环节损坏了。

## 三、v1 修法错在哪（必须承认）

### 3.1 v1 做了什么

上一轮我用 `cgb`（程高本）回目兜底去修 `zhiping`：

```python
# v1（错误）
ref = huimu['cgb'].get(str(hui))
if ref and '\ufffd' not in ref:
    return ref          # ← 直接把抚琴居本回目换成程高本的
```

乱码确实消失了。**但这是用 A 版本的数据去覆盖 B 版本。**

### 3.2 造成的实际错误

对一个「版本可追溯」的项目，这比乱码更严重 —— 它破坏了版本信息的真实性：

| 第22回 | 制灯**谜** | 制灯**迷** | 异体字被替换 |
| 第25回 | 魇魔法**叔嫂**逢五鬼<br>**通灵玉蒙蔽遇双真** | 魇魔法**姊弟**逢五鬼<br>**红楼梦通灵遇双真** | **版本异文被替换** |

## 四、v2 修法：真正从 PDF 提取

新建 `pipeline/s8_1_rehuimu_from_pdf.py`。

### 4.1 提取策略

1. **双源提取**：
   - 目录页（前 40 页）→ 一次拿全 80 条
   - 正文回首页（全书 2272 页）→ 补齐目录缺失项
2. **处理字间空格**：PDF 里回次常写成「第 七 十 八 回」，正则允许 `\s{0,8}`
3. **清洗**：去页码、站名（`www.hlmbbs.com`、`redactor: kolistan`）、合并多余空格
4. **交叉核对**：与 `cgb` 比对，差异项**逐条人工确认是版本差异还是提取错误**
5. **不覆盖，只纠错**：写出 `huimu_pdf.json` 作为权威来源，同时修 `huimu.json`

## 六、这次的教训

| # | 教训 |
|:---|:---|
| 1 | **乱码要往前追一层**。看到 U+FFFD 就想着「用另一个源覆盖」，是治症状不治病。应该先问：这个字段是哪来的？原始载体（PDF）里是什么？ |
| 2 | **交叉核对 ≠ 直接用另一个版本的数据**。v1 把 `cgb` 当"正确答案"，实际上它只是**另一个版本**。对于版本敏感的项目，跨版本覆盖是数据污染。 |
| 3 | **原文是唯一权威**。`huimu.json` 是中间产物，PDF 才是源。中间产物坏了应该回到源重建，而不是拿另一个中间产物打补丁。 |
| 4 | **差异要核实，不能默认是错**。脚本报出 5 处与程高本不同，如果直接"取一致"，会把 4 处真实的版本异文抹掉。必须回原文逐条确认。 |
