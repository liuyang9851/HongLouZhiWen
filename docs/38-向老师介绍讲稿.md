# 红楼智问 · 向老师介绍讲稿

> 用途：口头汇报 / 当面介绍本机演示
> 时长：**约 5 分钟**（讲 3 分半 + 演示 1 分半）
> 用法：黑体是**要念出来的话**，灰色小字是**给你自己看的提示**，不用念
> 配套：完整命令行版见 `07-课堂演示文档.md`

---

## 一、开场（30 秒）

> **老师好，我做的项目叫「红楼智问」。**
>
> **一句话说：把《红楼梦》和脂批做成一个能问答的系统，而且每个回答都能点回到原文的具体段落。**
>
> **我特意没有做成一个普通的 AI 问答 Demo。普通的做法是「问一句、模型编一段」，对不对没法验证。我做的核心是——答案里每个结论，都能溯源到原文第几回第几段。**

*提示：这里先不要说技术，把"能溯源"这个卖点立住。*

---

## 二、为什么选这个题（60 秒）

> **选这个题，是因为《红楼梦》有三个很适合做大数据的问题。**
>
> **第一，版本混乱。** 市面上有十几个版本，我用了三个：抚琴居校本 80 回、程高本 120 回、癸酉本后 28 回。同一句话在不同版本里可能不一样。所以我的索引里，**版本是主键的第一段**，加新版本不用改表结构。
>
> **第二，脂批是伴随文本。** 脂砚斋的批语有一万条左右，直接透露了后文走向和失稿信息。但它散在正文行间，一般检索抓不到。我把它单独建成了一路索引。
>
> **第三，答错没成本。** 普通问答错了就错了；红楼梦研究里，答错一个细节就是硬伤。所以整个系统的设计目标不是"答得漂亮"，是**"错的能被发现"**。

*提示：这三条对应「版本 / 脂批 / 可溯源」，后面演示时还要回扣。*

---

## 三、Hadoop 到底用在哪（60 秒）

*提示：这是大数据课的评分重点，必须说清楚，不能只说"用了 Hadoop"。*

> **老师可能会问：这个项目哪里算大数据？我用一句话说清楚——**
>
> **存储全在 HDFS。** 原文、切分后的数据、向量快照、MapReduce 的输出，全部落在 HDFS 上，副本 2 份。哪怕前端和后端都挂了，数据还在集群里。
>
> **索引全在 HBase。** 五张表、六十万行：文本块表、向量表、倒排表、词频表、统计表。查一个词，是 HBase 的行键点查，不用扫全表。
>
> **统计用 MapReduce。** 四个作业：词频、人物频次、人物共现、文本块统计。**注意——这些是离线跑完存下来的，在线问答时一次都不跑**，所以检索不到 2 秒。
>
> **另外还挂了 Hive 做 SQL 查询、Spark、Flink、Storm，以及 ZooKeeper。** 集群是 Docker 三节点，master 加两个 slave。

*提示：如果老师追问"为什么不在线跑 MapReduce"，答：因为在线要低延迟，MapReduce 启动就要几十秒，只适合离线。*

## 五、三个亮点（40 秒）

> **最后说三个我觉得做得比较扎实的地方。**
>
> **第一，可溯源不是嘴上说的。** 每个回答都带版本、回次、段号、字符区间，能精确跳到原文。
>
> **第二，不确定就说不确定。** 系统会判断：语料里有就答，没有就用模型通识兜底、并明确标注"非原文"，涉及精确统计就引导用户用查询工具，完全超出范围就软拒答。**不硬编。**
>
> **第三，能让 AI 写代码查数据。** 有些问题靠检索答不了，比如"数据库里各表多少行"。系统会让模型生成一段查询代码，在沙箱里跑完再把结果解读出来。沙箱有五层防护。

# 附：预判提问与参考回答

*提示：这些是老师最可能问的，提前过一遍。*

### Q1「这个项目的大数据体现在哪？数据量不算大吧？」

> **数据量确实不算大——一百多万字、六十万行索引。但大数据课要练的是"体系"，不是"规模"。**
>
> **我练的是完整链路：HDFS 存事实源 → MapReduce 离线算 → HBase 建索引 → 在线点查。这套链路换成十倍数据量也是同一套代码。**
>
> **而且我做了分区设计、副本策略、故障恢复，这些和数据量无关。**

### Q2「为什么不用现成的向量数据库？非要用 HBase？」

> **两个原因。**
>
> **一是课程要求存储落在 Hadoop 生态里。**
>
> **二是 HBase 够用：一万条向量、512 维，整体加载成矩阵做一次乘法就行，根本用不到专业向量库的近似检索。用 HBase 反而能把倒排、向量、正排放在同一个系统里，少一个组件。**

### Q3「检索效果怎么评估的？」

> **我建了评测集，分事实型、推理型、统计型三类。**
>
> **结论是：事实型准确率高，推理型弱一些——这是 RAG 的通病，检索到的片段不足以支撑推理。所以我没有硬提指标，而是加了"三档策略"：推理型问题如果证据不足，就明确说证据不足，而不是编。**
>
> **我认为诚实比分数重要。**

### Q4「如果检索错了会怎样？」

> **会答错，但能看出来。**
>
> **因为每个结论后面带引用编号。老师随便点一个编号，就能看到原文那一段到底说了什么。如果引用和结论对不上，一眼就能发现。**
>
> **这也是我做溯源的原因——不是为了好看，是为了让错误可被发现。**

### Q5「脂批是怎么处理的？为什么单独建索引？」

> **脂批在印刷上是夹在正文中间的，字号小、位置散。如果混在正文里切块，会被切碎。**
>
> **所以我单独提取，一条批语一个块，单独建一路倒排。检索时和正文并行召回，最后融合。**
>
> **提取的时候踩过坑：一开始按字体判断，但有的版本正文也用楷体，导致一条批语吞掉整页、断在页边界。后来改成按字号判断才修好，截断率从 36% 降到 0.1%。**

### Q6「这个项目你花了多久？最难的是什么？」

> **最难的不是写代码，是数据。**
>
> **《红楼梦》的版本、脂批的归属、回目的异文，每一项都要查资料核对。代码反而是最确定的 part。**
>
> **另一个难点是"一致性"：索引改了，前端写死的数字要跟着改，否则页面自相矛盾。所以我专门写了一个校验脚本，检查前端数字和数据库实测值是否一致。**

# 附：一次问答的时间构成（实测）

| 阶段 | 耗时 |
|:---|---:|
| 查询改写 | 0.1 ms |
| L1 关键词召回 | 约 70 ms |
| L2 向量召回 | 约 960 ms |
| L3 图谱召回 | 约 830 ms |
| RRF 融合 + 去重 | 0.2 ms |
| 回表取正文 | 0 ms |
| Prompt 拼装 | 0 ms |
| **大模型生成** | **约 5,300 ms** |
| **合计** | **约 7.2 秒** |

> 可以这样讲：**检索不到 2 秒，剩下 5 秒全在大模型**。
> 所以「索引放 HBase 做点查」这个设计是对的——真正慢的不是检索。

# 附：演示前检查清单

*提示：开场前 3 分钟过一遍，避免现场翻车。*

```powershell
# 1) 集群是否在跑（三节点都要 Up）
docker ps --format "{{.Names}}`t{{.Status}}"

# 2) HBase Thrift 是否起来（容器重启后必须手动启）
docker exec master bash -lc "jps | grep ThriftServer"

# 3) 后端健康
Invoke-WebRequest http://127.0.0.1:8000/health

# 4) 前端
Invoke-WebRequest http://127.0.0.1:5173/api/health
```

| 检查项 | 正常表现 |
|:---|:---|
| 三节点容器 | master / slave1 / slave2 全部 `Up` |
| ThriftServer | 有进程（没有就跑 `hbase thrift start`）|
| 后端 `/health` | `n_chunks` 有值、`hbase: ok` |
| 前端 5173 | 页面能打开、右上角显示「RAG 就绪」|
| 提问测试 | 先自己问一句确认能出答案 |

**备用方案**：万一后端连不上，先讲「项目原理」页（纯静态数据），
这一页能撑 1 分钟，同时后台排查。
