# S21 · 自定义查询：让 AI 写代码并执行

> 日期：2026-10-24
> 需求：「用户向 AI 提问要查询的内容（可以是额外的统计，比如全文中出现了几次"之"字），
>        AI 来编写代码实现查询，换句话说，实现一个让 AI 根据用户需求编写代码并运行的功能」

---

## 一、功能

### 1.1 交互

```
用户：全文出现了几次「之」字？
  ↓ 点 🔬 按钮
AI 写代码 → 沙箱执行 → 自然语言解释
```

界面显示四块：

```
🔬 自定义查询  [fuqinju] ⏱ 1933 ms
├─ AI 生成的代码                      [收起代码]
│    text = load_all_text("fuqinju")
│    n = text.count("之")
│    result = {"count": n, "total": len(text), "ratio": ...}
│    print(f"全文 {len(text)} 字，「之」出现 {n} 次")
├─ 执行结果
│    {"count": 1877, "total": 624373, "ratio": 0.3}
├─ 全文共 624373 字，其中「之」字出现 1877 次，约占全文的 0.3%
└─ 代码在受限沙箱中执行：禁止 import / open / 网络，CPU 5s、内存 512MB 上限
```

### 1.2 实测查询

| 查询 | 结果 |
|:---|:---|
| 全文出现了几次「之」字？ | 1,877 次 / 624,373 字（0.3%） |
| 统计每一回的字数，找出最长和最短的回 | 最长第67回 21,705 字；最短「凡例」957 字 |
| 哪一回出现的「宝玉」最多？ | 第19回 116 次（次名第28回 98 次）|
| 程高本和抚琴居本的总字数差多少？ | 程高 864,355 vs 抚琴居 624,373，差 239,982 |

**全部一次成功，无重试。**

## 二、安全设计（五层防护）

> 这是本功能最关键的部分。让 AI 生成代码并执行，是风险最高的一类功能。

### 2.1 先探明可用的隔离手段（实测）

| 手段 | 可用性 | 说明 |
|:---|:---:|:---|
| `timeout` | 可用 | 墙钟超时 |
| `prlimit --cpu` | 可用 | CPU 时间限制 |
| `prlimit --as` | 可用 | 地址空间限制（实测触发 MemoryError） |
| `prlimit --nproc` | 可用 | 进程数（防 fork 炸弹） |
| `prlimit --fsize` | 可用 | 单文件大小 |
| `unshare --net` | **不可用** | 容器无 CAP_SYS_ADMIN |
| `firejail` / `bwrap` | 不可用 | 未安装 |
| `RestrictedPython` | 不可用 | 未安装 |

**只能靠「AST 白名单 + subprocess 资源限制」双重防护。**

### 2.2 五层防护

**第 1 层 AST 静态检查**（父进程做，不执行）

拒绝：
- `import` / `from ... import` 全部
- `open` / `exec` / `eval` / `compile` / `__import__`
- `getattr` / `setattr` / `globals` / `locals` / `vars` / `dir`
- `__class__` / `__bases__` / `__subclasses__` / `__globals__` / `__builtins__`
- `socket` / `subprocess` / `multiprocessing` / `threading` / `ctypes`
- `while True` / `with` 语句 / `async`
- 超长字符串常量（>100KB）

要求：必须给 `result` 赋值

**第 2 层 受限 builtins**（白名单，只有 50 个安全函数）

`len` / `sum` / `max` / `min` / `sorted` / `range` / `enumerate` / `zip` / `print` / `int` / `str` / `dict` / `list` …
**没有** `open` / `exec` / `eval` / `__import__` / `getattr`

**第 3 层 数据入口白名单**

只能通过 `load_all_text` / `load_chapter` / `load_pizhu` / … 读语料
完全无法碰文件系统

**第 4 层 subprocess 资源限制**

```
prlimit --cpu=5 --as=512M --nproc=8 --fsize=1M --nofile=32
+ timeout 12
```

**第 5 层 网络拦截**

builtins 无 `socket` / `urllib`；子进程内 patch `socket.socket`

### 2.3 安全测试（9 个恶意用例）

| 攻击 | 结果 |
|:---|:---|
| 删库 `import os; os.system("rm -rf /tmp/x")` | **AST 拦截**（禁止 import + system） |
| 读 /etc/passwd | **AST 拦截**（禁止 open） |
| 写文件 | **AST 拦截**（禁止 open） |
| 网络外传 `socket.create_connection` | **AST 拦截**（禁止 import socket） |
| 反射绕过 `().__class__.__bases__[0].__subclasses__()` | **AST 拦截**（禁止双下划线） |
| fork 炸弹 | **AST 拦截**（禁止 import os + while True） |
| 内存炸弹 `bytearray(800MB)` | **MemoryError**（`prlimit --as` 兜底） |
| CPU 死循环 `sum(range(10**9))` | **被 kill**（`prlimit --cpu` 兜底） |
| **正常代码** | 执行成功 |

**8 类恶意代码全部被拦截，正常代码正常执行。**

> 内存/CPU 炸弹通过了 AST 检查（AST 无法预测运行时行为），
> 但被第 4 层 prlimit 兜底 —— **这正是分层的意义**。

## 三、实现

### 3.1 三个新文件

| 文件 | 职责 |
|:---|:---|
| `backend/query_api.py` | 语料 API（沙箱内唯一的数据入口） |
| `backend/sandbox.py` | AST 检查器 + 沙箱执行器 |
| `backend/app.py` | 新增 `/query/custom` 和 `/query/examples` 接口 |

### 3.2 提供给 AI 的 API

```python
load_all_text(ver="fuqinju") -> str       读全书正文
load_chapter(ver, hui) -> str             读某一回
load_chapters(ver) -> list[dict]          逐回结构化
load_pizhu(ver) -> list[str]              读批语
load_person_roles() -> dict               人物身份表
load_stats() -> dict                      统计汇总
VERSIONS / VERSION_LABELS                 常量
```

### 3.3 代码生成 prompt（关键约束）

```
【硬性约束（违反会被安全检查拒绝）】
1. 禁止 import 任何模块（包括标准库）
2. 禁止 open()，读数据只能用上面 API
3. 禁止 exec / eval / compile / __import__
4. 禁止 while True（死循环）
5. 结果必须赋给变量 result
6. 代码不超过 30 行，不要定义 class
```

### 3.4 失败自动重试（用户在 q3 选的 A）

```python
for attempt in range(req.max_retry + 1):     # 默认重试 1 次
    code = await generate_code(question, last_error)
    result = run_sandboxed(code)
    if result["ok"]:
        break
    # 把错误回给 LLM，让它自己修
```

**注意**：安全检查拒绝的代码**不会重试**（避免 AI 反复尝试绕过）。

## 五、附带发现的数据问题

测试「每回字数统计」时发现：**第67回在语料里有 3 条记录**

```
{"hui":67, "chars":21705}
{"hui":67, "chars":12487}
{"hui":67, "chars":9195}
```

原因：`hlm_corpus/fuqinju/` 下有 `067_合并.txt`（21,705 字）、`067a.txt`、`067b.txt`
三个文件，原提取脚本把它们都当成了独立的「回」写进 jsonl。

**影响**：

- 「每回字数统计」会重复计第67回
- 「全书总字数」会多算（624,373 包含重复部分）

**修法**：生成 chapters jsonl 时只保留 `067_合并.txt`，跳过 067a/067b。

> 这是一个**独立的数据问题**，不影响本次自定义查询功能本身
> （功能如实反映了数据现状）。

## 六、局限

| # | 局限 | 说明 |
|:---|:---|:---|
| 1 | 沙箱与后端同容器 | 用户选的 A 方案。若 AI 找到 AST 绕过 + 逃逸 builtins，可访问后端进程资源 |
| 2 | 网络仅靠 builtins + patch | `unshare` 不可用，无法内核级隔离 |
| 3 | 单机串行 | 没有队列，并发多个查询会争 CPU |
| 4 | 无查询历史记录 | 不像问答那样存 qa_logs |
| 5 | AST 黑名单不完备 | 依赖白名单 + 资源限制兜底 |

### 如果要上生产

建议改成 B 方案（独立 sandbox 容器）+ gVisor/Firecracker 类隔离。
当前 A 方案适合**教学/内网演示**场景。
