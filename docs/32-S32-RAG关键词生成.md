# S32 · RAG 流程升级：由模型生成检索关键词

> 日期：2026-10-27
> 用户需求：「更新一下 RAG 过程，先由模型直接处理原提问，生成检索关键词，再由关键词和原问题组合做 RAG 的部分」

---

## 一、改动前后

### 改动前（纯规则改写）

```
用户原问题
   ↓
REWRITE_RULES 规则表（人工枚举的触发词 → 扩展词）
   ↓
别名展开
   ↓
关键词检索 + 向量检索
```

**问题**（S30 已暴露）：
- 规则是人工枚举，覆盖不到就失效
  （「宝玉为什么挨打」曾被注入「进/入/到/接/送」等无关词）
- 规则无法理解语义
  （「挨打」→「板子/打死」这种映射，人穷举不完）

### 改动后（模型生成 + 规则兜底）

```
用户原问题
   ↓
① LLM 生成检索关键词（理解语义 + 红楼专名归一）
   ↓  失败/超时则退回规则改写（兜底）
② 组合检索：原问题 / 原问题+关键词 / 纯关键词 / 规则改写 → 取并集
   ↓
③ L1 关键词 + L2 向量 + L3 图谱 → RRF 融合
   ↓
④ 生成回答
```

## 二、关键词生成实现

### 2.1 Prompt 设计

```python
KEYWORD_SYS_PROMPT = """你是《红楼梦》文本检索专家。用户会给你一个问题，
你要提取用于全文检索的**关键词**。

【任务】
把用户问题转换成一组检索词，要求：
1. **用原文可能出现的词**，不要用现代口语
   · 「挨打」→「笞挞」「板子」「打死」（第33回正文用「板子」「打死」）
   · 「被撵」→「撵出去」「逐出」「打发出去」
   · 「死了」→「没了」「去世」「亡故」「殡天」
2. **补全专名**：简称 → 全名
   · 宝玉 → 贾宝玉　黛玉 → 林黛玉　凤姐 → 王熙凤
3. **补上可能相关的人物/物件/地点**（帮助定位情节）
   · 「宝玉挨打」→ 贾政、金钏、琪官、忠顺王府
4. 关键词 3~8 个，每个 1~4 字

【输出格式】严格输出 JSON：
{"keywords": ["词1", "词2"], "reason": "一句话说明检索思路"}
"""
```

**三个关键设计**：

1. **要"原文用词"而非"问题用词"**
   这是最有价值的一点 —— LLM 知道「挨打」在原文里写作「板子」「打死」。

2. **强约束 JSON 输出**
   避免 LLM 输出解释性长文污染检索。

3. **给出反例/正例**
   `「挨打」→「板子」「打死」` 这类映射示范，比抽象指令有效得多。

### 2.2 容错与降级

```python
async def gen_keywords(question, model_id, timeout=8.0):
    try:
        out = await asyncio.wait_for(call_llm(...), timeout=timeout)
        raw = out.get("content") or ""
        raw = re.sub(r"^```(?:json)?\s*|\s*```$", "", raw).strip()
        m = re.search(r"\{.*\}", raw, re.S)
        if not m:
            return []
        obj = json.loads(m.group(0))
        kws = obj.get("keywords") or []
        # 清洗：只保留中文，长度 1~8
        return [k for k in (str(x).strip() for x in kws)
                if 1 <= len(k) <= 8 and re.fullmatch(r"[\u4e00-\u9fff]+", k)][:8]
    except asyncio.TimeoutError:
        log("关键词生成超时，降级到规则改写")
        return []
    except Exception as e:
        log(f"关键词生成失败: {e}")
        return []
```

**四种降级路径**：
| 情况 | 处理 |
|:---|:---|
| 超时（>8s） | 返回空 → 只用规则改写 |
| 调用失败（网络/额度） | 返回空 → 只用规则改写 |
| 输出不是 JSON | 正则提取 `{...}` 再试 |
| 关键词含非中文/超长 | 单条过滤 |

### 2.3 同步/异步桥接（踩坑）

`retrieve()` 是**同步函数**，`call_llm` 是 **async**。桥接时遇到问题：

```python
# ❌ 直接 asyncio.run 在 FastAPI 里会报
#    RuntimeError: asyncio.run() cannot be called from a running event loop
asyncio.run(gen_keywords(...))

# ✅ 分情况处理
def gen_keywords_sync(question, model_id, timeout=8.0):
    try:
        asyncio.get_running_loop()
        in_loop = True
    except RuntimeError:
        in_loop = False

    if not in_loop:
        return asyncio.run(gen_keywords(...))     # 脚本/测试环境

    # 已在 event loop（FastAPI）→ 丢到线程池
    def _worker():
        return asyncio.run(gen_keywords(...))
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as ex:
        return ex.submit(_worker).result(timeout=timeout + 3)
```

> **关键**：`asyncio.get_running_loop()` 抛异常 = 没有 loop，可以直接 run；
> 不抛 = 有 loop，必须换线程。

## 三、检索流程改造

### 3.1 多路查询组合

```python
# 0) 规则改写（保留，作兜底）
rewrites = rewrite_query(question)

# 1) LLM 生成关键词
llm_kws = gen_keywords_sync(question, model_id, timeout=8.0)
if llm_kws:
    # 组合两路：原问题+关键词、纯关键词
    rewrites.append(" ".join([question] + llm_kws))
    rewrites.append(" ".join(llm_kws))

# 2) 别名展开
queries = []
for rq in rewrites:
    for eq in expand_aliases(rq):
        if eq not in queries:
            queries.append(eq)

# 3) 关键词本身也直接参与 L1（不光是拼成句子）
for k in llm_kws:
    if k not in queries:
        queries.append(k)

queries = queries[:24]
```

**为什么要三种组合**：
| 组合 | 作用 |
|:---|:---|
| 原问题 + 关键词 | 保留语义 + 加锚点 |
| 纯关键词 | 去掉疑问句式干扰，纯粹按词检索 |
| 单个关键词 | 每个词独立检索，取并集最大化召回 |

### 3.2 实测关键词质量

| 问题 | LLM 生成的关键词 |
|:---|:---|
| 宝玉为什么挨打？ | 板子, 打死, 贾政, 金钏, 琪官, 忠顺王府 |
| 晴雯为什么被撵？ | 撵出去, 晴雯, 王夫人, 宝玉, 病, 狐狸精, 打发出去 |
| 林黛玉为什么进贾府？ | 林黛玉, 贾府, 贾母, 林如海, 投亲, 孤女 |

**质量分析**：
- ✅ 抓住了「挨打」→「板子/打死」这类原文用词映射
- ✅ 补全了相关人物（金钏、琪官、忠顺王府 —— 正是第33回的三条导火索）
- ✅ 专名归一（宝钗 → 薛宝钗）

## 四、附带修复：长度归一化

### 4.1 新流程暴露的问题

LLM 关键词变准后，反而暴露了排序问题：

```
「宝玉为什么挨打」Top1 = 第80回（11 字 chunk）
  内容：「与前要打死宝玉遥遥一对。」   kw=10.65
第33回（705 字正文）                      kw=9.95   排第二
```

**超短 chunk 的 bigram 密度虚高。**

### 4.2 语料的长度分布（实测）

| 类型 | 数量 | 平均长度 | 最短 | 最长 |
|:---|---:|---:|---:|---:|
| 正文 | 3,295 | **546 字** | 150 | 879 |
| 脂批 | 8,662 | **30 字** | 2 | 672 |

**差 18 倍。** 这解释了为什么脂批总是抢占前排。

### 4.3 三次尝试（前两次都错）

| 版本 | 做法 | 结果 |
|:---|:---|:---|
| 8.2 | 标准 BM25 归一 `score / (1-b+b*len/avg)` | ❌ 黛玉问题 Top1 从第3回变成第28回<br>**长 chunk 也被压了** |
| 8.3 | 单侧惩罚：只打 `len < 60` 的 chunk | ✅ 宝玉挨打/晴雯被撵/黛玉进府 全对<br>❌ 宝钗搬出仍被脂批带偏 |
| 8.4 | 按 source 分别归一 + 脂批权重 0.75 | ❌ 反而更差（第80回脂批排第一） |
| **8.5** | **单侧惩罚 + 脂批权重 0.6** | ✅ **最佳** |

### 4.4 最终方案（8.5）

```python
# 长度归一化 + 脂批降权
#   ① 超短 chunk 的 bigram 密度虚高（正文平均 546 字 vs 脂批 30 字）
#   ② 脂批是"评点"不是"情节"，不该压过正文证据
_chunks = load_chunks()
_MIN_LEN = 60
_SRC_W = {"text": 1.0, "pizhu": 0.6}
_adj = {}
for cid, sc in scores.items():
    c = _chunks.get(cid) or {}
    _L = len(c.get("text") or "")
    _s = c.get("source") or "text"
    _w = _SRC_W.get(_s, 1.0)
    if 0 < _L < _MIN_LEN:
        _w *= (_L / _MIN_LEN)      # 11 字 → ×0.18
    _adj[cid] = sc * _w
scores = _adj
```

**为什么不用标准 BM25 长度归一**：

本项目的 kw 分数**已经按 qgrams 数量除过**（做了平均化），
再叠一层完整的 `(1-b+b*len/avg)` 等于**双重惩罚**，会把长 chunk 的分数也压下去。

所以改用**单侧惩罚**：只打短的，不动长的。

## 八、遗留

| # | 项 | 说明 |
|:--:|:---|:---|
| 1 | 「刘姥姥进大观园」检索失败 | 关键词抓住了「刘姥姥」「大观园」，但第40回正文未必同时高频出现这两个词 |
| 2 | 「宝钗搬出大观园」仍偏 | 正确答案在第78回（她自述理由），但第99/103回因「薛宝钗」「薛姨妈」命中被带偏 |
| 3 | 无关键词缓存 | 同一问题重复提问会重复调用 LLM |
| 4 | `_MIN_LEN`/`_SRC_W` 是拍定的 | 阈值靠试出来，非统计推导 |

### 关于遗留 #1、#2

这两个问题的共同点是：**答案不在关键词高频共现的地方**。

「刘姥姥进大观园」的正文里，「刘姥姥」和「大观园」可能分开出现在不同段落，
而 bigram 检索是逐 chunk 匹配的，跨段落共现抓不到。

**根治方向**：向量检索本该解决这类语义匹配，但当前 bge-small-zh（512 维）
对古典白话的语义区分力有限。换更大的 embedding 模型会有改善。
