## 一、先摸清真正的瓶颈

上一轮把字号提到 11/12.5，但用户仍觉得小。继续放大前先确认瓶颈在哪：

### 事实① 这台机器的视口只有约 1230 CSS px

```
视口 1230 - 左侧栏 168 = stage 1062
.v-home max-width 1120 > 1062  →  实际按 1062 算
架构图卡片 ≈ 1039px
SVG max-width 1024  →  渲染 1024px，比例 1024/900 = 1.14
```

所以 **CSS 的 `max-width:1120` 在这台机器上不是瓶颈**，视口才是。

### 事实② 课堂投影通常是 1920 宽

那时 stage ≈ 1752，`max-width:1120` 就变成真瓶颈了 —— 明明有空间却只用 1120。

**结论**：放宽 `max-width` 对投影场景有效，对本机无感。

## 三、意外发现：索引又被污染了

放大后截图核对时发现顶部状态变成 **`13,124 chunk`**（应为 11,780）。

### 排查

| 步骤 | 结果 |
|:---|:---|
| 后端 `/health` | chunk=13124，脂批=9854 |
| HBase `strategy_rev` | **`v2-pizhu` × 4,563**（应为 `v3-pizhu3src` × 3,219）|
| 写入时间戳 | `2026-10-26T04:34`（容器 UTC → 北京 **12:34**）|
| 容器 crontab | 无 |
| Windows 计划任务 | 无相关 |
| compose / entrypoint | 不跑管道 |

### 结论

**没有自动触发源** —— 是某次手动执行了旧脚本 `s5_4_add_pizhu.py`（它写 `v2-pizhu`），
覆盖了正确的 `s10_1_unify_pizhu.py`（写 `v3-pizhu3src`）的结果。

这是**第二次**发生（昨天 20:15 一次，今天 12:34 一次）。

### 修复

```bash
docker exec master bash -lc "cd /workspace/pipeline && python3 s10_1_unify_pizhu.py"
```

```
去重: 12,457 → 8,662（合并重复 3,729）
chunk 数: 8,662
hlm_chunks 总行数: 11,780   ← 恢复
```

重启后端后：`chunk=11780 向量=11780 正文=3270 脂批=8510` ✅

## 四、新增：数字一致性校验脚本

这类「硬编码数字过期」反复出现，写个脚本兜底。

`scripts/s32_verify_diagram_numbers.py`

### 它做什么

| 检查项 | 数据源 |
|:---|:---|
| chunk / 向量数 | 后端 `/health` |
| HBase 5 张表行数 | HBase 实测 |
| 图谱节点 / 边数 | `web/data/graph.json` |
| 正文总字数 | `corpus_stats.json` |
| **`strategy_rev` 是否为 v3** | HBase（防旧脚本污染）|

### 用法

```bash
python scripts/s32_verify_diagram_numbers.py        # 只校验
```

## 七、遗留提醒

**索引污染大概率会再发生**，因为：

1. 旧脚本 `s5_4_add_pizhu.py` 还留在 `pipeline/` 目录里
2. 两个脚本写不同的 `strategy_rev`，跑错了很难一眼看出

### 建议

把旧脚本改名或加保护：

```bash
# 方案A：直接重命名，防误跑
mv pipeline/s5_4_add_pizhu.py pipeline/_deprecated_s5_4_add_pizhu.py.old
```

或者在脚本开头加确认提示。
