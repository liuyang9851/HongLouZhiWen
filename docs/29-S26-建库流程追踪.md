# S26 · 补充建库流程：一条数据怎么变成索引

> 日期：2026-10-25
> 需求：「补充一下建库的时候一条数据的流转过程」
> 承接：S25 已展示在线问答全链路（8 阶段），本次补上离线建库（9 阶段）

---

## 一、设计思路

### 1.1 用同一条 chunk 把两个方向接起来

在线追踪里，回答的第 [4] 号引用是 `chenggao 第3回 段17-25`。
我就选**这一条 chunk** 做建库追踪 —— 于是页面上可以形成闭环：

```
建库阶段落下的 517c6120437ffe24
        ↓
问答时被 L2 向量通道命中 → 成为 [4] 号引用
```

用户可以在同一页切换两个标签，看到同一条数据在两个方向上的旅程。

### 1.2 交互：标签页而非堆叠

原理页已有 6 个章节，再加 9 张建库卡片会过长。
改用**标签页**：

| 标签 | 阶段数 | 内容 |
|:---|:---:|:---|
| **建库（离线）** | 9 | 原始文本 → chunk → HDFS → bigram → 倒排 → 向量 → HBase |
| **问答（在线）** | 8 | 改写 → 三路召回 → RRF → 回表 → prompt → LLM |

默认显示「建库」（符合数据生命周期的时间顺序：先建库，后问答）。
两套时间线复用同一个 `renderStageCard`，只是配色和详情渲染不同。

## 二、建库的 9 个阶段

| # | 阶段 | 组件 | 输入 → 输出 |
|:--:|:---|:---|:---|
| 1 | 原始语料落盘 | 本地 txt | PDF 提取 → 8,564 字符/回 |
| 2 | 按段落结构化 | chapters jsonl | 整回文本 → 32 个段落 |
| 3 | **Chunk 切分** | s7_2_index_versions.py | 段落 17–25 → 1 个 chunk / 660 字 |
| 4 | 上传 HDFS | HDFS | chunks.jsonl → 分布式存储（副本 2） |
| 5 | **bigram 切分** | MapReduce Mapper | 552 汉字 → 527 个 bigram |
| 6 | **MapReduce 建倒排** | HBase hlm_terms | 527 bigram → 倒排行 |
| 7 | 向量编码 | ONNX → hlm_vectors | 660 字 → 512 维 / 2048 字节 |
| 8 | 写入 HBase 正排 | hlm_chunks | chunk → 11 个 cell |
| 9 | 闭环：进入问答 | 在线检索 | chunk → 回答的 [4] 号引用 |

## 三、三个关键阶段的可视化

### 3.1 Chunk 切分：哈希可复算验证

这是最核心的设计。页面把**哈希输入**和**输出**并排展示，并给出复算结果：

```
哈希输入
chenggao|003|0017|0025|09|v2-3ver
                    ↓ sha1
chunk_id
517c6120437ffe24          ✅ 复算一致
```

实测数据：

| 字段 | 值 |
|:---|:---|
| chunk_id | `517c6120437ffe24` |
| 哈希输入 | `chenggao\|003\|0017\|0025\|09\|v2-3ver` |
| 复算结果 | **True（完全一致）** |
| 字数 | 660 |
| 目标区间 | 300–800 |
| 策略版本 | `v2-3ver` |

**为什么要把版本放进 ID**：三版本同位置的 chunk 天然不同 ID，不会串版本；
**为什么要把策略版本放进 ID**：改了切分参数后新旧 ID 不会混。

### 3.2 bigram 切分：条形图 + 停用字表

```
汉字 552 个 → 滑窗取相邻两字 → 527 个不同 bigram（共 545 次）

宝玉  ████████████████████████████████████  6
丫鬟  ███████████████                       2
进来  ███████████████                       2
来了  ███████████████                       2
黛玉  ███████████████                       2
...
```

停用字表 22 字：`一上不下个中为了人们到和国在大就我是有的说这都`

> 用 bigram 而非分词，是为了**避免分词错误影响召回**。

### 3.3 MapReduce 倒排：验证本 chunk 在 postings 里

这是**最有说服力的一处** —— 不光展示倒排行的结构，还验证了本 chunk 确实在里面，
且 tf 与本地重算完全一致：

| bigram | rowkey | df | postings 条数 | 本 chunk 在内？ | tf |
|:---|:---|---:|---:|:---:|---:|
| 宝玉 | `chenggao\|text\|宝玉` | 908 | 908 | ✅ | **6** |
| 丫鬟 | `chenggao\|text\|丫鬟` | 163 | 163 | ✅ | **2** |
| 进来 | `chenggao\|text\|进来` | 473 | 473 | ✅ | **2** |

本地重算 bigram 时「宝玉」出现 6 次，「丫鬟」2 次 —— 与 HBase 里存的 tf **完全一致**。
这说明离线建库与本地复算用的是同一套逻辑，没有偏差。

### 3.4 向量编码

```
chunk 正文  →  2048 字节向量
                前 8 维 [0.06157, 0.04851, -0.01146, 0.04508, -0.06666, 0.0044, 0.00856, -0.02629 …]
                L2 模长 = 1.0
```

cell 结构：`m:dim` `m:hui` `m:model_id` `m:source` `v:emb`(2048 B)

### 3.5 HBase 正排：11 个 cell 全展开

| cell | 值 |
|:---|:---|

| `d:source` | text |
| `d:text` | （660 字正文） |
| `m:hui` | 3 |
| `m:huimu` | 第3回 贾雨村夤缘复旧职 林黛玉抛父进京都 |

## 四、建库链路的真实来源

`pipeline/run_all.sh` 六阶段：

```
[0/6] 环境自检（HDFS safemode / live datanodes / YARN nodes）
[1/6] 上传 chunks 到 HDFS      → s2_2_index.py --stage upload
[2/6] 向量化（ONNX）           → s2_2_index.py --stage embed
[3/6] 写 HBase 索引            → s2_2_index.py --stage hbase
[4/6] MapReduce 4 个统计作业   → s3_mapreduce.py
[5/6] 统计写 HBase + Hive      → s3_to_hbase_hive.py
[6/6] 检索验证                 → s2_3_search.py
```

**4 个 MapReduce 作业**：

| 作业 | Mapper | Reducer | 输出 |
|:---|:---|:---|:---|
| wordfreq | job1_mapper.py | job1_reducer.py | wordfreq.tsv（133,673 行） |
| personfreq | job2_mapper.py | job2_reducer.py | personfreq.tsv（41 行） |
| cooccur | job3_mapper.py | job3_reducer.py | cooccur.tsv（588 行） |
| chunkstat | job4_mapper.py | job4_reducer.py | chunkstat.tsv |

**三版本全量**（11,780 chunk）由 `s7_2_index_versions.py` 单独跑，
策略版本 `v2-3ver`：

```python
STRATEGY_REV = "v2-3ver"
TARGET_MIN, TARGET_MAX = 300, 800
WIN_SIZE, WIN_OVERLAP = 500, 100

def make_chunk_id(version, hui, p_start, p_end, seg):
    return sha1(f"{version}|{hui:03d}|{p_start:04d}|{p_end:04d}|{seg:02d}|{STRATEGY_REV}")[:16]
```

## 五、采集过程中踩的 3 个坑

| # | 问题 | 原因 | 修法 |
|:--|:---|:---|:---|
| 1 | **chunk_id 算出来不对**（`0e9ea5ea…` vs 实际 `517c6120…`） | 假设 `SEG=0`，实际该 chunk 是第 3 回的第 10 个切分段 `SEG=9` | 从 HBase `m:seg` 字段读取真实值 |
| 2 | 原始语料 0 字符 | `hlm_corpus` 在宿主机，容器里只挂了 `pipeline/out` | `docker cp` 单个文件到 `/tmp/hlm_corpus/` |
| 3 | 正排行 0 个 cell | rowkey 拼错（因为 chunk_id 错） | 修 #1 后自然解决 |

### 关于坑 1 的教训

我一开始用「回次 + 段区间」推测 chunk_id，忘了**同一段区间可能有多个切分段**
（长段落被 `split_long_text` 按 500 字滑窗切开后，`seg` 会递增）。

正确做法不是猜，而是**从 HBase 读真实字段再反算验证**。

```python
# 从 HBase 读 m:seg，再复算
ps, pe, seg = d[b"m:para_start"], d[b"m:para_end"], d[b"m:seg"]
key = f"{ver}|{int(hui):03d}|{int(ps):04d}|{int(pe):04d}|{int(seg):02d}|{rev}"
print(s1(key))   # -> 517c6120437ffe24  ✅ 与 rowkey 里的 chunk_id 一致
```

### 6.4 顺带修的显示问题

建库阶段 9 的 note 里写了 `**建库和检索在这里接上了。**`，
但 note 是用 `esc()` 渲染的，`**` 原样显示。

修法：加一个 `renderNote()`，先转义再把 `**x**` 转 `<b>x</b>`：

```javascript
function renderNote(t) {
  return esc(t || '').replace(/\*\*(.+?)\*\*/g, '<b>$1</b>');
}
```

## 九、一句话总结

> **建库把书变成索引，问答在索引里取用。**
> 同一条 chunk `517c6120437ffe24` 在页面上走完两个方向：
> 从 8,564 字符的 txt 里被切出 660 字 → 变成 527 个 bigram → 落进倒排表（tf=6）
> → 编码成 512 维向量 → 存进 HBase；一天之后，它被 L2 通道召回，成为回答的 [4] 号引用。
