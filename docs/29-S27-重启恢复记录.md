## 二、实际恢复过程（3 个坑）

### 坑1：compose 文件名不是 docker-compose.yml

```bash
$ docker compose -f docker-compose.yml ps
compose file "docker-compose.yml" is invalid: no such file

$ docker inspect master --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'
D:\Programming\hadoop\cluster\compose.yaml    ← 实际是 compose.yaml
```

**修法**：
```bash
cd D:\Programming\hadoop\cluster
docker compose -f compose.yaml up -d
```

### 坑2：HBase Thrift 不会自动启动

这是**已知的反复出现的问题**。容器重启后，HBase 服务（Master/RegionServer）会自启，
但 **Thrift 9090 需要手动启动**，否则后端连不上 HBase。

```bash
# 检查
docker exec master bash -lc "bash -c 'cat < /dev/null > /dev/tcp/127.0.0.1/9090' && echo OK"

# 启动
docker exec -d master bash -lc "hbase thrift start > /logs/hbase-thrift.log 2>&1"
```

### 坑3：端口 3000 被 Hyper-V 保留（**这次新出现**）

前端启动报错：

```
Error: listen EACCES: permission denied 127.0.0.1:3000
```

排查发现 **Windows 的 Hyper-V 动态保留了端口段**，而 3000 刚好落在里面：

```
netsh interface ipv4 show excludedportrange protocol=tcp

Start Port    End Port
      2980        3079      ← 3000 在这里面
      3080        3179
      3180        3279
      ...
```

**为什么重启前能用**：这些保留段是**动态变化**的，每次 Windows 重启可能不同。

**修法**：`server.js` 支持 `HLM_WEB_PORT` 环境变量，换端口：

```powershell
$env:HLM_WEB_PORT='5173'
node server.js
```

实测可用且不在保留段：**5173**（Vite 默认端口）、4173、5050、7070、8090。

## 五、要「固化」的正确姿势

用户说「忘记固化镜像」。实际上：

### 镜像不需要固化 —— 已经在硬盘上

```
$ docker images | grep hlm-rag-api
hlm-rag-api:6.1   7.24GB   11 hours ago
...
```

**39 个镜像、6 个命名卷全部持久化在 Docker 的存储目录里**，重启不丢。

### 真正需要固化的只有「启动顺序」

问题不是数据，而是**服务不会自动起来**。三个选择：

| 方案 | 做法 | 评价 |
|:---|:---|:---|
| **A. 恢复脚本**（已实现） | 重启后跑一条命令 | ✅ 推荐，简单可靠 |
| B. Docker 容器重启策略 | `--restart unless-stopped` | ⚠️ hlm-api 已设，但 Thrift 仍需手动 |
| C. 开机自启脚本 | 注册 Windows 计划任务 | 可以做，但调试麻烦 |

**当前用 A**。进一步可以把脚本做成桌面快捷方式：

```powershell
# 创建快捷方式到桌面
$ws = New-Object -ComObject WScript.Shell
$sc = $ws.CreateShortcut("$env:USERPROFILE\Desktop\启动红楼智问.lnk")
$sc.TargetPath = "pythonw.exe"
$sc.Arguments = "`"D:\学校事务\大数据原理与应用\红楼智问\scripts\s27_restore_after_reboot.py`""
$sc.WorkingDirectory = "D:\学校事务\大数据原理与应用\红楼智问"
$sc.Save()
```

## 六、清理建议：37 个旧镜像可删

当前累积了 **37 个 `hlm-rag-api` 版本**（每个 7.24 GB，但共享层所以实际占用远小于 268 GB）：

```bash
# 只保留最新的 6.1，删除 6.0 及以下
docker images --format "{{.Repository}}:{{.Tag}}" | grep '^hlm-rag-api:' | grep -v ':6.1$' | xargs docker rmi
```

**注意**：因为都是同一基础镜像的变体，共享层多，实际释放空间可能只有几 GB。
建议先看 `docker system df` 确认。

> 顺带发现：`.dockerignore` 里没有排除 `__pycache__`，可能导致镜像里混入缓存。

## 七、教训

| # | 教训 |
|:---|:---|
| 1 | **数据放命名卷，容器随便重启**。这次没有任何数据丢失，就是因为当初没用容器可写层存数据。 |
| 2 | **Thrift 要手动起**。这个问题已经出现多次（S21/S24 都遇到过），应该写进恢复脚本 —— 现在写了。 |
| 3 | **Windows 动态端口保留是隐形地雷**。3000 昨天能用今天不能用，必须自动探测可用端口而不是硬编码。 |
| 4 | **compose 文件名要确认**。`compose.yaml` 和 `docker-compose.yml` 都能用，但不能猜。 |
| 5 | **「固化镜像」是误解**。镜像本来就在硬盘上；真正需要固化的是**启动流程**。 |
