## 一、项目概述

### 1.1 一句话说明

**把《红楼梦》前 80 回（60 万字）+ 8,510 条脂批（三源：抚琴居 3,219 + 癸酉本 222 + 脂批大全 5,069），做成一个能溯源的知识问答系统：
所有答案都能点回原文具体段落，而文本与向量全部存储在 Hadoop 生态（HDFS + HBase + Hive + MapReduce）里。**

### 1.2 要解决的问题

普通 RAG demo 的通病：

| 通病 | 本项目的处理 |
|:---|:---|
| 答案无法验证 | 每条答案强制带 `[n]` 引用，点击跳转原文并高亮 |
| 编造（幻觉） | 语料没有就明说「未找到」，实测拒答率 100% |
| 向量库用 Milvus/Pinecone | **违反本项目要求**，改用 HBase 存向量 |
| 检索只有一路 | 三路混合：关键词 bigram 倒排 + 向量 + 图谱，RRF 融合 |
| 统计数字说不清口径 | 三个字数口径全部列出来，让用户自己选 |
| 评测报一个「准确率」 | 事实型/推理型/拒答**三类分开报告** |

### 3.2 关键设计：事实源与派生层分离

这是本项目最重要的架构决策（对应教材 §3.10.4）：

```
┌──────────────── 事实源层（HDFS，可靠、可追溯）────────────────┐
│  /hlm/warehouse/chunks/fuqinju/chunks.jsonl      2.0 MB      │
│  /hlm/warehouse/pizhu/fuqinju/pizhu_chunks.jsonl 1.3 MB      │
│  /hlm/derived/vectors/…/vectors.jsonl            2.8 MB      │
│  /hlm/derived/vectors/…/pizhu_vectors.jsonl      8.8 MB      │
│  /hlm/mrout/{wordfreq,personfreq,cooccur,chunkstat}          │
│  /hlm/logs/qa/qa_*.jsonl                                     │
└───────────────────────────┬──────────────────────────────────┘
                            │ 可全量重建
┌───────────────────────────▼──────────────────────────────────┐
│            派生索引层（HBase，低延迟、可重建）                  │
│  hlm_chunks   11,780 行   chunk 正文 + 元数据                 │
│  hlm_vectors  11,780 行   512 维 float32 向量                │
│  hlm_terms   448,841 行   bigram 倒排索引                    │
│  hlm_wordfreq 133,673 行  词频（MapReduce 产出）              │
│  hlm_stats       709 行   人物/共现/逐回统计                   │
└──────────────────────────────────────────────────────────────┘
```

**为什么这么分**（教材原话：「事实源必须可靠、可追溯、有版本；派生层按访问模式选存储、坏了能从事实源重建」）：

| 层 | 存储 | 理由 |
|:---|:---|:---|
| 事实源 | HDFS | 高吞吐顺序读写、多副本容错、便宜；JSONL 人类可读，可审计 |
| 派生索引 | HBase | 低延迟点查、行键范围扫描；可按访问模式重新组织 |

**已实测验证**：删掉 3 张 HBase 表 → 从 HDFS 拉回事实源 → 重建 → 检索结果 **15/15 逐条完全一致**。

### 4.2 HDFS 使用（R-501 / R-509 / R-510 / R-513）

#### 4.2.1 目录规划

```
/hlm/
├── warehouse/                    ← 事实源：语料
│   ├── chunks/fuqinju/chunks.jsonl              2,099,616 B
│   └── pizhu/fuqinju/pizhu_chunks.jsonl         1,310,943 B
├── derived/                      ← 派生：向量快照
│   └── vectors/fuqinju/model=bge-small-zh-v1.5/
│       ├── vectors.jsonl                        2,957,930 B
│       └── pizhu_vectors.jsonl                  9,268,644 B
├── mrin/chunks/chunks.jsonl      ← MapReduce 输入（**注意不是 _mrin**）
├── mrout/                        ← MapReduce 输出
│   ├── wordfreq/part-00000                      1,210,673 B
│   ├── personfreq/part-00000                          502 B
│   ├── cooccur/part-00000                         210,164 B
│   └── chunkstat/part-00000                         1,344 B
├── manifest/chunks_manifest.json ← 分区清单 + sha256
└── logs/qa/qa_20261024.jsonl     ← 问答日志
```

**目录名有讲究**（实测踩过的坑）：
```
❌ /hlm/_mrin  → MapReduce 报 "Input path does not exist"（虽然 ls 能看到）
✅ /hlm/mrin   → 正常
```
原因：Hadoop `FileInputFormat` 会**静默过滤** `_` 和 `.` 开头的路径
（这是约定：`_SUCCESS`、`.crc` 这类元数据文件不该被当数据处理）。

**块利用率分析**（教材知识点）：

| 项 | 值 |
|:---|---:|
| 文件大小 | 2,099,616 B（2.00 MB） |

#### 4.2.4 副本故障注入（R-509 实测）

```
1. 基线：块 blk_1073742639_1839  Live_repl=2（slave1 + slave2）
2. pkill slave1 的 DataNode → Dead datanodes: 1
3. 验证：
   hdfs dfs -cat … | wc -l        → 1,035 行（完整可读）
   hdfs dfs -checksum …           → 889a5aef…（与基线一致）
4. 重启 DataNode：
   Live datanodes (2)，Under-replicated 0，Missing blocks 0，Status HEALTHY
   校验值仍为 889a5aef…
```

#### 4.2.5 索引可重建（R-510 实测）

```
1. 基线：查询「林黛玉为什么进贾府」→ 保存 Top-5（RRF / rowkey / 位置）
2. disable + drop hlm_chunks / hlm_vectors / hlm_terms
3. 确认 HDFS 事实源完好（chunks.jsonl + vectors.jsonl 仍在）
4. hdfs dfs -get 拉回事实源 → 重新写 HBase
5. 再查同一问题 → 与基线逐条对拍
   → ✅ 15/15 行完全一致，零差异
```

### 4.3 HBase 使用（R-502 / R-503 / R-504 / R-508 / R-512）

#### 4.3.1 五张表设计

| 表 | 行数 | 列族 | 列限定符 | rowkey |
|:---|---:|:---|:---|:---|
| `hlm_chunks` | 11,780 | `d`, `m` | `d:text` `d:char_count` `d:source` `m:hui` `m:huimu` `m:para_start` `m:para_end` `m:seg` `m:version` `m:partition` `m:pizhu_versions` | `<ver>\|<source>\|<hui:03d>\|<chunk_id>` |
| `hlm_vectors` | 11,780 | `v`, `m` | `v:emb`（2048 B float32）`m:model_id` `m:dim` `m:hui` | 同上 |
| `hlm_terms` | 448,841 | `p` | `p:postings` `p:df` `p:source` | `<ver>\|[pizhu\|]<bigram>` |
| `hlm_wordfreq` | 133,673 | `f` | `f:cnt` | `<ver>\|<bigram>` |
| `hlm_stats` | 709 | `s` | `s:cnt` `s:n_chunk` `s:n_bytes` `s:n_chars` | `<metric>\|<key>` |

#### 4.3.2 行键设计（教材核心知识点）

```
rowkey = <version> | <source> | <hui:03d> | <chunk_id>
          fuqinju  |  text    |  003      |  bde3ef…
          fuqinju  |  pizhu   |  003      |  001190a5…
```

**三段设计各自的作用**：

| 段 | 作用 | 教材对应 |
|:---|:---|:---|
| `version` 在最前 | 按版本扫描 `scan(row_prefix=b"fuqinju\|")` 一次搞定；**不同版本的同一位置 chunk 天然隔离，永不串版本** | 行键设计 = 访问模式 |
| `hui:03d` 补零三位 | 字典序 = 数值序，`001..080` 可按回次范围扫描 | 行键有序性 |
| `chunk_id` 在尾 | 同回内按 ID 排序稳定，便于定位 | — |

> **这是「版本不破坏分区」（R-512）的直接实现**：
> 版本进 rowkey 前缀 → 分区（按回次）与版本**正交**，加新版本不需要改建表方案。

#### 4.3.3 预分区（写热点治理，教材 V3 硬指标）

```
create 'hlm_chunks', {NAME=>'d',VERSIONS=>1}, {NAME=>'m',VERSIONS=>1},
       SPLITS => ['1','2','3','4','5','6','7']
→ 8 个 region
```

| 项 | 无预分区 | 有预分区（实测） |
|:---|:---|:---|
| region 数 | 1（写满才分裂） | **8** |
| 1,035 行写入耗时 | — | **2.5 s**（约 414 行/秒） |
| 脂批 8,510 行写入 | — | **12.8 s** |

**为什么按 rowkey 首字符切 8 段**：首字符是回次的十位（`0`~`7`），
`SPLITS => ['1'..'7']` 把 80 回切成 8 个区间，8 个 region 并行接收写入。

#### 4.3.4 列族设计

| 表 | 列族 | 设计理由 |
|:---|:---|:---|
| `hlm_chunks` | `d`（data）、`m`（meta） | 正文可能很大且总是整取 → 单独族；元数据小且常用于过滤 → 另一族。**不同访问模式分开** |
| `hlm_vectors` | `v`（vector）、`m`（meta） | 同上 |
| `hlm_terms` | `p`（postings） | 单一用途 |
| `hlm_stats` | `s`（stat） | 单一用途 |

版本数统一设 `VERSIONS => 1`：语料是静态的，不需要多版本，省空间。

#### 4.3.5 向量存储（R-502）

**关键决策：向量以 float32 原始字节存，不是 base64 字符串**

| 方案 | 1,035 条 × 512 维 | 11,780 条 | 评价 |
|:---|---:|---:|:---|
| **float32 bytes（本项目）** | 2.0 MB | **23.2 MB**（11,780 条） | ✅ 无膨胀 |
| base64 字符串 | 2.7 MB | 30.9 MB | 膨胀 4/3 |
| JSON 数组 | ~20 MB | ~232 MB | 膨胀 10× + 精度丢失 |

实测抽样回读：`len(v:emb) == 2048`（= 512 × 4），11,780 条全部一致 ✅

#### 4.3.6 分区方案对比（R-508 实测）

| 方案 | 分区数 | 记录 max/mean | 字节 max/mean | 判定 |
|:---|---:|---:|---:|:---|
| **A 章节范围（每10回）** | 8 | **1.229** | 1.240 | 均衡 ✅ |
| B chunk_id 哈希（8 区） | 8 | 1.105 | 1.110 | 均衡 ✅ |
| B' chunk_id 哈希（16 区） | 16 | 1.268 | 1.292 | 均衡 ✅ |
| C 按版本（1 版本退化） | 1 | 1.000 | 1.000 | — |

**三个有教学价值的结论**：

1. **两种方案的最大/平均负载比都远低于教材阈值 2**
   为什么范围分区这次也不热点？因为切分单元是「场景段」而非「整回」，
   块大小被约束在 151–879 字（mean=589），**块本身就均匀**，热点前提被消除了。
   → 这是「**切分策略决定分区均衡性**」的直接证据。

2. **若按整回分区，就必须解释热点**
   第 67 回 21,728 字 = 均值 7,490 的 **2.9 倍** → max/mean ≈ 2.9 > 2。
   这才是教材说法的正确适用场景。

3. **分区数不是越多越好**
   B（8 区）ratio=1.105，B'（16 区）ratio=1.268 —— 分区数翻倍，负载比反而更差。
   分区越细，越容易被随机波动主导（与 `V3分区实验文档` 里「二级分区 12.57 最倾斜」一致）。

**最终选方案 A**：① 负载比已达标 ② 保留回次顺序，查某回只扫 1 个 region ③ 语义清晰。

### 4.4 MapReduce 使用（R-506）

#### 4.4.1 四个作业（Hadoop Streaming + Python）

| 作业 | Map 输入 | Map 输出 | Combine 输出 | Reduce 输出 |
|:---|---:|---:|---:|---:|

| `personfreq` | 1,035 chunk | 15,000 | **72** | **41** 人物 |
| `cooccur` | 1,035 chunk | 11,562 | **927** | **10,742** 组 |
| `chunkstat` | 1,035 chunk | 1,035 | **81** | **80** 回 |

#### 4.4.2 Combiner 效果（教材「combiner 在同 key 重复多时收益最大」）

| 作业 | Combine 前 | Combine 后 | 压缩率 |
|:---|---:|---:|---:|
| personfreq | 15,000 | 72 | **99.5%** |
| cooccur | 11,562 | 927 | **92.0%** |
| chunkstat | 1,035 | 81 | **92.2%** |

> personfreq 压缩 99.5% 的原因：15,000 次人名提及只对应 41 个人物，
> key 重复度极高，combiner 在 map 端就完成了 99.5% 的聚合，
> Shuffle 数据量从 15,000 条降到 72 条。**这就是 combiner 的价值所在。**

**踩过的坑**：共现最初输出 `a|b \t 1`（两列），Hive 按 tab 分列后

### 5.2 分块策略（三级）

| 级别 | 方法 | 产出 | 用途 |
|:---|:---|:---|:---|
| L1 | 按回 | 81 条 | 章节导航、逐回统计 |
| **L2** | **场景段合并** | **1,035 条** | **RAG 主检索单元** |
| L3 | 滑动窗口 | 67 次触发 | 超长块兜底（500 字 / 100 字重叠） |

**切分参数与实测分布**：

| 指标 | 值 |
|:---|---:|
| chunk 数 | 1,035 |
| 块大小 min / mean / p50 / p95 / max | **151 / 589.3 / 597 / 786 / 879** |
| 总字数 | 609,947 |
| L3 滑窗触发 | 67 次 |
| 尾块合并 | 1,052 → 1,035（并入 17 个碎块） |
| 分区负载比 max/mean | **1.229** |

**chunk_id 生成规则（关键设计）**：

```
chunk_id = sha1(version | hui | para_start | para_end | seg | strategy_rev)[:16]
```

- `version` 进 ID → 不同版本的同位置 chunk 天然隔离
- **`strategy_rev` 进 ID → 改切分策略就得到全新 ID 集**，
  旧索引可并行保留、对比、回滚。这是「索引可重建」的前提。

### 5.3 向量化

| 项 | 值 |
|:---|:---|
| 模型 | `bge-small-zh-v1.5`（ONNX，94.8 MB） |
| 维数 | **512** |
| Pooling | Mean pooling（attention_mask 加权）+ L2 归一化 |
| 正文向量化 | 1,035 条 / 34.7 s（**29.8 chunk/s**） |
| 脂批向量化 | 8,510 条 / 18.0 s（**179 chunk/s**，批量更大） |
| 运行时 | onnxruntime 1.23.2，CPU |
| 存储 | HBase `v:emb`（float32 bytes）+ HDFS 快照 |

**为什么用 bge-small-zh 而不是调用云端 embedding API**：
1. 离线可用（演示环境不保证网络）
2. 免费（11,780 条 × 每次重建，用 API 要花不少钱）
3. 512 维 × 11,780 条 = 8.3 MB，完全可以常驻内存
4. 中文语义检索效果足够（实测引用回次命中率 91.3%）

### 5.4 检索性能（实测）

| 查询 | L1 关键词 | L2 向量 | L3 图谱 | 总检索 |
|:---|---:|---:|---:|---:|
| 贾宝玉的丫鬟有谁 | 27.4 ms | 22 ms | 0 | **102 ms** |
| 林黛玉为什么进贾府 | 93.6 ms | 274.9 ms | 0 | **368 ms** |
| 脂批价值 | 9.9 ms | 19.2 ms | 0 | **29 ms** |

**向量检索的重要优化**：
S2 阶段每次查询从 HBase 扫 11,780 行反序列化（383 ms）；
S4 改成**启动时全量载入内存 numpy 矩阵**，纯计算 < 1 ms。
→ 瓶颈从「HBase 扫描」转移到「矩阵乘」，这是数量级的改进。

**为什么不上 ANN（Faiss/Milvus）**：
实测推算：10 万条 × 512 维 = 195 MB（内存可容，暴力约 3–5 ms）；
1,000 万条 = 19.5 GB（内存不够，必须 ANN）。
本项目 11,780 条规模下暴力检索是**正确的工程判断**，不是偷懒。

### 9.2 评测驱动的四轮修复（真实缺陷）

| 轮次 | 发现 | 根因 | 修法 | 效果 |
|:---|:---|:---|:---|:---|

## 十、工程实践

### 10.1 踩坑记录（9 个，全部实测）

| # | 坑 | 现象 | 根因 | 修法 |
|:---|:---|:---|:---|:---|
| 1 | `hdfs dfs -fsck` 不存在 | Unknown command | fsck 是 `hdfs fsck` 独立子命令 | 用 `hdfs fsck` |
| 2 | **MapReduce 输入 `_` 前缀** | 目录存在但报 "Input path does not exist" | `FileInputFormat` 静默过滤 `_`/`.` 开头路径 | 目录改名不带下划线 |
| 3 | **happybase 表名前缀** | 建表变 `_hlm_chunks`，读写找 `hlm_chunks` → 找不到 | 内部拼接 `prefix + separator + name`，`prefix=b""` 仍会加 `_` | 同时设 `table_prefix_separator=b""` |
| 4 | HBase DDL 被 bash 展开 | 建表语法错，表没建成 | `echo "{VERSIONS=>1}" \| hbase shell` 被 brace expansion 破坏 | 写临时文件用 `hbase shell -n <file>` |
| 5 | `hbase shell describe` 太慢 | 3 张表各等 4 分钟 | 每次启动 JVM 约 240 秒 | 改用 happybase scan(limit=1) 探测 |
| 6 | 表存在性判断误报 | 「已存在」但实际没有 | `name in output` 子串匹配会撞上日志行 | 解析 `=> [...]` 做精确成员判断 |
| 7 | `scan(filter=...)` 不是 Python 函数 | `TDecodeException` | happybase 的 filter 是 Thrift 服务端过滤器语法 | 全表扫建内存字典 |
| 8 | **happybase 线程不安全** | 单请求正常，并发就 `TSocket read 0 bytes` | thriftpy2 的 TSocket 非线程安全，FastAPI 线程池共享连接 | 加锁 + `with_hbase_retry()` 重连 |
| 9 | onnxruntime 不在镜像层 | `ModuleNotFoundError` | 上一轮 `docker exec` 临时装的，属容器可写层 | 写进 Dockerfile |

## 十二、局限与改进

### 12.1 已知局限（诚实列出）

| # | 局限 | 影响 | 改进方向 |
|:---|:---|:---|:---|
| 1 | 只用前 80 回（抚琴居校本） | 后 40 回内容无法回答 | 把程高本后 40 回也切 chunk 入索引 |
| 2 | 小文件问题（块利用率 1.56%） | HDFS 空间浪费 | 教学规模可接受；生产应合并大文件 |
| 3 | 向量检索是暴力扫描 | 规模 > 10 万条会变慢 | 上 HNSW / Faiss（但违反「Hadoop 生态」要求，需权衡） |
| 4 | 无重排序（reranker） | Top-5 精度还有提升空间 | 加 bge-reranker 或 LLM 重排 |
| 5 | 推理型未人工评分 | 评测结论不完整 | 15 条 × 2 人独立打分，算 Kappa |
| 6 | 单机 ZooKeeper | 不是真正的高可用 | 生产应部署 ZK 集群 |
| 7 | 分区数与 DataNode 数不匹配 | HBase 8 region 但只有 2 个 RegionServer | 生产应 region 数 ≈ RegionServer 数 × N |
| 8 | 脂批 9 个版本未分离检索 | 问「甲戌本怎么批」无法精确回答 | 加 `version` 维度到检索过滤 |
| 9 | 无用户体系 | 无法多用户隔离 | 需求明确「不做用户体系」 |
| 10 | 未做版本校勘 | 「哪个版本对」无法回答 | 明确非目标（《难点分析》要求不做校勘） |

### 12.2 明确的非目标

依据 `项目A-难点分析.md`，以下**不做**：

| 非目标 | 理由 |
|:---|:---|
| 红学版本校勘 | 本项目「版本 = 元数据」，不做「哪个版本更对」的判断 |
| NER 模型训练 | 用别名表 + 规则足够，训练成本高收益低 |
| Milvus / Weaviate 集群 | 违反「RAG 存储在 Hadoop 框架下」的硬性要求 |
| 实时流式主链 | 语料是静态的，批处理足够 |
| 用户注册/登录 | 需求未要求，增加复杂度 |
| 语料再分发 | 版权与许可考量 |

### 12.3 后续可做（按性价比排序）

1. **推理型人工评分**（半天，补齐评测结论）
2. **后 40 回入索引**（1 小时，覆盖率立刻提升）
3. **重排序**（1 天，Top-5 精度可能 +5~10%）
4. **多模型横向对比**（半天，有评测集现成）
5. **脂批按版本检索**（1 天）
6. **语义缓存**（半天，重复问题不重复调 LLM，省钱）
