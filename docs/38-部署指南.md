## 一、先获取项目和数据

### 1. 克隆仓库

```bash
git clone https://github.com/liuyang9851/HongLouZhiWen.git
cd HongLouZhiWen
```

仓库约 **30 MB**，含全部代码、文档、前端数据（章节 + 脂批）。

### 2. 下载大文件（必需）

有两类文件**不在 git 仓库里**，必须从 GitHub Release 下载：

| 文件 | 大小 | 内容 | 不下的后果 |
|:---|---:|:---|:---|
| `hlm-deploy-v1.0-full.zip` | 114 MB | 完整部署包（含数据+模型） | 跑不起来 |
| `hlm-data-v1.0.zip` | 28 MB | 仅数据快照（已有模型时用） | 本地/HDFS 模式无数据 |
| `hlm-model-bge-small-zh-v1.5.zip` | 52 MB | 仅 embedding 模型 | 向量检索不可用 |

**最简单：只下 `hlm-deploy-v1.0-full.zip`（114 MB），解压即用。**

到 https://github.com/liuyang9851/HongLouZhiWen/releases 下载。

### 3. 解压方式（二选一）

**方式 A：只要完整包**（推荐新手）

```bash
# 下载 hlm-deploy-v1.0-full.zip 后
unzip hlm-deploy-v1.0-full.zip -d hongloumeng-qa
cd hongloumeng-qa
# 已经包含 deploy/data/ 和 backend/models/，可以直接跑
```

**方式 B：clone 仓库 + 补下载缺失部分**（适合想跟 git 更新）

```bash
git clone https://github.com/liuyang9851/HongLouZhiWen.git
cd HongLouZhiWen

# 下数据 + 模型两个分包
unzip ~/Downloads/hlm-data-v1.0.zip -d deploy/
unzip ~/Downloads/hlm-model-bge-small-zh-v1.5.zip -d backend/models/
```

### 4. 校验下载完整性

Release 附带了 `SHA256SUMS`：

```bash
# Linux / macOS
sha256sum -c SHA256SUMS

# Windows PowerShell
Get-FileHash hlm-deploy-v1.0-full.zip -Algorithm SHA256
# 与 SHA256SUMS 里的值比对
```

### 5. 确认目录完整

```bash
ls deploy/data/*.jsonl              # 应有 7 个文件
ls backend/models/bge-small-zh-v1.5/model.onnx   # 应约 90 MB
```

如果缺文件，按 `deploy/data/README.md` 和 `backend/models/README.md`
里的说明自行获取（含国内镜像地址）。

## 二、一键启动（推荐先看这节）

所有模式都走**同一个入口**：

```bash
cd 项目根目录

./start.sh --cluster       # 完整 Hadoop 集群（HBase）
./start.sh --with-hdfs     # 单节点 HDFS（只有 Docker）
./start.sh --local-only    # 纯本地文件（最快）
./start.sh                 # 自动探测，有集群就用

./start.sh --status        # 只看状态
./start.sh --stop          # 停止全部
```

### 四种模式对比

| 模式 | 数据源 | 需要 Hadoop | 冷启动耗时 |
|:---|:---|:---:|:---:|
| `--cluster` | HBase（完整集群） | ✅ 已有集群 | 11~20 秒 |
| `--with-hdfs` | 单节点 HDFS | ✅ 自带 | 1~2 分钟 |
| `--local-only` | 本地 JSONL | ❌ | 30 秒 |

**四种模式的检索结果完全相同**（实测 5/5 命中一致）。

### 它会自动做什么

```
1. 检查 Docker / Node 版本
2. 检查 backend/.env（缺了就提示填 Key）
3. 按模式准备数据源
   · --cluster  → 起集群 + 等 HDFS/HMaster/Thrift + 后端
   · --with-hdfs → 建/起 hlm-hdfs + 等数据导入 + 后端
   · --local-only → 直接挂 deploy/data
4. 等后端加载满 11,932 chunk（不满足就报错并给排查命令）
5. 在 Windows 侧启动前端（WSL 必需，见下）
6. 打印访问地址
```

### Windows / WSL 用户注意

**前端必须在 Windows 侧启动。** WSL2 的 localhost 转发只对
Windows → WSL 单向有效，WSL 里起的 node 服务，Windows 浏览器访问不到。

`start.sh` 会自动检测 WSL 环境并调用 `start-web.ps1`：

```
▸ 启动前端 ...
  WSL 环境，转到 Windows 侧启动
  [web] starting on http://127.0.0.1:5173
  [web] ready on http://127.0.0.1:5173
  ✓ 前端就绪（http://127.0.0.1:5173）
  （Windows 侧运行，WSL 内无法直接 curl 验证，以启动器退出码为准）
```

如果前端单独出问题，可以手动跑：

```powershell
powershell -ExecutionPolicy Bypass -File start-web.ps1
powershell -ExecutionPolicy Bypass -File start-web.ps1 5180   # 换端口
```

**两个容易踩的坑**（脚本已处理，但手动操作时会遇到）：

| 坑 | 现象 | 原因 |
|:---|:---|:---|
| `set` 后面有空格 | 前端 503，日志 `Failed to parse URL from http://127.0.0.1:8000 /health` | `set VAR=value && next` 把空格写进了变量值 |
| 用 `cmd /c start` 启动 | `EADDRINUSE: 3000` | 环境变量没传过去，退回默认端口 3000（Windows 保留段）|

## 三、先看这个：版本兼容性

### 2.1 核心问题

你的 Hadoop **各组件版本可能和我的不一致**。这对项目的影响**差别很大**：

| 组件 | 版本敏感度 | 说明 |
|:---|:---:|:---|
| **HDFS**（文件 + WebHDFS） | **低** | 文件格式与 REST API 从 Hadoop 1.x 到 3.x 稳定 |
| **HBase**（Thrift 接口） | **极高** | 见下表，3.x 直接不可用 |
| MapReduce / Hive | 低 | 本项目只消费它们的输出文件，不调用 API |
| Spark / Flink / Storm | 无 | 项目未使用（见 README 说明） |

### 2.2 一个诚实的说明：验证覆盖范围

我的开发环境是 **Hadoop 3.3.6 + HBase 2.5.10**，因此：

| 组合 | 验证状态 |
|:---|:---|
| Hadoop 3.x + HDFS 模式 | ✅ **实测通过** |
| 纯 Docker 本地模式 | ✅ **实测通过** |
| Hadoop 2.x + HDFS 模式 | ⚠️ **未实测**（端口 50070 的探测逻辑已写，但没有 2.x 环境验证） |
| HBase 1.x / 2.x + HBase 模式 | ✅ 2.x 实测；1.x 未实测 |
| Hadoop/HBase 3.x + HBase 模式 | ❌ **已知不可用** |

如果你在 2.x 环境遇到问题，很可能是端口或 API 差异，
欢迎反馈（这也是我标注「未实测」的原因，而不是假装都验证过）。

### 2.3 HBase 版本兼容性（重点）

本项目用 `happybase` 访问 HBase，它**只实现了 Thrift1 协议**：

| HBase 版本 | Thrift1 (9090) | happybase 能否连 | 本项目可用性 |
|:---|:---:|:---:|:---|
| HBase 1.x | ✅ 支持 | ✅ | ✅ 可用 |
| HBase 2.x | ✅ 需手动启动 | ✅ | ✅ 可用（我的环境） |
| **HBase 3.x** | ❌ **已移除** | ❌ | ❌ **完全不可用** |

**结论：如果你用 HBase 3.x，HBase 模式无法使用。**

这不是本项目的问题，是 `happybase` 库本身的限制。换 Thrift2 网关或改用其他客户端才能解决（工作量大，未做）。

### 2.4 因此我做了什么改动

**S39 的核心调整：把数据从「HBase 表」迁移到「HDFS 文件」。**

```
旧方案（S38）              新方案（S39）
─────────────              ─────────────
HBase 表    ←────────────  HDFS 文件（JSONL）
  ├ hlm_chunks              ├ /hlm/warehouse/chunks3ver/chunks_3ver.jsonl
  ├ hlm_vectors             ├ /hlm/derived/vectors3ver/.../vectors_3ver.jsonl
  ├ hlm_terms               ├ /hlm/warehouse/pizhu3src/pizhu_3src.jsonl
  └ hlm_stats               └ /hlm/derived/vectors3ver/.../pizhu_3src_vectors.jsonl
  ↑ 版本敏感                 ↑ 版本无关（WebHDFS HTTP API）
```

**这意味着**：
- 你只需要一个能跑 HDFS 的 Hadoop（2.x / 3.x 都行）
- 不需要装 HBase、不需要配 Thrift、不用管版本
- 本地 `deploy/data/` 和 HDFS 上是**同一批文件**，格式完全一致

## 四、三条部署路线怎么选

| 你的环境 | 选哪条 | 部署时间 | 有 Hadoop 吗 |
|:---|:---|:---:|:---:|
| **有 Hadoop 集群**（任意 2.x/3.x） | **路线 A：接入现有集群** | 10 分钟 | ✅ 你自己的 |
| **只有 Docker，没有 Hadoop** | **路线 B：起单节点 HDFS** | 15 分钟 | ✅ 内置的 |
| 只想最快看到效果 | 路线 B-：纯本地文件 | 8 分钟 | ❌ |
| 有 HBase 1.x/2.x 且想复现表结构 | 路线 C：HBase 模式 | 40 分钟 | ✅ |

**三条主路线（A / B / C）的检索逻辑和结果完全相同**（实测 9/10 命中一致）。

### 关于路线 B

**只有 Docker 的同学不必退化成纯本地模式。** 项目自带一个
「单节点 HDFS」镜像（`hadoop/Dockerfile.hdfs`，2.54 GB），
一条命令就能起一个真 HDFS：

```bash
./start.sh --with-hdfs
```

这样你能得到：
- 真的 HDFS（`hdfs dfs -ls` 可用，有 WebHDFS UI）
- 项目通过 WebHDFS 读数据（**和路线 A 完全同一条代码路径**）
- 不需要装 HBase、不用管版本

代价：首次要构建镜像（约 3~5 分钟，取决于网速），镜像 2.54 GB。

## 五、路线 A：HDFS 模式（有 Hadoop · 推荐）

### 4.1 环境要求

| 项 | 要求 |
|:---|:---|
| Hadoop | **2.x 或 3.x 均可**（只要 HDFS 能跑） |
| Docker | 20.10+ |
| Node.js | 20+ |
| 磁盘 | 约 1.5 GB |

### 4.2 确认 HDFS 可用

```bash
# 假设你的 namenode 容器叫 master（换成你的实际容器名）
docker exec master hdfs dfs -ls /

# 检查 safe mode（应为 OFF）
docker exec master hdfs dfsadmin -safemode get
```

若显示 `Safe mode is ON`，先退出：
```bash
docker exec master hdfs dfsadmin -safemode leave
```

### 4.3 确认 WebHDFS 可用

这是本方案的关键依赖（**版本无关的 HTTP REST API**）：

```bash
# Hadoop 3.x
curl http://127.0.0.1:9870/webhdfs/v1/?op=LISTSTATUS

# Hadoop 2.x（端口不同）
curl http://127.0.0.1:50070/webhdfs/v1/?op=LISTSTATUS
```

应返回 JSON（`{"FileStatuses":...}`）。若失败：

```bash
docker port master      # 检查端口是否映射到宿主机
```

> 如果没映射，`start.sh` 仍能通过 Docker 网络访问（不需要宿主机端口）。
> 但手动 curl 测试需要 `-p 9870:9870`。

### 4.4 把数据导入 HDFS

```bash
chmod +x tools/import_to_hdfs.sh
./tools/import_to_hdfs.sh master
```

脚本做四件事（只用 `hdfs dfs` 基础命令，跨版本兼容）：

```
1. 检查容器/HDFS 可用性
2. hdfs dfs -mkdir -p /hlm/{warehouse,derived}/...
3. docker cp 数据进容器 → hdfs dfs -put 上传
4. 校验行数（应 3295）
```

预期输出：

```
▸ 目标容器: master
▸ 数据目录: deploy/data
▸ 创建 HDFS 目录 ...
▸ 拷贝数据到容器 /tmp/hlm_import ...
    chunks_3ver.jsonl  (6.1M)
    ...
▸ 上传到 HDFS ...
▸ 验证上传结果 ...
  -rw-r--r--   2 root supergroup    6.0 M ... /hlm/warehouse/chunks3ver/chunks_3ver.jsonl
▸ chunks_3ver.jsonl 行数: 3295（应为 3295）
```

### 4.5 配置并启动

```bash
cp backend/.env.example backend/.env
# 编辑填入 DEEPSEEK_API_KEY

chmod +x start.sh
./start.sh
```

`start.sh` 会**自动探测**：

```
▸ 检查基础环境 ...
▸ 探测数据源 ...
  发现 Hadoop 容器: master
  Docker 网络: hadoop-lab_cluster
  WebHDFS 可用: http://master:9870/webhdfs/v1
▸ 数据源: HDFS（http://master:9870/webhdfs/v1）
    数据位置: /hlm/warehouse/ 与 /hlm/derived/
▸ 构建后端镜像（首次约 1 分钟）...
▸ 启动后端 ...
▸ 等待后端就绪（加载 11,932 chunk + 11,957 向量）...
▸ 后端就绪（11932 chunk，数据源 hdfs）
▸ 启动前端 ...
✅ 启动完成

  前端界面   http://127.0.0.1:5173
  数据源     hdfs
             http://master:9870/webhdfs/v1
```

### 4.6 手动指定（如果自动探测失败）

```ini
# 在 backend/.env 里加：
HLM_DATA_SOURCE=hdfs
HLM_WEBHDFS_URL=http://master:9870/webhdfs/v1
HLM_HDFS_BASE=/hlm
```

> 手动指定用于：容器名不是 `master`/`namenode`、端口不是 9870/50070、网络名不规范。

## 六、路线 B：Docker 单节点 HDFS（只有 Docker · 推荐）

### 5.1 这是什么

项目自带一个**只含 HDFS 的轻量镜像**，可在你的 Docker 里起一个真 HDFS（伪分布式，单容器）。

| 项 | 值 |
|:---|:---|
| 镜像 | `hlm-hdfs`（2.54 GB） |
| 内含 | Hadoop 3.3.6（仅 HDFS 组件）+ JDK 11 |
| 运行方式 | 单容器同时跑 NameNode + DataNode |
| 端口 | 9870（WebHDFS/UI）、9000（RPC），映射到宿主 19870/19000 |
| 数据 | Docker volume `hlm-hdfs-data` 持久化 |
| 首次构建 | 3~5 分钟（下载 730MB Hadoop 包） |
| 启动到就绪 | 约 12~30 秒 |

> 对比：完整 hadoop-lab 镜像 6.89 GB（含 HBase/Spark/Hive/Flink/Storm/ZooKeeper）。
> 本项目的数据源层只需要 HDFS，所以砍掉其余组件。

### 5.2 一条命令启动

```bash
cp backend/.env.example backend/.env
# 编辑填入 DEEPSEEK_API_KEY

chmod +x start.sh
./start.sh --with-hdfs
```

`start.sh` 会：

```
▸ 检查基础环境 ...
▸ 选择部署方案 ...
▸ 启动单节点 HDFS ...
▸ 构建 HDFS 镜像（首次约 3~5 分钟）...
▸ 等待 HDFS 就绪（格式化 + 导入数据，约 30~60 秒）...
▸ 方案: 单节点 HDFS（容器 hlm-hdfs）
▸ 构建后端镜像（首次约 1 分钟）...
▸ 等待后端就绪（加载 11,932 chunk + 11,957 向量）...
▸ 后端就绪（11932 chunk，数据源 hdfs）
▸ 启动前端 ...
✅ 启动完成

  前端界面   http://127.0.0.1:5173
  数据源     hdfs
             http://hlm-hdfs:9870/webhdfs/v1
  HDFS UI    http://127.0.0.1:19870
```

**注意**：`start.sh` 默认是交互式询问。如果你不想交互，加 `--with-hdfs` 直接进入该模式。

### 5.3 HDFS 容器做了什么（自动化的部分）

启动脚本 `hadoop/entrypoint.sh` 会自动完成：

```
1. 首次启动 → hdfs namenode -format
2. 启动 NameNode
3. 等待退出 safe mode（约 4 秒）
4. 确认 WebHDFS 可访问
5. 启动 DataNode
6. 创建项目目录 /hlm/{warehouse,derived,logs}
7. 检测到 /seed 挂载 → 自动导入 4 个数据文件
8. 前台等待，保持容器存活
```

**数据自动导入**：因为启动时挂了 `-v ./deploy/data:/seed:ro`，
容器检测到 `/seed/chunks_3ver.jsonl` 就自动 `hdfs dfs -put`。

日志示例：

```
[hdfs] 11:23:18 首次启动，格式化 NameNode ...
[hdfs] 11:23:20 格式化完成
[hdfs] 11:23:20 启动 NameNode ...
[hdfs] 11:23:25 safe mode OFF（等待 4 秒）
[hdfs] 11:23:25 WebHDFS 就绪
[hdfs] 11:23:25 启动 DataNode ...
[hdfs] 11:23:31 DataNode 状态: 1 项
[hdfs] 11:23:31 创建 HDFS 目录 ...
[hdfs] 11:23:37 检测到 /seed 数据，自动导入 ...
[hdfs] 11:23:39   chunks_3ver.jsonl ✓
[hdfs] 11:23:41   pizhu_3src.jsonl ✓
[hdfs] 11:23:44   vectors_3ver.jsonl ✓
[hdfs] 11:23:47   pizhu_3src_vectors.jsonl ✓
[hdfs] 11:23:47 HDFS 就绪
```

### 5.4 验证 HDFS 真的在跑

```bash
# 1) 容器健康状态
docker ps --filter name=hlm-hdfs
# STATUS 应含 "(healthy)"

# 2) HDFS 目录
docker exec hlm-hdfs hdfs dfs -ls -h /hlm/warehouse/chunks3ver/
# 应看到 chunks_3ver.jsonl  6.0 M

# 3) 数据行数
docker exec hlm-hdfs hdfs dfs -cat /hlm/warehouse/chunks3ver/chunks_3ver.jsonl | wc -l
# 应为 3295

# 4) WebHDFS 从宿主机访问
curl http://127.0.0.1:19870/webhdfs/v1/hlm?op=LISTSTATUS

# 5) 浏览器打开 HDFS UI
#    http://127.0.0.1:19870
```

### 5.5 手动操作（不用 start.sh）

如果你想把 HDFS 和项目分开管理：

```bash
# 1) 构建 HDFS 镜像
docker build -f hadoop/Dockerfile.hdfs -t hlm-hdfs .

# 2) 建网络（两个容器要互通）
docker network create hlm-net

# 3) 起 HDFS（映射端口避开已有集群的 9870/9000）
docker run -d --name hlm-hdfs     --network hlm-net     -p 127.0.0.1:19870:9870     -p 127.0.0.1:19000:9000     -v hlm-hdfs-data:/data     -v "$(pwd)/deploy/data:/seed:ro"     --restart unless-stopped     hlm-hdfs

# 4) 等就绪（约 30 秒）
docker exec hlm-hdfs hdfs dfs -ls /hlm/warehouse/chunks3ver/

# 5) 起后端（注意 --network 和 URL 用容器名）
docker build -f backend/Dockerfile.standalone -t hlm-api ./backend
docker run -d --name hlm-api -p 8000:8000     --network hlm-net     --env-file backend/.env     -e HLM_STORAGE=local     -e HLM_DATA_SOURCE=hdfs     -e HLM_WEBHDFS_URL=http://hlm-hdfs:9870/webhdfs/v1     hlm-api

# 6) 起前端
cd web && HLM_WEB_PORT=5173 node server.js
```

### 5.6 资源占用

| 项 | 值 |
|:---|:---|
| HDFS 镜像磁盘 | 2.54 GB |
| HDFS 容器内存 | 约 700 MB（NameNode 512M 堆 + DataNode 384M 堆） |
| 后端容器内存 | 约 1.2 GB |
| 合计内存 | **约 2 GB** |
| 数据 volume | 约 43 MB（4 个 JSONL） |

8 GB 内存的电脑足够。

### 5.7 Apple Silicon（M1/M2/M3）用户注意

镜像基于 `eclipse-temurin:11-jre-jammy`，该基础镜像有多架构支持，
Docker Desktop 在 Apple Silicon 上会自动拉取 arm64 版本。
Hadoop 是纯 Java 程序，理论上有 JRE 就能跑。

**但：我没有 Apple 设备，无法实测。** 如果启动失败，可能原因：

| 现象 | 可能原因 |
|:---|:---|
| `exec format error` | 基础镜像架构不匹配 → 试 `--platform linux/amd64` |

### 6.4 三个已知坑

#### 坑 1：Thrift 不会自动启动

**现象**：容器重启后所有检索 500：

```
TTransportException: Could not connect to ('master', 9090)
```

**原因**：`hbase thrift start` 是独立进程，不是 HBase Master 的子进程。

**修法**（手动）：

```bash
docker exec -d master bash -lc "hbase thrift start > /logs/hbase-thrift.log 2>&1"
```

**修法**（自动，见 `deploy/cluster-config/entrypoint-fixed.sh`）：
加一个 30 秒轮询守护，不在就拉起。

#### 坑 2：HBase meta 损坏后无法启动

**现象**：`HMaster` 启动 30 秒后崩溃，日志是：

```
hbase:meta,,1.1588230740 is NOT online;
state={... server=slave2...,16020,<旧时间戳>}
Master startup cannot progress, in holding-pattern
```

**原因**：meta 的 `info:server` 指向已死的 RegionServer 会话。

**这个修复很重**，完整步骤见 `docs/42-S40H-HBase元数据损坏修复.md`。
简要：

```bash
# 1) 停全部容器
docker stop master slave1 slave2

# 2) 清 ZK（务必用实际卷名！见下方坑 3）
docker inspect master --format '{{range .Mounts}}{{.Name}} -> {{.Destination}}{{println}}{{end}}'
docker run --rm -v <实际卷名>:/data hadoop-lab:2026.10 -c "rm -rf /data/zookeeper"

# 3) 起 master（只跑 NameNode）+ slave（只跑 DataNode）
HLM_NO_HBASE=1 docker compose -f compose.yaml -f compose.override.yaml up -d master
HLM_NO_REGIONSERVER=1 ... up -d slave1 slave2

# 4) 退出 safemode，删 /hbase
docker exec master hdfs dfsadmin -safemode leave
docker exec master hdfs dfs -rm -r -f -skipTrash /hbase

# 5) 完整模式重启，等 90 秒初始化
docker stop master
HLM_NO_HBASE=0 ... up -d

# 6) 重建表 + 导数据（回到 6.2）
```

#### 坑 3：compose 卷名带项目前缀

```bash
# compose.yaml 里写的是 master-data
# 实际卷名是 hadoop-lab_master-data（项目名 + 下划线 + 卷名）
```

**用错卷名会创建一个同名的空卷，清理操作全是空操作。**
这次排查在这一点上耗了最久。永远先用 `docker inspect` 确认。

### 6.5 容器反复退出怎么办

如果 `master`/`slave` 启动后几十秒就 `Exited (1)` 且没有日志，
是原版 entrypoint 的 `wait -n` 缺陷：

```bash
wait -n "${children[@]}"    # 任一子进程退出 → 整个容器退出
```

HBase Master 崩一次就带走 NameNode 和 ZooKeeper，slave 随之崩溃，形成死循环。

**修法**：用 `deploy/cluster-config/` 里的修复版：

```bash
cp deploy/cluster-config/* /path/to/cluster/
cp deploy/cluster-config/entrypoint-fixed.sh /path/to/cluster/workspace/cluster-entrypoint-fixed.sh
cd /path/to/cluster
docker compose -f compose.yaml -f compose.override.yaml up -d
```

修复版做了三件事：

| 改动 | 效果 |
|:---|:---|
| 服务分级（核心/边缘） | RegionServer 崩了不再带走 DataNode |
| 边缘服务自动重拉（3 次） | YARN/Spark/RegionServer 挂了能自愈 |
| Thrift 轮询守护 | 9090 不再丢 |

### 6.6 healthcheck 显示 unhealthy

如果 slave 显示 `unhealthy` 但服务正常，是 healthcheck 检查了边缘服务：

```yaml
# 错的：要求 RegionServer(16020) 和 Spark Worker(8081) 也通
nc -z slave1 9864 && nc -z slave1 8042 && nc -z slave1 16020 && nc -z slave1 8081

# 对的：只查真正必需的
nc -z slave1 9864 && nc -z slave1 8042
```

`deploy/cluster-config/compose.yaml` 里已经改好了。

## 九、常见问题

### Q1: `n_chunks` 是 0 或 -1

**排查顺序**：

```bash
# 1) 看数据源探测日志
docker logs hlm-api 2>&1 | grep -E '数据源|载入'

# 2) 看具体探测失败原因
docker exec hlm-api python3 -c "import data_source;print(data_source.describe())"
```

常见原因：

| 现象 | 原因 | 解决 |
|:---|:---|:---|
| `probe_log: ["HDFS: URLError"]` | WebHDFS 连不上 | 检查端口/容器名/网络 |
| `probe_log: ["local: ... 不存在"]` | 本地数据没挂载 | 检查 `-v` 参数 |
| `source: none` | 两者都不可用 | 走 3.4 导入 HDFS，或走路线 B |

### Q2: HDFS 模式连不上 WebHDFS

```bash
# 从容器内测试（关键：不是宿主机）
docker exec hlm-api python3 -c "
import urllib.request
print(urllib.request.urlopen('http://master:9870/webhdfs/v1/?op=LISTSTATUS',timeout=5).status)
"
```

| 原因 | 检查 | 对策 |
|:---|:---|:---|
| 容器不在同一 Docker 网络 | `docker inspect hlm-api` | `--network <hadoop网络>` |
| 端口不对（2.x 是 50070） | `docker port master` | 改 `HLM_WEBHDFS_URL` |
| WebHDFS 未启动 | `docker exec master netstat -tlnp \| grep 9870` | 查 `dfs.webhdfs.enabled` |
| 容器名不是 master | `docker ps` | 改 URL 里的主机名 |

### Q3: 只有 Docker，能跑真 Hadoop 吗

**能。** 路线 B 自带单节点 HDFS 镜像：

