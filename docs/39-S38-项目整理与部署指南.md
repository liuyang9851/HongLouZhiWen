> 日期：2026-10-27

## 一、核心问题：原项目无法被他人部署

排查发现的**四个阻断性障碍**：

| # | 障碍 | 后果 |
|:--:|:---|:---|
| 1 | 后端**强依赖 HBase** | 同学必须装一套 3 节点 Hadoop 集群 |
| 2 | `Dockerfile` **FROM hadoop-lab:2026.10** | 基础镜像外部拿不到，构建必失败 |
| 3 | **缺 `requirements.txt`** | Python 依赖无从安装 |
| 4 | 脚本**硬编码 `D:\` 路径** | 换机器全部失效 |

其中 #1 是根本矛盾：**RAG 能力绑死在 HBase 上**。

## 二、关键决策：双模式架构

### 2.1 方案对比

| 方案 | 优点 | 缺点 | 采纳 |
|:---|:---|:---|:---:|
| 只发 HBase 版 | 架构完整 | 同学装不上，等于没发 | ❌ |
| 只发本地版 | 好部署 | 丢失 Hadoop 展示价值 | ❌ |
| **双模式** | 都能满足 | 需写适配层 | ✅ |

### 2.2 实现方式

新增 `backend/storage_local.py`，在 `app.py` 的四个入口处分流：

```python
def use_local_storage() -> bool:
    """
    HLM_STORAGE 取值：
      local  → 强制本地
      hbase  → 强制 HBase
      auto   → 先试 HBase，连不上自动降级
    """
```

分流点：

| 函数 | HBase 版 | 本地版 |
|:---|:---|:---|
| `load_chunks()` | scan `hlm_chunks` | 读 `chunks_3ver.jsonl` + `pizhu_3src.jsonl` |
| `load_vectors()` | scan `hlm_vectors` | 读两个 vectors jsonl，拼 numpy 矩阵 |
| `search_keyword()` | 查 `hlm_terms` 倒排 | 内存 dict 倒排 |
| `search_vector()` | numpy 矩阵点积 | 同上（代码复用） |
| `search_graph()` | 查 `hlm_stats` cooccur | 扫描 chunk 实时算共现 |

### 2.3 数据快照

从容器导出 7 个 JSONL 到 `deploy/data/`（48 MB）：

## 三、让本地模式「结果一致」的三次修正

这是本次最花时间的地方 —— 本地版不是简单读文件就行，
**打分逻辑必须和 HBase 版逐项对齐**，否则排序全乱。

### 3.1 修正①：向量字段名

| 症状 | 向量完全没载入，全部召回退化为纯关键词 |
|:---|:---|
| 原因 | 我按 `emb` / `vector` 找字段，实际是 **`vec_b64`** |
| 修法 | `rec.get("vec_b64") or rec.get("emb") or rec.get("vector")` |
| 效果 | 向量矩阵 11,957 × 512 正常载入 |

### 3.2 修正②：IDF 的 df 必须按版本统计

| 症状 | `宝玉为什么挨打` Top1 从第33回变成第80回 |
|:---|:---|
| 原因 | HBase 的 `p:df` 是**单版本内**的文档频率（如 fuqinju 内「晴雯」df=117）<br>本地版把所有版本合起来算 df（≈3 倍大）→ IDF 偏小 → 泛用词权重虚高 |
| 实测 | HBase `kw=9.66` vs 本地 `kw=2.38`（差 3.9 倍） |
| 修法 | 建索引时按 `ver|src` 分组统计 df，打分时用对应版本的 df 和 N |

### 3.3 修正③：图谱通道的 score 口径

| 症状 | `宝玉和黛玉是什么关系` Top1 从第3回变成第49回 |
|:---|:---|
| 原因 | HBase 给的是 `cnt/100`（共现 237 次 → score=2.37，强信号）<br>本地版偷懒给了固定 `0.5`（弱信号）→ 被其它通道顶掉 |
| 修法 | 本地实时算出共现 chunk 数，`score = cnt/100`，与 HBase 完全一致 |

### 3.4 对齐结果

10 个标准问题，Top-3 命中：

| 模式 | 命中 |
|:---|:---:|
| 完整 HBase | **9 / 10** |
| 本地模式 | **9 / 10** |

**持平。**（唯一差异是「晴雯为什么被撵」偶有波动，属排序细节）

```
1. 检查 Docker / Node >= 20
2. 检查 .env 是否存在（不存在则从模板创建并提示填 Key）
3. 检查 Key 是否还是占位符
4. 检查数据快照是否完整
5. 构建镜像
6. 启动容器（本地模式 + 挂载数据）
7. 轮询 /health 直到就绪（最多 120 秒）
8. 启动前端
9. 打印访问地址与常用命令
```

## 七、诚实披露（写进部署指南的局限）

部署指南里明确写了三件事，避免误导同学：

### 7.1 本地模式不体现 Hadoop 价值

> 本地模式**不体现 Hadoop 的分布式价值**。
> 如果你要展示「这个项目用了 Hadoop」，必须跑完整 HBase 模式。
> 本地模式的定位是「**让人能快速看到效果**」。

### 7.2 检索质量基线（含失败项）

明确列出 10 题里哪题会失败：

> 「刘姥姥进大观园」这题两种模式都偏（到第103回）——
> 原因是「刘姥姥」和「大观园」在多回分别出现，跨段落共现抓不到。
> 属于已知局限，非部署问题。

### 7.3 内存占用偏大

> 倒排索引是主要开销：11,780 个 chunk 每个约 200 个 bigram，
> 共约 232 万个 posting 条目。Python 字典/list 的内存开销是 C 数组的 5~10 倍。
> **优化方向（未实施）**：改成 `array` 或 `marisa-trie`，可降到 100 MB 内。

## 八、踩坑记录

### 坑①：`_N_BY_VER` 推导式作用域错误

```python
# 错（变量 v 不在作用域）
_N_BY_VER = {k: len(v) and sum(...) for k in _df_by_ver}
# → NameError: name 'v' is not defined

# 对（改成显式累积）
_cnt_by_ver = {}
for c in _chunks.values():
    k = f"{c.get('version')}|{c.get('source')}"
    _cnt_by_ver[k] = _cnt_by_ver.get(k, 0) + 1
```

**教训**：Python 3 推导式有独立作用域，外部变量不能直接引用。
复杂推导式不如写成显式循环。

### 坑②：测试用了 dummy key 导致误判

一开始用 `-e DEEPSEEK_API_KEY=dummy` 测试，
结果本地模式的 **LLM 关键词生成全部失败**（只有 3 路查询而非 5 路），
命中率偏低 —— 我一度以为是本地模式实现有问题。

换成真实 key 后恢复正常。

**教训**：**测试环境要尽量仿真**。降级路径（LLM 失败）和主路径的行为差异很大，
用 dummy key 测出来的结果不能代表真实表现。

### 坑③：`docker rm -f hlm-api-standalone:test` 语法错误

`docker rm` 只接受容器名，`docker rmi` 才删镜像。
混用导致清理失败，旧的测试容器残留占用端口。
